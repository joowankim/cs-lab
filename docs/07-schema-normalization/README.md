# 정규화 관계도

07 스키마 설계와 정규화 실험을 복습하는 설명용 화면이다. 페이지 하나에 장면 셋을 두고, 장면마다 작은 표로 쿼리를 한 단계씩 따라간다. 단계마다 관계도(표와 그 단계에서 본 칸, 결과, 락 목록), 코드, 모든 단계를 한눈에 보는 띠가 같은 단계를 가리킨다. 2026-11-23에 만들었다.

화면의 단계는 설명용 모형(`model.js`)이 만든 순서다. 장면 1의 표는 실험 SQL(`sql/01`, `sql/02`)의 행과 같고, 맥에서 돌린 구성의 결과는 묶음 ② 결과와 같다. 장면 2의 고친 행 수 규칙은 원자료의 `check`와, 계획 문구는 원자료의 `EXPLAIN FORMAT=TREE`와 같다. 장면 3의 A·B 락은 원자료의 `performance_schema.data_locks`와 같다(아래 "확인 결과"). 실측값은 "실험에서 잰 값" 칸에만 있고, 모두 [실험 README](../../experiments/07-schema-normalization/README.md)의 결과에서 옮겼다.

06 화면과 같은 틀로 만들었다. 전체 지도, 요소를 눌러 여는 설명 칸, 재생 버튼은 두지 않았고, 관계도는 SVG가 아니라 HTML 표로 그렸다. 이상과 정규화는 행과 칸을 보는 것이라 표가 가장 읽기 쉽다고 봤다.

## 그림 규칙

[01 화면의 그림 규칙](../01-concurrency-models/README.md#그림-규칙)과 [06 화면의 그림 규칙](../06-mysql-joins/README.md#그림-규칙)을 따른다. 아래는 이 화면에서 정하거나 바꾼 것이다.

- 테이블은 표 하나, 행은 줄 하나다. 위에 테이블 이름과 그 장면에서의 역할(회원, 차, 예약, 클러스터형 인덱스(행), 보조 인덱스 리프, 부모, 자식)을 적는다. 보조 인덱스는 리프 항목을 정렬된 순서대로 줄로 그린다.
- 지금 따지는 행은 굵은 파랑 테두리, 찾은 짝과 쥔 락은 옅은 파랑, 이 단계에 들어가거나 바뀐 행은 옅은 파랑 굵은 글자, 읽었지만 쓰지 않은 행은 회색 글자, 지운 행은 줄을 긋는다. 이상(값이 갈린 행, 함께 지워진 사실, 넣지 못한 행), 락 대기, 오류는 옅은 주황이다. 넣지 못한 행은 주황 점선 테두리다.
- 그 단계에서 읽거나 고친 칸은 칸 안의 값에 테두리를 둘러 표시한다(`member_plan`, `car_number · type · fee` 등).
- 한 표 `reservation_flat`의 칼럼 여덟 개는 넷(예약 id, 회원 셋, 차 셋, 시각)으로 묶어 휴대폰 폭에서도 옆으로 밀지 않는다.
- 락 목록은 `data_locks`처럼 누구·대상·모드·상태를 적고, 대기(WAITING)는 주황, 쥔 락(GRANTED)은 파랑이다. 락의 종류(테이블, 레코드)와 모드(IX·IS·S·X)를 다른 칸에 적는다.
- 색은 세 갈래다. 파랑은 지금 행과 짝·결과·쥔 락, 주황은 이상·대기·오류, 나머지는 회색이다. 어두운 테마도 같다.
- 단계는 이벤트의 순서이고 시간 길이가 아니다. 사람이 적을 예상은 미리 채우지 않는다. "내 예상" 칸은 비워 두고, 적은 글은 그 브라우저에만 남는다.

## 화면 구성

위에서부터 장면 버튼, 먼저 생각해 볼 질문과 "내 예상" 칸, 구성 버튼, 단계 이동 막대(방향키, Home, End로도 옮김), 관계도와 설명 한 문장·개수 칸, 코드와 그 구성이 실험에서 돌린 것인지, 모든 단계 띠가 이어진다. 아래 접힌 칸에 볼 것, 실험에서 잰 값, 근거와 복습 카드가 있다. 주소 끝에 `#anomaly`, `#denorm`, `#fk`를 붙이면 그 장면으로 열린다.

| 장면 | 구성 | 보는 것 | 실험 README |
|---|---|---|---|
| 이상과 나누기 | (A) 등급 바꾸기, (B) 예약 없는 새 차 넣기, (C) 예약 3 지우기, 나누기·되살리기 × 한 표, 나눈 표 | 한 표에서 kim의 등급이 둘로 갈리는 행, 기본 키가 NULL일 수 없어 넣지 못하는 행(오류 1048·1364), 함께 지워지는 차의 사실. 결정자마다 표를 떼어 나누고, JOIN으로 원래 행을 잇고 양쪽 EXCEPT 0행·0행 | 묶음 ②, 질문 3·4 |
| 정규화와 비정규화 | Q1, Q2, U1, U2 × 정규화(JOIN), 비정규화(등급 복사), 비정규화 + 새 인덱스 | 인덱스 리프만 읽는지(커버링) 행으로 다시 가는지, 등급으로 거를 인덱스가 없어 전체를 훑는지, 등급을 바꿀 때 고치는 행 수와 지우고 다시 넣는 인덱스 항목 | 묶음 ③, 첫 해석, 질문 7 |
| 외래 키와 락 | 외래 키 있음, 없음 × A가 커밋하지 않음(실험), A가 커밋함(모형) | 외래 키 검사가 부모 members·cars의 기본 키 레코드에 거는 S 모드 레코드 락, B의 UPDATE가 원하는 X 모드와의 충돌과 오류 1205, 외래 키가 없을 때 바로 고치는 B | 묶음 ④, 첫 해석, 질문 5·6 |

## 모형의 가정

- 장면 1은 실험의 작은 표(예약 3행, 회원 2명, 차 2대)를 그대로 쓴다. 맥에서 돌린 구성은 한 표의 (A)(B)(C)(`sql/01`)와 나눈 표의 (B)·되살리기(`sql/02`)다. 나눈 표의 (A)(C)와 한 표의 나누기는 실험에서 돌리지 않았고, 화면의 코드 칸 아래에 "모형"이라고 적힌다. 나누기는 결정자(`member_email`, `car_number`)마다 `SELECT DISTINCT`로 표를 떼는 순서로 보였고, 그 결과는 `sql/02`가 만든 표와 같다.
- 장면 2는 회원 5명(골드 2명), 예약 13건(회원 1은 5건, 나머지는 2건씩), Q1은 최근 3건이다. 실험은 회원 10만(골드 2만), 예약 100만(회원 1은 1만 건, 회원 2~99001은 10건씩), Q1은 최근 20건이다. 단계 하나는 인덱스 항목 하나나 행 하나를 읽거나 고치는 일이다. 비정규화 + 새 인덱스의 U에서 `member_plan`이 인덱스 키에 있어 항목을 지우고 다시 넣는 것은 InnoDB 보조 인덱스 갱신 방식을 그린 것이고, 실험의 `Using temporary`는 그리지 않았다(까닭은 실험 README에서 추측으로 남김). Q2 비정규화 + 새 인덱스는 실험 계획대로 인덱스 전체를 훑는다.
- 장면 3은 회원 2명·차 1대, A가 예약 1건을 넣는다. A의 락 다섯 개와 B의 대기는 실험의 `data_locks`와 같다. 락을 얻는 순서(회원 먼저, 차 다음)는 외래 키 칼럼 순서로 그렸고 실험에서 확인하지 않았다. "A가 커밋함"과 외래 키 없음에서 B가 X 락을 얻는 단계는 실험에서 기록하지 않은 모형이다(실험은 외래 키 없음에서 B가 0.00146초에 1행을 고쳤다는 것만 남김).

## 확인 결과

`node --test model.test.cjs`(Node.js 18 이상, 따로 설치할 것 없음)로 아래 8개를 확인했다(2026-11-23, 모두 통과).

1. 원자료(`2026-11-20T210942023292-norm`, `2026-11-20T212601895675-norm-cov`, `2026-11-20T214449560144-fk`)의 모든 기록이 검증을 통과했다.
2. 장면 1의 표가 `sql/01`, `sql/02`의 행과 같다.
3. 장면 1의 결과가 실험 README 묶음 ② 결과와 같다: (A) kim의 등급 두 값, (B) 오류 1048·1364와 0행, (C) 0행, 되살리기 3행·EXCEPT 0행·0행, 나눈 뒤 새 차를 넣어도 3행. 한 표의 나누기 결과가 `sql/02`의 표와 같다.
4. 장면 2에서 앞 단계의 그림이 뒤 단계의 변경에 영향받지 않는다.
5. 장면 2의 고친 행 수 규칙(정규화 1행, 비정규화 1 + 그 회원의 예약 수)이 원자료의 `check`(U1 1 / 10,001, U2 1 / 11)와 같고, 모형에서도 같은 규칙으로 센다.
6. 장면 2의 Q1·Q2 결과가 세 판에서 같고, 테이블로 다시 간 행이 비정규화 판에만 있으며, 계획 문구가 원자료 `EXPLAIN FORMAT=TREE`(Q1 커버링 여부, Q2 테이블 스캔·커버링 인덱스 스캔)와 같다.
7. 장면 3의 A 락(res_fk IX, members·cars IS, members·cars PRIMARY 1 S,REC_NOT_GAP)과 B의 대기(members PRIMARY 1 X,REC_NOT_GAP WAITING)가 원자료 `data_locks`와 같고, 외래 키 없음의 A 락(res_nofk IX)도 같다.
8. "실험에서 잰 값" 칸의 시간(③ 16개 조건의 중앙값·최솟값·최댓값, ④ P2 초와 초당 행, 약 14%, P3 3.018초·0.00146초)이 원자료에서 다시 계산한 값과 같다.

브라우저에서는 장면 셋의 모든 구성(24개)의 모든 단계를 데스크톱 폭(1024px)과 휴대폰 폭(375px)에서 넘겨 보고, 콘솔 오류가 없고 페이지와 표가 옆으로 밀리지 않는 것을 확인했다(2026-11-23). 이 점검에서 휴대폰 폭의 락 목록이 `GRANTED`·`WAITING`을 낱말 중간에서 끊는 것을 고쳤고, 칼럼 이름은 밑줄 뒤에서 줄을 바꾸게 했다.
