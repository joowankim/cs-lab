# Python 실행 구조 관계도

01 동시성 모델 비교 실험을 복습하는 설명용 UI다. 프로세스, 인터프리터, OS 스레드, 논리 CPU, GIL, 이벤트 루프, Task, 공유 객체, Lock, Semaphore를 한 관계도에 놓고, 구성과 단계에 따라 실행·대기·보유 상태를 함께 보여 준다.

관계도 위에서 CPU, GIL, Lock, Semaphore 내부 카운터, 루프의 실행 차례가 조각으로 움직인다. 조각은 그 단계에 그것을 가진 요소에 붙고, 가진 쪽이 없으면 원래 자리로 돌아간다. 공유 카운터 값 읽기와 쓰기, GIL 해제 요청, Task 생성은 한 요소에서 다른 요소로 날아가는 조각으로 보인다.

이 화면의 단계는 설명용 모형이 만든 순서다. 실측값은 화면에서 `실측 기록` 표시가 붙은 곳에만 있고, 모두 [실험 README](../../experiments/01-concurrency-models/README.md)의 결과에서 옮겼다.

## 실행 애니메이션 (viz.html)

`viz.html`은 같은 모형을 알고리즘 시각화 도구처럼 보여 주는 화면이다. 한 화면에 네 칸을 두고 모두 같은 단계를 가리킨다.

- 실행 그래프: CPU, 프로세스, 인터프리터, GIL, 스레드, 이벤트 루프, Task, Semaphore, counter, Lock을 노드로 그린다. 실행·보유·대기·소속 관계를 간선으로 그린다. CPU·GIL·Lock·Semaphore 내부 카운터·루프의 실행 차례는 조각으로 움직이고, 값 읽기·쓰기·해제 요청·Task 생성·반납 후 깨움·타이머 만료는 노드 사이를 오가는 조각으로 보인다. Semaphore 노드에는 단계가 끝난 뒤의 내부 카운터와 얻기 대기 수를 적는다.
- 코드: 장면의 코드를 띄우고, 스레드나 Task가 지금 실행하는 줄과 멈춘 줄에 이름표를 붙인다.
- 공유 상태: CPU 배정, GIL 보유자와 대기열, 작업 진행, counter와 지역 변수, Lock, 준비된 Task, 타이머, Semaphore를 얻은 Task와 얻기 대기, B의 재개 기록을 칸으로 보이고 이번 단계에 바뀐 칸을 강조한다.
- 로그: 지금 단계까지의 이벤트.

코드 패널에 대해:

- 스레드 장면과 카운터 장면, asyncio 장면의 코드는 실험 코드에서 옮겼다. 쓰기만 Lock은 실험에서 실행하지 않은 설명용 변형이다.
- 카운터 장면의 "읽기부터 쓰기까지"는 `increment_unlocked`의 본문을 `with lock:` 안에 펼쳐 보인다. 실험 코드는 `with lock:` 안에서 `increment_unlocked`를 부른다. `board.html`은 실험 코드대로 보인다.
- 네이티브 장면의 코드는 hashlib 문서를 바탕으로 만든 설명용 예다. 실험 코드에 없고 측정하지 않았다.
- 루프 장면의 heartbeat와 main은 실험 흐름을 줄인 설명용 코드다.
- Python 계산 장면에서 count_primes 안의 강조 줄이 단계마다 바뀌는 것은 루프를 도는 모습을 보이려는 것이다. 실제 반복 횟수와 맞지 않는다.

조작: ⏮ ◀ ▶ ▶▏ ⏭, 속도 막대(5단계), 단계 막대 끌기, 키보드 `←` `→` `Space` `Home` `End` `Esc`. 노드를 누르거나 Tab으로 옮겨 Enter를 누르면 개념과 지금 연결이 나온다.

## 정돈한 관계도 시험판 (board.html)

`board.html`은 위에 전체 지도를 두고, 아래에는 고른 장면에 필요한 부분만 그리는 시험판이다. 장면은 공유 카운터와 Lock, 루프 지연, Task와 Semaphore 셋이다. 장면마다 관계도 아래에 모든 단계를 한눈에 보는 띠를 붙였다. 모든 장면의 단계 기록은 다른 화면과 같은 `model.js`에서 나온다. 연결선(CPU에서 스레드, 스레드에서 counter, 루프 스레드에서 실행 자리)은 모두 두 끝에서 세로로 나가고 들어오는 곡선으로 그린다. 두 끝이 같은 세로줄에 있으면 곧은 선이 된다.

그림 요소마다 뜻은 하나다. 테두리 상자는 무엇이 무엇 안에 있는지(프로세스, 인터프리터, 스레드, 이벤트 루프, Semaphore), 옅은 칸은 Task가 머무는 곳, 모양은 종류(CPU 칩, 스레드 원, Task 알약, 객체 상자), 채움과 점선은 실행 상태를 나타낸다. 5판까지는 스레드 줄과 공유 객체 줄에도 옅은 칸을 깔아서, Task가 머무는 칸과 종류로 묶은 칸이 같은 모양이었다. 6판에서 스레드는 테두리 상자로 바꾸고 공유 객체 칸은 없앴다.

### 전체 지도와 장면 고르기

- 전체 지도는 움직이지 않는 작은 그림이다. 논리 CPU, 프로세스, 인터프리터, GIL, OS 스레드, 이벤트 루프와 Task, counter, Lock, Semaphore를 한 번에 놓고, 고른 장면에 나오는 부분만 진하게 그린다. 공유 카운터는 CPU, GIL, 스레드, counter, Lock을 진하게 그린다. 루프 지연은 CPU, GIL, 스레드 하나, 이벤트 루프, Task를 진하게 그리고, Task와 Semaphore는 여기에 Semaphore를 더한다.
- 지도는 요소의 종류만 보인다. 그 구성의 개수(논리 CPU, 프로세스, 인터프리터, GIL, OS 스레드, counter와 Lock 또는 이벤트 루프, 작업, Task, Semaphore 상한)는 지도 옆 "이 장면의 개수"에 적는다.
- 장면 버튼 셋으로 장면을 바꾼다. 주소 끝에 `#counter`, `#loop`, `#sem`을 붙이면 그 장면으로 열리고, 붙이지 않으면 그 브라우저에서 마지막에 본 장면이 열린다. 다른 장면에 다녀와도 장면마다 고른 구성은 남고, 단계는 0으로 돌아간다. "내 예상" 칸의 글은 장면마다 따로 그 브라우저에 저장된다.

### 공유 카운터와 Lock

- 모양: 논리 CPU는 사각 칩, 프로세스와 인터프리터는 상자, OS 스레드는 원이고 스레드마다 테두리 상자 하나에 담는다. GIL은 인터프리터마다 꼬리표 하나, counter는 값 상자, Lock은 쥔 스레드와 기다리는 스레드를 적는 상자다. 프로세스는 옅은 바탕이고, 인터프리터와 스레드 상자는 흰 바탕이다. 이 장면에는 Task가 없어서 옅은 칸도 없다.
- 인터프리터 안에는 스레드 상자가 같은 너비로 나란히 놓인다. 스레드 상자에는 원과 그 스레드만 쓰는 것(쥔 GIL 꼬리표, 기다리는 이유, 지역 변수)이 들어가고, 모든 스레드가 함께 쓰는 counter와 Lock은 그 아래 상자 밖에 놓인다. 그래서 무엇을 함께 쓰는지가 위치로 보인다. counter는 가운데에 두고, Lock 상자가 인터프리터 안쪽을 넘으면 둘을 함께 왼쪽으로 민다. 상자 이름 "스레드"는 원 왼쪽에 들어갈 만큼 상자가 넓을 때만 적는다(1440px 화면에서는 스레드 셋까지).
- CPU가 실행하는 스레드는 칩 아래에서 원 위로 곡선을 긋는다. GIL 꼬리표는 쥔 스레드의 상자 안 원 아래에 붙고, 비어 있으면 인터프리터 왼쪽 위, 스레드 상자 위의 GIL 자리(점선 테두리)로 돌아간다. 쥔 스레드가 있는 동안 GIL 자리는 비어 있다. 해제 요청이 있으면 꼬리표 옆에 "요청"이 붙는다. GIL 끔이면 꼬리표와 GIL 자리가 없고, 스레드 상자가 인터프리터 위쪽에 바로 붙는다.
- 스레드 상태는 넷이다: 실행 중(채운 원), 차례 기다림(빈 원), 이벤트 기다림(점선 원), 끝(흐린 원). 기다릴 때는 원 아래에 이유를 한 낱말로 적는다: GIL 차례, CPU 차례, 시작 전, Lock 대기, sleep 대기.
- 스레드 상자마다 아래 가장자리에서 counter로 가는 곡선은 모든 스레드가 같은 객체를 쓴다는 뜻이다. 곡선이 납작해지지 않도록 스레드 상자와 counter 사이를 조금 띄웠다. 그 단계에 읽으면 스레드 쪽으로, 쓰면 counter 쪽으로 화살촉을 단다. 다른 스레드의 증가를 덮어쓴 쓰기는 주황색이다.
- 스레드 상자 안 원 아래 `previous = 0`은 그 스레드의 지역 변수다. 상자가 좁으면 `previous=0`으로 줄이거나 두 줄로 적는다. 함수가 끝난 스레드에는 적지 않는다.
- 설명 한 문장: 그 단계의 이벤트 가운데 하나를 덮어쓰기, 쓰기, 읽기, Lock, GIL 순으로 고른다. 나머지 이벤트는 "이 단계의 다른 일"에 접어 둔다. 마지막 단계에는 최종값과 기대값을 적는다.
- 코드: 줄 번호 왼쪽에 스레드 이름표를 붙인다. 채운 이름표는 그 줄을 실행 중, 빈 이름표는 그 줄 앞에서 기다리는 중이다. "읽기부터 쓰기까지"의 마지막 주석 줄과 "쓰기만"의 변형 코드는 설명을 위해 덧붙였다고 화면에 적었다.
- 단계 띠: 열은 단계, 줄은 스레드와 counter 값이다. 칸 글자는 그 단계에 실행한 연산이다(읽, 쓰, 0, 잠, 풀). 칸이나 단계 번호를 누르면 그 단계로 간다.
- 실행 여부(원 채움, CPU 선)는 그 단계 동안의 상태이고, 값과 자원(counter, previous, Lock, GIL)은 그 단계가 끝난 뒤의 상태다.

### 루프 지연, Task와 Semaphore

- 두 장면은 프로세스 하나, 인터프리터 하나, OS 스레드 하나(루프 스레드)만 그린다. 스레드 원 아래에서 나온 곡선이 이벤트 루프 상자의 실행 자리에 닿는다. 스레드 상태와 CPU 선은 공유 카운터와 같은 방식으로 그리고, 루프 스레드도 테두리 상자 하나에 담는다. 이벤트 루프는 Task들이 함께 쓰는 객체라서 스레드 상자 밖에 두고, 스레드가 루프를 돌린다는 것은 원에서 실행 자리로 가는 곡선으로 보인다. GIL 꼬리표는 쥔 동안 상자 안 원 왼쪽에 붙고, 비어 있으면 스레드 상자 위의 GIL 자리로 돌아간다. 루프 스레드가 기다리는 이유(시작 전, sleep 대기, 타이머까지 대기)는 원 오른쪽에 적는다. 좁은 화면에서는 이 글자를 11px로 적어 상자 안에 넣는다.
- Task는 알약 모양이다. 옅은 칸은 Task가 머무는 곳에만 쓴다: Task가 머무는 줄마다 옅은 바탕의 칸을 깔고 줄 이름을 칸 안에 적었다. 알약은 그 단계가 끝난 뒤 Task가 있는 칸에 놓이고, 알약 모양도 그 칸의 상태를 따른다: 실행 중 칸이면 채운 알약, 준비 큐면 빈 알약, 타이머·gather 대기·얻기 대기 칸이면 점선 알약, 끝 칸이면 흐린 알약이다. 루프 스레드가 `time.sleep()`으로 멈춘 동안 실행 중 칸에 남은 Task는 실행하지 못하므로 점선이다. 만료 단계가 지났는데 아직 실행하지 못한 Task는 주황으로 칠한다.
- 실행 중 칸에는 알약 하나 크기의 점선 자리(실행 자리)가 있고, 루프 스레드에서 내려온 곡선이 이 자리 위 가운데에 닿는다. 루프는 한 번에 Task 하나만 실행하므로 이 자리에는 알약 하나만 앉는다.
- 이벤트 루프 상자 안에는 루프가 직접 가진 칸만 둔다: 실행 중(아직 루프에 제어를 돌려주지 않은 Task), 준비 큐, 타이머. 타이머 칸의 알약 아래에는 만료 단계를 적고, 지나면 "지남"을 붙인다. gather를 기다리는 main Task, Semaphore 상자(얻은 Task 네모, 얻기 대기 칸, 내부 카운터), 끝 칸은 루프 상자 밖에 둔다.
- 한 단계씩 앞으로 넘길 때, 그 단계에 실행하고 다른 칸으로 간 Task의 알약은 먼저 실행 자리로 옮겨 가 채운 알약이 되고, 0.28초 뒤 갈 칸으로 옮겨 가며 그 칸의 모양으로 바뀐다. 만료 단계 글자는 갈 칸에 닿을 때 적는다. 칸을 옮기는 알약은 다른 알약 위로 지나간다. 뒤로 넘기거나 여러 단계를 건너뛰거나 동작 줄이기를 켜면 실행 자리를 거치지 않고 바로 갈 칸에 놓인다.
- 실행 여부(스레드 원 채움, CPU 선, 코드 이름표, 단계 띠)는 그 단계 동안의 상태이고, 알약이 놓인 칸과 모양, 타이머, Semaphore를 얻은 Task와 내부 카운터는 그 단계가 끝난 뒤의 상태다. 그래서 그 단계에 실행하고 타이머 칸으로 간 Task는 알약이 점선이어도 코드 이름표와 띠 칸은 채워져 있다. 알약에 마우스를 올리면 나오는 이름에는 "이 단계에 실행함"을 붙인다.
- Semaphore를 얻은 Task는 Semaphore 상자 첫 줄에 모서리가 덜 둥근 네모로 적는다. 이 줄은 Task가 머무는 곳이 아니라 Semaphore의 상태라서 옅은 칸을 깔지 않는다. 네모는 상한(내부 카운터의 초깃값)만큼 있다. 빈 네모는 점선이고, 세마포어를 얻은 Task가 있으면 옅은 파랑으로 채우고 그 Task 이름을 굵지 않은 글자로 적어 알약과 구별한다. Task가 블록을 나가며 세마포어를 반납할 때 얻기를 기다리는 Task가 있으면 그 Task가 깨어나 세마포어를 얻는다. 깨어난 Task는 반납한 Task의 네모를 그대로 쓰고 준비 큐로 가며, 내부 카운터는 0에 머문다.
- Semaphore 용어는 파이썬 문서(asyncio 동기화 프리미티브)의 말을 쓴다: 내부 카운터(internal counter), 세마포어를 얻다(acquire), 반납하다(release). 문서에는 "자리"나 "slot"이라는 말이 없다. `acquire()`는 내부 카운터를 1 줄이고, 카운터가 0이면 `release()`를 기다린다. CPython 3.14.2의 `Lib/asyncio/locks.py`에서 `release()`는 카운터를 1 늘린 뒤 기다리던 첫 Task를 깨우면서 그 Task 몫으로 다시 1 줄인다. 그래서 반납하고 바로 넘겨주는 단계에서 카운터는 0에 머문다. 모형의 Task와 Semaphore 48개 구성 874개 단계에서 내부 카운터와 얻은 Task 수의 합은 늘 상한과 같다.
- 모형이 단계마다 남기는 상태에는 Task별 상태만 있고, 준비 큐의 순서, 끝난 순서, 얻은 Task 네모의 위치는 없다. 그래서 이 셋은 모형의 이벤트 기록(Task 만들기, 타이머 만료, 준비, 반납 후 깨움, 루프 실행, 세마포어 얻기와 반납, Task 끝)을 처음부터 차례로 다시 놓아 만든다. 타이머 줄과 얻기 대기 줄의 순서는 모형의 상태에서 바로 읽는다.
- 설명 한 문장은 그 단계의 이벤트 하나를 고른다. 이벤트가 없는 단계(루프 스레드가 `time.sleep()`으로 멈춘 동안 등)에는 스레드가 하는 일과 만료 단계가 지난 Task를 적는다. 마지막 단계에는 결과를 적는다. 루프 지연은 B의 두 재개 기록이 몇 단계 늦었는지, Task와 Semaphore는 작업 Task가 모두 끝났는지와 Semaphore 안에 동시에 있던 Task의 최대 수다.
- 코드: 줄 번호 왼쪽에 Task 이름표를 붙인다. 채운 이름표는 그 단계에 그 줄을 실행한 Task, 빈 이름표는 준비 큐에서 그 줄을 기다리는 Task, 점선 이름표는 이벤트를 기다리는 Task, 주황 이름표는 만료 단계가 지난 Task다. 한 줄에 셋 이상 몰리면 하나만 보이고 나머지 수를 "+n"으로 적는다. 그 단계에 실행한 Task를 앞에 둔다.
- 코드 출처: Task와 Semaphore의 코드는 실험 코드(`run_asyncio`, `run_async_job`)에서 옮겼고, 세마포어를 반납하는 지점을 보이려고 주석 한 줄을 덧붙였다. 루프 지연의 `heartbeat()`와 `main()`은 모형의 흐름을 보이려고 쓴 설명용 코드이고, A가 하는 일의 함수는 `loop_kernels.py`에서 옮겼다. 두 장면 모두 이 출처를 화면에 적었다.
- 단계 띠: 줄은 스레드와 Task다. Task 줄의 칸 글자는 그 단계에 실행한 일이다(생 Task 만들기, 타 타이머 등록, 기 재개 기록, 얻 세마포어 얻기, 반 세마포어 반납). 주황 칸은 만료 단계가 지났는데 아직 실행하지 못한 단계다. Task와 Semaphore는 마지막 줄에 Semaphore 안의 Task 수를 적는다.
- 루프 지연에서 B는 실험의 12번 대신 두 번만 재개한다. 단계 수는 설명용이다.

### 조작과 뺀 것

⏮ ◀ ▶ ▶▏ ⏭, 속도 3단계, 단계 막대, 키보드 `←` `→` `Space` `Home` `End`. 단계 띠의 칸이나 단계 번호를 누르면 그 단계로 간다. 장면마다 버튼 한 줄로 바꾸는 항목이 하나 있다: Lock 범위(없음, 쓰기만, 읽기부터 쓰기까지), A가 하는 일(A 없음, time.sleep, await sleep, CPU 계산), Semaphore 상한(1–4). "구성 더 바꾸기"에서 빌드와 GIL, 논리 CPU 수(1–4)를 바꾼다. 공유 카운터는 읽기와 쓰기 사이 `time.sleep(0)`과 스레드 수(2–4)를, Task와 Semaphore는 작업 수(1–6)를 더 바꾼다. 구성을 바꾸면 단계 0으로 돌아간다.

## 모형의 가정

- 한 단계는 이벤트 순서를 나누는 구간이다. 시간 길이, 속도 비율, 비용을 뜻하지 않는다.
- 작업 길이는 단계 수로 고정한다. Python 계산 4, 네이티브 계산 3, sleep 3, asyncio.sleep 3, 루프 안 대기 4, 루프 안 CPU 계산 5, B의 주기 2. 실측에서 가져온 값이 아니다.
- GIL 교대: 기다리는 스레드가 2단계(`SWITCH_WAIT`) 동안 교대가 없으면 drop 요청을 하고, 보유 스레드는 다음 확인 지점에서 놓는다. 실제로는 `sys.getswitchinterval()`(설정값 0.005초)과 eval breaker 확인 지점이 정한다. 2단계는 5ms를 뜻하지 않는다.
- GIL 대기열은 먼저 온 순서(FIFO)다. 실제 CPython에서 누가 다음에 GIL을 얻는지는 OS 스케줄링에 따라 달라진다.
- 한 단계 안에서 GIL을 먼저 정한 뒤 CPU를 배정한다. 그래서 GIL을 가진 스레드가 CPU를 기다리는 상태가 나올 수 있다.
- CPU 배정은 오래 쉬었던 스레드를 먼저, 직전 CPU를 다시 쓰는 방식이다. 실제 OS 스케줄러의 정책이 아니다.
- 프로세스 하나에 인터프리터 하나만 둔다. 서브인터프리터는 다루지 않는다.
- 작업은 작업자 스레드에 고정된 순서로 나눈다(작업자 w → 프로세스 w % P, 스레드 floor(w / P)). 실제 풀의 작업 분배와 같지 않다.
- threading.Lock은 기다린 순서대로 넘긴다. 실제 넘김 순서는 보장되지 않는다.
- 카운터의 읽기와 쓰기 사이 `time.sleep(0)`은 GIL을 놓는 지점으로 둔다. 실험의 `counter_kernels.py`와 같은 위치다.
- 루프 장면은 스레드 0을 루프 스레드로 쓰고 나머지 스레드는 쓰지 않는 것으로 흐리게 표시한다.

## 생략한 부분

- 풀, 프로세스, IPC의 생성 비용과 직렬화 비용. 실험에서 따로 측정하지 않았다.
- GIL 교대 시각과 교대 횟수. 실험 기록에 없다.
- 네이티브 코드의 GIL 해제는 실험에서 측정하지 않았다. 관련 코드의 hashlib 예는 문서에 나온 예로만 둔다.
- GIL 끔 빌드에서 루프 지연은 측정하지 않았다. 이 장면은 모형으로만 보여 준다.
- 싱글턴 실험(`singleton_kernels.py`)은 장면으로 만들지 않았다.
- 메모리 사용량, 캐시, 코어 이동 비용.
- 화면에 예상이나 답을 미리 채우지 않는다. 장면 안내의 질문에는 답을 적지 않았다.

GitHub Pages 경로 확인: `docs/`를 로컬 서버의 `/cs-lab/` 아래에 두고 같은 Chromium으로 24개 항목을 확인했다. 첫 화면(`docs/index.html`)은 320, 390, 768, 1440px과 밝은·어두운 테마에서 가로 넘침이 없고, 세 화면으로 가는 링크와 화면끼리 잇는 링크가 모두 열리며 `/cs-lab/` 밖으로 나가지 않는다. 근거 링크 50개는 모두 GitHub 저장소, CPython 소스, 파이썬 문서의 절대 주소다. 저장소를 가리키는 30개는 `main`의 파일 14개로 가고, 14개 모두 저장소에 있으며 GitHub에서 열린다. 실험 README 제목으로 가는 17개도 GitHub이 만드는 제목 주소와 맞는다. 화면 코드가 쓰는 근거 이름 46개는 모두 정의돼 있다. 저장소에 없는 `mental-models.md`를 가리키던 근거 하나는 화면에서 쓰지 않아 뺐다. 콘솔 오류와 실패한 요청이 없다. 같은 경로에서 정돈한 관계도 85개 항목과 두 화면의 Semaphore 용어 확인도 다시 통과했다.

`viz.html`과 같은 방법으로 센 값(공유 카운터, Lock 없음·스레드 2·CPU 4, 1440px 화면). board.html은 지금 화면에서 다시 셌고, 괄호 안은 전체 지도와 장면 버튼을 넣기 전 값이다. 곡선 연결선을 넣은 뒤로는 곡선의 색도 센다.

낱말 수는 지도를 넣으며 232개에서 287개로, 칸 이름 "공유 객체"를 넣으며 289개로, 6판에서 칸 이름 "스레드"와 "공유 객체"를 빼고 스레드 상자 이름 "스레드" 둘과 표시 뜻 "상자: 포함 관계", "OS 스레드"를 더해 293개로 늘었다. 절반 목표에는 여전히 못 미친다. 287개였을 때 그 가운데 전체 지도 칸이 46개(제목 8, 지도 글자 16, 개수 표 22), 장면 버튼이 7개, 단계 띠의 숫자와 칸 글자가 24개, 화면 낭독기용 문장이 12개다. "1-1이 CPU 1에서 실행"이 나오는 곳도 목표인 3곳보다 많은 5곳이다: 관계도의 CPU 선과 원 채움, 설명 문장, 코드 이름표, 단계 띠 칸.

공유 카운터의 색은 프로세스 바탕에 쓴 옅은 색 하나가 늘었다. 6판에서 공유 카운터의 옅은 칸을 없앴지만 프로세스 바탕이 같은 색이라 색 수는 4개 / 6개 그대로다. 루프 장면 둘의 기본 구성에서 모든 단계를 지나며 센 관계도 색은 칸을 넣기 전보다 루프 지연이 5개에서 6개(칸 바탕색), Task와 Semaphore가 3개에서 5개(칸 바탕색, 자리를 가진 자리 칸의 옅은 파랑)로 늘었고, 스레드 칸과 GIL 자리를 넣은 뒤에도, 6판에서 스레드 칸을 스레드 상자로 바꾼 뒤에도 같다.
