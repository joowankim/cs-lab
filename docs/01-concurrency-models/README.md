# 동시성 관계도

01 동시성 모델 비교 실험을 복습하는 설명용 화면이다. 페이지 하나에 전체 지도와 장면 여섯을 둔다. 장면마다 관계도, 코드, 모든 단계를 한눈에 보는 띠가 같은 단계를 가리키고, 관계도의 요소를 고르면 그 요소의 개념, 지금 상태, 근거가 설명 칸에 나온다.

화면의 단계는 설명용 모형(`model.js`)이 만든 순서다. 실측값은 "실험에서 잰 값" 칸과 `실측 기록` 표시가 붙은 근거에만 있고, 모두 [실험 README](../../experiments/01-concurrency-models/README.md)의 결과에서 옮겼다.

2026-10-24에 실행 애니메이션(`viz.html`)과 자세한 설명 화면(그때의 `index.html`)을 이 페이지에 합치고 두 화면을 지웠다. 두 화면에만 있던 장면 셋(Python 계산, 네이티브 계산, time.sleep() 대기)과 요소 설명을 이 페이지의 그림 규칙으로 다시 그렸다. 지금의 `index.html`은 관계도 시험판이던 `board.html`을 이어받았다.

## 그림 규칙

다음 실험의 복습 화면도 이 규칙으로 그린다.

- 개념 하나에 모양 하나를 쓴다. 논리 CPU는 사각 칩, OS 스레드는 원, GIL은 꼬리표, Task는 알약, counter와 Lock은 값 상자다. 같은 요소는 지도와 장면에서 같은 모양이다.
- 테두리 상자는 무엇이 무엇 안에 있는지만 뜻한다: 프로세스, 인터프리터, 스레드, 이벤트 루프, Semaphore. 옅은 칸은 Task가 머무는 곳에만 쓴다.
- 상태는 넷이다: 실행 중(채운 원), 차례 기다림(빈 원), 이벤트 기다림(점선 원), 끝(흐린 원). 기다릴 때만 원 곁에 이유를 한 낱말로 적는다: GIL 차례, CPU 차례, 시작 전, Lock 대기, sleep 대기, 타이머까지 대기. 맡은 작업이 없는 작업자는 넷과 따로, 상자째 흐리게 하고 원을 성긴 점선으로 그린다.
- 색은 세 갈래다. 강조(파랑)는 실행 중인 것과 쥔 자원, 경고(주황)는 덮어쓴 쓰기, 만료 단계가 지난 Task, GIL 해제 요청처럼 눈여겨볼 곳에 쓰고, 나머지는 회색이다. 어두운 테마도 같은 세 갈래다.
- 연결선은 두 끝에서 세로로 나가고 들어오는 곡선이다. CPU에서 스레드, 스레드에서 counter, 루프 스레드에서 실행 자리로 긋는다.
- 계속 도는 애니메이션은 없다. 한 단계씩 넘길 때 CPU 선의 끝, GIL 꼬리표, Task 알약이 0.28초 동안 옮겨 가고, counter 값이 바뀌면 한 번 커졌다 돌아온다. 여러 단계를 건너뛰거나 운영체제의 동작 줄이기 설정을 켜면 바로 바꾼다.
- 시점을 나눈다. 실행 여부(원 채움, CPU 선, 코드 이름표, 단계 띠 칸)는 그 단계 동안의 상태이고, 값과 자원(작업 진행, counter, previous, Lock, GIL, Task가 놓인 칸과 알약 모양, 타이머, Semaphore)은 그 단계가 끝난 뒤의 상태다.
- 단계는 이벤트의 순서이고 시간 길이가 아니다. 단계 수를 실측값과 견주지 않는다.
- 사람이 적을 예상이나 답을 미리 채우지 않는다. 질문에는 답을 적지 않고 "내 예상" 칸은 비워 둔다.
- 좁은 화면에서는 관계도와 지도를 보이는 폭에 맞춰 다시 배치해 글자 크기를 유지한다. 관계도에서 가장 작은 글자는 11px이다.

## 화면 구성

위에서부터 장면 버튼, 전체 지도와 "이 장면의 개수", 먼저 생각해 볼 질문과 "내 예상" 칸, 단계 이동 막대와 장면별 조절 버튼, 관계도가 이어진다. 1100px 이상 화면에서는 관계도 오른쪽에 설명 칸(요소를 골랐을 때)과 코드를 두고, 그 아래에 단계 띠를 둔다. 그보다 좁으면 관계도, 설명 칸, 단계 띠, 코드 순서로 한 줄에 놓는다. 맨 아래 접힌 칸에는 구성 더 바꾸기, 볼 것, 실험에서 잰 값, 근거와 복습 카드, 이 단계까지의 기록이 있다.

### 전체 지도와 장면 고르기

- 전체 지도는 움직이지 않는 작은 그림이다. 논리 CPU, 프로세스, 인터프리터, GIL, OS 스레드, 이벤트 루프와 Task, counter, Lock, Semaphore를 한 번에 놓고, 고른 장면에 나오는 부분만 진하게 그린다. 지도는 종류만 보이고, 그 구성의 개수는 지도 옆 "이 장면의 개수"에 적는다.
- 장면 버튼은 두 무리다. "스레드와 프로세스"에 Python 계산, 네이티브 계산, time.sleep() 대기, 공유 카운터와 Lock이 있고, "asyncio"에 루프 지연, Task와 Semaphore가 있다.
- 주소 끝에 `#py`, `#native`, `#tsleep`, `#counter`, `#loop`, `#sem`을 붙이면 그 장면으로 열린다. 붙이지 않으면 그 브라우저에서 마지막에 본 장면이, 처음이면 Python 계산이 열린다. 장면을 바꾸면 주소 끝도 바뀐다.
- 다른 장면에 다녀와도 장면마다 고른 구성은 남고, 단계는 0으로 돌아간다. "내 예상" 칸의 글은 장면마다 따로 그 브라우저에 저장된다.

| 장면 | 보는 것 |
|---|---|
| Python 계산 | 한 인터프리터의 스레드들이 순수 Python을 실행할 때 GIL 보유와 계산 도중 교대. GIL 끔, 프로세스 여러 개와 비교한다. |
| 네이티브 계산 | GIL을 놓는 네이티브 계산이 GIL 없이 CPU에서 도는 동안 다른 스레드가 Python을 실행하는 모습 |
| time.sleep() 대기 | time.sleep() 안의 스레드가 GIL과 CPU를 쓰지 않고 OS 대기를 겹치는 모습 |
| 공유 카운터와 Lock | 읽기와 쓰기 순서, Lock 범위(없음, 쓰기만, 읽기부터 쓰기까지)에 따른 증가 유실 |
| 루프 지연 | 루프 안 Task A가 하는 일(없음, time.sleep(), await asyncio.sleep(), CPU 계산)에 따라 B의 재개가 밀리는지 |
| Task와 Semaphore | 작업 수, Task 수, Semaphore 상한의 차이와 반납 후 깨움 |

### 작업자 장면: Python 계산, 네이티브 계산, time.sleep() 대기

- 실행 방식 버튼으로 작업자를 스레드로 둘지 프로세스로 둘지 고른다. 스레드 방식은 프로세스 하나에 작업자 스레드 n개(실험의 `run_threads`), 프로세스 방식은 프로세스 n개에 스레드 하나씩(`run_processes`)이다. "구성 더 바꾸기"에서 작업자 수를 1–4개로 바꾸고, 이 항목의 이름은 실행 방식에 따라 "스레드"나 "프로세스"로 바뀐다. 처음 구성은 스레드 방식 작업자 2개, 논리 CPU 2개, 작업 2개이고, time.sleep() 대기만 작업자 4개, CPU 2개, 작업 4개다.
- 프로세스마다 같은 너비의 칸을 나란히 두고, 칸마다 프로세스, 인터프리터, GIL 하나를 그린다. 논리 CPU 줄은 프로세스가 여럿이어도 하나다.
- CPU 선은 스레드 원 위에서 끝나고, 프로세스가 여럿이면 다른 프로세스 칸의 위쪽을 지나간다. 그래서 작업자 장면의 GIL 자리(빈 GIL이 돌아가는 점선 테두리)는 다른 장면과 달리 스레드 상자 아래, 인터프리터 왼쪽 아래에 둔다. 쥔 GIL은 쥔 스레드 상자 안 원 아래에 붙는다. GIL 끔이면 꼬리표와 자리가 없고 인터프리터 이름 옆에 "GIL 끔"을 적는다. 프로세스 칸이 좁아 들어가지 않으면 이름만 적고, 개수 표의 GIL 줄과 설명 칸에서 본다.
- 스레드 상자 아래 "작업 1 · 2/4"는 그 스레드가 단계 끝에 하고 있는 작업과, 그 작업을 몇 단위 했는지다. 단위는 설명용 단계 수다. 상자가 좁으면 "작업1 2/4"로 줄이거나 두 줄로 적는다. 맡은 작업을 다 마친 스레드에는 적지 않는다.
- 작업은 작업자에게 차례로 하나씩 나눈다. 작업이 작업자보다 적으면 남는 작업자는 흐리게 그리고 "작업 없음"이라 적는다. 개수 표에는 그 수를 작업자 줄(스레드 방식이면 OS 스레드, 프로세스 방식이면 프로세스)에 적고, 단계 띠에는 그 작업자의 줄을 두지 않는다.
- GIL 해제 요청은 쥔 스레드의 꼬리표 오른쪽에 주황 "요청"으로 적는다. 스레드 상자가 좁아 들어가지 않으면 원 아래 이유 자리에 "해제 요청"으로 적는다.
- 관계도 너비를 프로세스 수로 나눈 값이 140px보다 작으면 화면이 넓어도 좁은 화면의 간격과 11px 글자를 쓴다. 프로세스 칸이 100px보다 좁아지면 줄이지 않고 관계도 칸 안에서 옆으로 밀어 본다. 390px 화면의 프로세스 4개가 그렇다.
- 설명 한 문장은 그 단계의 이벤트 가운데 하나를 GIL 해제, 해제 요청, 네이티브 계산 끝, 대기에서 깨어남, GIL 얻기, 작업 끝 순으로 고른다. 이벤트가 없는 단계에는 실행한 스레드와 그 스레드가 한 일, OS 대기 중인 스레드를 적는다. 마지막 단계에는 결과를 적는다. Python 계산은 한 단계에 Python을 실행한 스레드의 최대 수, 네이티브 계산은 CPU를 쓴 스레드와 Python을 실행한 스레드의 최대 수, time.sleep() 대기는 함께 기다린 스레드의 최대 수다. 단계 수는 설명용이라 결과에 적지 않는다.
- 코드: 작업 함수 아래에 작업을 작업자에게 나눠 주는 실험 코드(`models.py`의 `run_threads`나 `run_processes`)를 붙인다. Python 계산의 `count_primes`와 time.sleep() 대기의 `run_job`은 `workloads.py`에서 옮겼다. 네이티브 계산의 `hash_job()`은 hashlib 문서의 예를 바탕으로 쓴 설명용 코드이고, 이 실험에서 실행하거나 측정하지 않았다. 이름표는 스레드가 하고 있는 연산의 줄에 붙는다. Python 계산은 안쪽 반복문 줄에 붙이고, 실제로 몇 번 도는지와는 상관없다.
- 단계 띠: 줄은 작업이 있는 스레드와 프로세스마다의 GIL이다. 스레드 줄의 칸 글자는 그 단계에 실행한 작업 번호이고, 네이티브 계산에서 GIL 없이 실행한 칸은 "네"다. GIL 줄에는 그 단계가 끝난 뒤 GIL을 쥔 스레드를 적는다(관계도의 꼬리표와 같은 시점). GIL 끔이면 GIL 줄이 없다.
- 작업을 나눠 주는 main 스레드와 프로세스 방식의 부모 프로세스는 그리지 않는다. 관계도 아래 설명에도 적었다.

### 공유 카운터와 Lock

- 인터프리터 안에는 스레드 상자가 같은 너비로 나란히 놓인다. 스레드 상자에는 원과 그 스레드만 쓰는 것(쥔 GIL 꼬리표, 기다리는 이유, 지역 변수)이 들어가고, 모든 스레드가 함께 쓰는 counter와 Lock은 그 아래 상자 밖에 놓인다. 그래서 무엇을 함께 쓰는지가 위치로 보인다. counter는 가운데에 두고, Lock 상자가 인터프리터 안쪽을 넘으면 둘을 함께 왼쪽으로 민다. 상자 이름 "스레드"는 원 왼쪽에 들어갈 만큼 상자가 넓을 때만 적는다.
- 빈 GIL은 인터프리터 왼쪽 위, 스레드 상자 위의 GIL 자리로 돌아간다. 해제 요청이 있으면 꼬리표 옆에 "요청"이 붙는다. GIL 끔이면 꼬리표와 GIL 자리가 없고, 스레드 상자가 인터프리터 위쪽에 바로 붙는다.
- 스레드 상자마다 아래 가장자리에서 counter로 가는 곡선은 모든 스레드가 같은 객체를 쓴다는 뜻이다. 그 단계에 읽으면 스레드 쪽으로, 쓰면 counter 쪽으로 화살촉을 단다. 다른 스레드의 증가를 덮어쓴 쓰기는 주황색이다.
- 스레드 상자 안 원 아래 `previous = 0`은 그 스레드의 지역 변수다. 상자가 좁으면 `previous=0`으로 줄이거나 두 줄로 적는다. 함수가 끝난 스레드에는 적지 않는다.
- 설명 한 문장은 그 단계의 이벤트 가운데 하나를 덮어쓰기, 쓰기, 읽기, Lock, GIL 순으로 고른다. 나머지 이벤트는 "이 단계의 다른 일"에 접어 둔다. 마지막 단계에는 최종값과 기대값을 적는다.
- 코드: 줄 번호 왼쪽에 스레드 이름표를 붙인다. 채운 이름표는 그 줄을 실행 중, 빈 이름표는 그 줄 앞에서 기다리는 중이다. "읽기부터 쓰기까지"는 실험 코드대로 `increment_candidate`가 `with lock:` 안에서 `increment_unlocked`를 부르고, Lock을 놓는 지점을 보이는 주석 한 줄만 덧붙였다. "쓰기만"의 `increment_write_only`는 실험에서 실행하지 않은 설명용 변형이다. 둘 다 코드 아래에 적었다.
- 단계 띠: 줄은 스레드와 counter 값이다. 칸 글자는 그 단계에 실행한 연산이다(읽, 쓰, 0, 잠, 풀).
- 이 장면은 프로세스 하나만 그린다. 프로세스마다 counter가 따로 생긴다는 것은 counter 설명의 주요 특성에 적었다.

### 루프 지연, Task와 Semaphore

- 두 장면은 프로세스 하나, 인터프리터 하나, OS 스레드 하나(루프 스레드)만 그린다. 실험도 루프를 스레드 하나에서 돌렸다. 스레드 원 아래에서 나온 곡선이 이벤트 루프 상자의 실행 자리에 닿는다. 이벤트 루프는 Task들이 함께 쓰는 객체라서 스레드 상자 밖에 둔다. GIL 꼬리표는 쥔 동안 상자 안 원 왼쪽에 붙고, 비어 있으면 스레드 상자 위의 GIL 자리로 돌아간다. 루프 스레드가 기다리는 이유(시작 전, sleep 대기, 타이머까지 대기)는 원 오른쪽에 적는다.
- Task는 알약이다. Task가 머무는 줄마다 옅은 칸을 깔고 줄 이름을 칸 안에 적었다. 알약은 그 단계가 끝난 뒤 Task가 있는 칸에 놓이고, 모양도 그 칸의 상태를 따른다. 실행 중 칸이면 채운 알약, 준비 큐면 빈 알약, 타이머·gather 대기·얻기 대기 칸이면 점선 알약, 끝 칸이면 흐린 알약이다. 루프 스레드가 `time.sleep()`으로 멈춘 동안 실행 중 칸에 남은 Task는 실행하지 못하므로 점선이다. 만료 단계가 지났는데 아직 실행하지 못한 Task는 주황으로 칠한다.
- 실행 중 칸에는 알약 하나 크기의 점선 자리(실행 자리)가 있다. 루프는 한 번에 Task 하나만 실행하므로 이 자리에는 알약 하나만 앉는다.
- 이벤트 루프 상자 안에는 루프가 직접 가진 칸만 둔다: 실행 중, 준비 큐, 타이머. 타이머 칸의 알약 아래에는 만료 단계를 적고, 지나면 "지남"을 붙인다. gather를 기다리는 main Task, Semaphore 상자(얻은 Task 네모, 얻기 대기 칸, 내부 카운터), 끝 칸은 루프 상자 밖에 둔다.
- 한 단계씩 앞으로 넘길 때, 그 단계에 실행하고 다른 칸으로 간 Task의 알약은 먼저 실행 자리로 옮겨 가 채운 알약이 되고, 0.28초 뒤 갈 칸으로 옮겨 간다. 뒤로 넘기거나 여러 단계를 건너뛰거나 동작 줄이기를 켜면 바로 갈 칸에 놓인다. 그래서 그 단계에 실행하고 타이머 칸으로 간 Task는 알약이 점선이어도 코드 이름표와 띠 칸은 채워져 있다.
- Semaphore를 얻은 Task는 Semaphore 상자 첫 줄에 모서리가 덜 둥근 네모로 적는다. 이 줄은 Task가 머무는 곳이 아니라 Semaphore의 상태라서 옅은 칸을 깔지 않는다. 네모는 상한(내부 카운터의 초깃값)만큼 있고, 반납한 Task의 네모는 깨어난 Task가 그대로 이어 쓴다.
- 용어는 파이썬 문서(asyncio 동기화 프리미티브)의 말을 쓴다: 내부 카운터(internal counter), 세마포어를 얻다(acquire), 반납하다(release). CPython 3.14.2의 `Lib/asyncio/locks.py`에서 `release()`는 카운터를 1 늘린 뒤 기다리던 첫 Task를 깨우면서 그 Task 몫으로 다시 1 줄인다. 그래서 반납하고 바로 넘겨주는 단계에서 카운터는 0에 머문다.
- 모형이 단계마다 남기는 상태에는 Task별 상태만 있고, 준비 큐의 순서, 끝난 순서, 얻은 Task 네모의 위치는 없다. 그래서 이 셋은 모형의 이벤트 기록(Task 만들기, 타이머 만료, 준비, 반납 후 깨움, 루프 실행, 세마포어 얻기와 반납, Task 끝)을 처음부터 차례로 다시 놓아 만든다.
- 설명 한 문장은 그 단계의 이벤트 하나를 고른다. 이벤트가 없는 단계에는 스레드가 하는 일과 만료 단계가 지난 Task를 적는다. 마지막 단계에는 결과를 적는다. 루프 지연은 B의 두 재개 기록이 몇 단계 늦었는지, Task와 Semaphore는 작업 Task가 모두 끝났는지와 Semaphore 안에 동시에 있던 Task의 최대 수다.
- 코드: 줄 번호 왼쪽에 Task 이름표를 붙인다. 채운 이름표는 그 단계에 그 줄을 실행한 Task, 빈 이름표는 준비 큐에서 기다리는 Task, 점선 이름표는 이벤트를 기다리는 Task, 주황 이름표는 만료 단계가 지난 Task다. Task와 Semaphore의 코드는 실험 코드(`run_asyncio`, `run_async_job`)에서 옮겼고, 세마포어를 반납하는 지점을 보이려고 주석 한 줄을 덧붙였다. 루프 지연의 `heartbeat()`와 `main()`은 모형의 흐름을 보이려고 쓴 설명용 코드이고, A가 하는 일의 함수는 `loop_kernels.py`에서 옮겼다.
- 단계 띠: 줄은 스레드와 Task다. Task 줄의 칸 글자는 그 단계에 실행한 일이다(생 Task 만들기, 타 타이머 등록, 기 재개 기록, 얻 세마포어 얻기, 반 세마포어 반납). 주황 칸은 만료 단계가 지났는데 아직 실행하지 못한 단계다. Task와 Semaphore는 마지막 줄에 Semaphore 안의 Task 수를 적는다.
- 루프 지연에서 B는 실험의 12번 대신 두 번만 재개한다.

공유 카운터를 뺀 장면의 코드에서는 한 줄에 이름표가 셋 이상 몰리면 하나만 보이고 나머지 수를 "+n"으로 적는다. 그 단계에 실행한 주체를 앞에 둔다.

## 요소 설명

- 관계도의 요소를 누르거나 Tab으로 옮겨 Enter나 Space를 누르면 설명 칸이 열린다. 고를 수 있는 요소는 논리 CPU, 프로세스, 인터프리터, GIL(꼬리표와 GIL 자리), OS 스레드(원과 스레드 상자), counter, Lock, 이벤트 루프, Semaphore, Task다.
- 설명 칸에는 요소의 종류와 이름, 개념 한 문장, "지금 · 단계 k", 주요 특성, 접힌 "근거와 복습 카드"가 있다. 개념, 주요 특성, 근거, 복습 카드는 요소마다 정해져 있고(`content.js`의 `ELEMENTS`), "지금"만 단계마다 바뀐다. "이 단계 동안"은 그 단계에 일어난 실행과 대기이고, "단계 끝"은 그 단계를 마친 뒤의 값이다.
- 맡은 작업이 없는 작업자와, Lock 범위가 "없음"일 때의 Lock을 고르면 설명 맨 위에 쓰지 않는 이유가 나온다. 작업이 없는 스레드에는 ThreadPoolExecutor가 그 스레드를 만들지 않을 수 있다는 것과 그 근거를 적는다. 작업이 없는 프로세스에는 ProcessPoolExecutor가 그 프로세스를 만드는지 이 실험에서 확인하지 않았다고 적는다.
- 단계를 옮겨도 설명 칸은 열린 채로 "지금"만 바뀌고, 펼친 근거 칸도 닫히지 않는다. 구성을 바꿔 고른 요소가 없어지거나 장면을 바꾸면 설명 칸을 닫는다. `Esc`나 닫기 단추로 닫으면 초점을 고른 요소에 둔다.
- 고른 요소는 테두리를 진하게 그린다. 근거 링크는 새 탭으로 연다.

## 조작

- 단계: ⏮ 처음, ◀ 이전, ▶ 재생과 멈춤, ▶▏ 다음, ⏭ 끝, 속도(느리게, 보통, 빠르게), 단계 막대. 단계 띠의 칸이나 단계 번호를 누르면 그 단계로 간다.
- 키보드: `→` 다음, `←` 이전, `Home` 처음, `End` 끝, `Space` 재생과 멈춤, `Esc` 설명 칸 닫기. 관계도의 요소는 `Tab`으로 옮겨 가고 `Enter`나 `Space`로 고른다.
- 장면마다 버튼 한 줄로 바꾸는 항목이 하나 있다: 실행 방식(작업자 장면), Lock 범위(공유 카운터), A가 하는 일(루프 지연), Semaphore 상한 1–4(Task와 Semaphore).
- "구성 더 바꾸기"에서 빌드와 GIL(일반 빌드 GIL 켬, free-threaded GIL 켬, free-threaded GIL 끔)과 논리 CPU 수(1–4)를 바꾼다. 작업자 장면은 작업자 수(1–4)와 작업 수(1–8)를, 공유 카운터는 스레드 수(2–4)와 읽기와 쓰기 사이 `time.sleep(0)`을, Task와 Semaphore는 작업 수(1–6)를 더 바꾼다. 구성을 바꾸면 단계 0으로 돌아간다.

## 모형의 가정

- 한 단계는 이벤트 순서를 나누는 구간이다. 시간 길이, 속도 비율, 비용을 뜻하지 않는다.
- 작업 길이는 단계 수로 고정한다. Python 계산 4, 네이티브 계산 작업은 Python 1, 네이티브 구간 3, Python 1, time.sleep() 작업은 호출 1, 대기 5, 반환 1, await asyncio.sleep 3, 루프 안 대기 4, 루프 안 CPU 계산 5, B의 주기 2다. 실측에서 가져온 값이 아니다.
- time.sleep() 대기는 3단계였다가 이번에 5단계로 늘렸다. GIL을 켜면 스레드들이 GIL을 차례로 얻어 한 단계에 하나씩 대기에 들어가는데, 3단계로는 작업자 4개의 대기가 모두 겹치는 단계가 없었다(가장 많을 때 3개). 장면의 질문과 볼 것은 네 대기가 겹치는 경우를 다루므로 대기를 Python 구간(1단계)보다 충분히 길게 했다. 5단계면 처음 구성(작업자 4, CPU 2, 작업 4, GIL 켬)에서 네 스레드가 모두 대기인 단계가 두 번 나온다. 실험에서도 time.sleep(0.1) 작업 40개를 스레드 4개로 1.036234초에 끝내, 순차 실행 4.145660초의 약 1/4이었다.
- GIL 교대: 기다리는 스레드가 2단계(`SWITCH_WAIT`) 동안 교대를 보지 못하면 해제 요청을 하고, 보유 스레드는 다음 확인 지점에서 놓는다. 실제로는 `sys.getswitchinterval()`(설정값 0.005초)과 eval breaker 확인 지점이 정한다. 2단계는 5ms를 뜻하지 않는다.
- GIL 대기열은 먼저 온 순서다. 실제 CPython에서 누가 다음에 GIL을 얻는지는 OS 스케줄링에 따라 달라진다.
- 한 단계 안에서 GIL을 먼저 정한 뒤 CPU를 배정한다. 그래서 GIL을 가진 스레드가 CPU를 기다리는 상태가 나올 수 있다.
- CPU 배정은 가장 오래 실행하지 않은 스레드를 먼저 고르고, 그 스레드가 직전에 쓴 CPU가 비어 있으면 그 CPU를 다시 준다. 실제 OS 스케줄러의 정책이 아니다.
- 프로세스 하나에 인터프리터 하나만 둔다. 서브인터프리터는 다루지 않는다.
- 작업 j는 작업자 j mod n(n은 작업자 수)이 맡는다. 실제 풀의 작업 분배와 같지 않다.
- threading.Lock은 기다린 순서대로 넘긴다. 실제 넘김 순서는 보장되지 않는다.
- 카운터의 읽기와 쓰기 사이 `time.sleep(0)`은 GIL을 놓는 지점으로 둔다. 실험의 `counter_kernels.py`와 같은 위치다.

## 생략한 부분

- 작업을 나눠 주는 main 스레드, 프로세스 방식의 부모 프로세스, 풀의 내부 스레드, 작업 전달과 결과 수집은 그리지 않는다. 풀, 프로세스, IPC의 생성 비용과 직렬화 비용도 모형에 없다. 실험에서 따로 측정하지 않았다.
- 실제 ProcessPoolExecutor가 작업이 없는 작업자 프로세스를 만드는지는 이 실험에서 확인하지 않았다. 화면은 그 작업자를 흐리게 그릴 뿐이다.
- GIL 교대 시각과 교대 횟수. 실험 기록에 없다.
- 네이티브 코드의 GIL 해제는 실험에서 측정하지 않았다. hashlib 예는 문서에 나온 조건으로만 둔다.
- GIL 끔 빌드에서 루프 지연은 측정하지 않았다. 이 장면은 모형으로만 보여 준다.
- OS 스케줄러는 따로 그리지 않고 CPU 요소의 설명에 넣었다.
- 공유 카운터에서 프로세스를 여럿 두어 프로세스마다 counter가 따로 생기는 모습은 그리지 않는다.
- 예전 두 화면에 있던 날아가는 조각, 계속 깜빡이거나 흐르는 표시, 공유 상태 표, 보기 전환, 비교 구성 목록은 옮기지 않았다. 이벤트 기록은 접어 둔 "이 단계까지의 기록"에 있다.
- 싱글턴 실험(`singleton_kernels.py`)은 장면으로 만들지 않았다.
- 메모리 사용량, 캐시, 코어 이동 비용.
- 화면의 코드는 실험 코드에서 문서 문자열, 일부 주석과 타입 표기, 그 장면에서 실행하지 않는 줄을 빼고 옮겼다.

## 확인 결과

2026-10-24에 확인했다.

모형 테스트: `node --test model.test.cjs` 22개 통과. 3,168개 구성을 돌려 다음을 확인한다.

- Python을 실행하는 스레드 수는 CPU 수를 넘지 않고, GIL 켬이면 인터프리터마다 1을 넘지 않는다. 그 스레드가 GIL을 가진다.
- GIL 끔이면 한 인터프리터에서 여러 스레드가 Python을 함께 실행하지만 CPU 수를 넘지 않는다. 프로세스가 여럿이면 GIL을 켜도 프로세스끼리 함께 실행한다.
- GIL 교대는 계산 도중에 일어나고, 해제 요청과 실제 해제는 다른 단계에 있다.
- GIL을 가졌지만 CPU를 기다리는 스레드와, GIL 없이 CPU에서 네이티브 계산을 하는 스레드가 나온다.
- time.sleep() 중인 스레드는 GIL과 CPU를 쓰지 않는다. GIL을 켠 스레드 4개, CPU 1개, 작업 4개에서 네 스레드가 함께 대기하는 단계가 있다.
- 루프는 프로세스마다 스레드 하나에서만 돈다. Task A가 time.sleep()이나 중단 없는 계산이면 GIL 설정과 관계없이 B가 밀리고, await asyncio.sleep()이면 밀리지 않는다.
- 세마포어를 얻은 Task 수는 상한을 넘지 않고, 반납하면 기다리던 다음 Task가 얻는다. 내부 카운터가 0보다 크면 진입에서 멈추지 않는다.
- 카운터 결과: Lock 없음과 쓰기만 Lock은 증가가 유실되는 순서가 나오고, 읽기부터 쓰기까지 Lock은 기대값이다. Lock을 기다리는 스레드는 GIL을 쥐지 않는다. 프로세스마다 카운터가 따로 있다.
- 작업 수가 작업자보다 적으면 남는 작업자를 쓰지 않는 것으로 표시한다. 같은 구성은 언제나 같은 결과를 내고, 작업 진행률은 줄지 않으며 마지막 단계에서 전체와 같다.

이번에 `model.js`에서 바꾼 것은 둘이다. time.sleep() 대기 길이를 3단계에서 5단계로 늘렸고(위 "모형의 가정"), 테스트도 네 스레드가 함께 대기하는지 보도록 고쳤다. 지운 화면만 쓰던 `elements()`를 지우고 그 테스트도 지워 테스트가 23개에서 22개가 됐다.

브라우저 기능 확인: Playwright와 Chromium 153.0.8010.12로 148개 항목을 확인했다.

- 장면 고르기: 처음 열면 Python 계산이 열리고 장면 버튼은 두 무리다. 장면 주소로 열기, 마지막에 본 장면 열기, 장면마다 따로 남는 "내 예상"과 구성, 장면마다 지도의 진한 부분과 개수 표, 조절 버튼을 확인했다.
- 작업자 장면: 처음 구성의 모든 단계에서 채운 원과 CPU 선이 모형과 같고, GIL을 켠 인터프리터에서 Python을 실행하는 스레드는 하나다. 해제 요청 "요청"이 보이는 단계가 있다. 작업 4개면 스레드 1-1의 진행이 작업 1에서 작업 3으로 이어지고 끝나면 비운다. GIL 끔은 꼬리표와 자리가 없고 두 스레드가 함께 Python을 실행하며 띠에 GIL 줄이 없다. 프로세스 방식은 프로세스·인터프리터·GIL이 둘이고, 두 GIL을 각각 쥔 단계가 있으며, 코드는 `run_processes`, 띠에는 GIL 줄이 둘이다. 프로세스 4개·작업 2개면 작업 없는 작업자 둘이 흐리고 개수 표의 프로세스 줄에 "작업 없음 2"가 붙는다. 네이티브 계산에는 한 스레드가 GIL 없이 계산하는 동안 다른 스레드가 Python을 실행하는 단계가 있다. time.sleep() 대기는 GIL을 켜도 네 스레드가 모두 OS 대기인 단계가 있고(점선 원 넷, CPU 선 없음, GIL 비어 있음, 이름표는 `time.sleep` 줄), GIL을 꺼도 함께 기다린 스레드는 최대 4개로 같다.
- 공유 카운터, 루프 지연, Task와 Semaphore: 시험판에서 확인한 값을 다시 확인했다. Lock 없음, 쓰기만, 읽기부터 쓰기까지의 최종값은 1, 1, 2(기대값 2)이고 Lock 없음은 단계 6에서 덮어쓴다. 루프 지연(time.sleep, GIL 켬, CPU 2)은 단계 4~7에 스레드가 sleep 대기이고 B의 두 기록이 모두 4단계 늦으며, 띠에서 B 줄의 주황 칸은 단계 5~8이다. await sleep은 늦지 않고, CPU 계산·GIL 끔은 5단계 늦다. Task와 Semaphore(작업 4, 상한 2)는 단계 8에 작업1이 반납하자 작업3이 깨어나 같은 네모를 이어 쓰고 내부 카운터는 0에 머문다. 이벤트 기록으로 다시 만든 준비 큐, 끝 줄, 얻은 Task 네모는 루프 지연 8개 구성과 Task와 Semaphore 48개 구성의 모든 단계(976개)에서 모형의 Task 상태와 같다.
- 요소 설명: 처음에는 닫혀 있고, CPU 칩을 누르면 종류, 이름, 개념, 지금 상태, 주요 특성, 근거와 카드가 나온다. 단계를 넘기면 지금 상태만 바뀌고 펼친 근거 칸은 그대로다. Tab으로 옮긴 스레드에서 Enter, GIL 꼬리표에서 Space(재생은 시작하지 않는다), Esc와 닫기 단추, 상자의 빈 곳 누르기, 작업 없는 스레드와 프로세스의 이유, Lock 없음의 이유, counter·Task·이벤트 루프·Semaphore의 지금 상태를 확인했다.
