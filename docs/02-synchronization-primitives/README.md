# 동기화 관계도

02 동기화 도구 직접 쓰기 실험을 복습하는 설명용 화면이다. 페이지 하나에 전체 지도와 장면 여섯을 둔다. 장면마다 관계도, 코드, 모든 단계를 한눈에 보는 띠가 같은 단계를 가리키고, 관계도의 요소를 고르면 그 요소의 개념, 지금 상태, 근거가 설명 칸에 나온다.

화면의 단계는 설명용 모형(`model.js`)이 만든 순서다. 실측값은 "실험에서 잰 값" 칸과 `실측 기록` 표시가 붙은 근거에만 있고, 모두 [실험 README](../../experiments/02-synchronization-primitives/README.md)의 결과에서 옮겼다. 본 측정이 아니라 컨테이너에서 임시로 확인한 값은 그렇다고 적었다.

페이지의 틀과 조작은 [01 동시성 관계도](../01-concurrency-models/README.md)와 같다. 2026-10-27에 만들었다.

## 그림 규칙

[01 화면의 그림 규칙](../01-concurrency-models/README.md#그림-규칙)을 따른다. 아래는 이 화면에서 정하거나 더한 것이다. 다음 실험의 복습 화면도 동기화 도구를 그리면 이 규칙을 쓴다.

- 모양: OS 스레드는 원, GIL은 꼬리표다(01과 같다). 동기화 도구(Lock, RLock, Semaphore, BoundedSemaphore, 조건 변수, Event)와 스레드들이 함께 쓰는 자료(jobs, 계좌, ready.flag, 가짜 API)는 값 상자다. 값 상자 안의 작은 상자는 담는 관계다: 조건 변수 안의 RLock, Ready 안의 Event, 계좌 안의 락.
- 상자 안 글자에는 그 도구가 기억하는 것만 적는다. Lock은 잠금과 잠금 해제, RLock은 주인과 수준, 세마포어는 카운터, 조건 변수는 대기 목록, Event는 깃발이다. Lock과 세마포어는 누가 잡거나 얻었는지 기억하지 않는다. 스레드에서 도구로 가는 파란 선은 모형이 따로 적어 둔 값으로 그린다.
- 스레드 상태 넷(실행 중, 차례 기다림, 이벤트 기다림, 끝)과 그 모양은 01과 같다. 기다리는 이유는 시작 전, 실행 차례, GIL 차례, Lock 대기, Semaphore 대기, 통지 대기, Event 대기, API 대기, sleep 대기 가운데 하나다. GIL을 그리지 않는 장면은 "GIL 차례" 대신 "실행 차례"라 적고, 식사하는 철학자는 "Semaphore 대기" 대신 "웨이터 대기"라 적는다. 끝난 스레드에는 "끝"을 흐리게 적는다.
- 채운 원은 그 단계에 실행한 스레드 하나다. 그 스레드가 단계 끝에 기다리게 되어도 원은 채운 채로 두고, 무엇을 기다리는지는 단계 끝 상태인 회색 점선 연결선으로 보인다. 원은 다음 단계에 점선이 된다.
- 잡지 않은 예외로 끝난 스레드는 흐린 원 아래에 예외 이름(IndexError 등)을 주황으로 적는다. 이 글자는 흐리게 하지 않는다. 이중 release()처럼 handle()이 잡은 예외는 난 단계에만 주황으로 적고, 스레드는 다음 요청으로 간다.
- 연결선은 01과 같은 곡선으로, 스레드 상자 아래 가장자리에서 받는 상자 위 가장자리로 긋는다. 쥔 락과 얻은 세마포어는 파란 실선, 기다리는 도구는 회색 점선, 호출 중인 가짜 API는 회색 실선이다. 선은 그 단계가 끝난 뒤의 상태다. 받는 상자 위 가장자리에 스레드 순서대로 끝점을 정해 두어 단계마다 선 끝이 옮겨 다니지 않는다. 작은 상자로 가는 선은 작은 상자의 위 가장자리에서 끝나고, 바깥 상자 위에 그려 테두리를 지나는 것이 보인다.
- 식사하는 철학자의 둥근 식탁에서만 연결선을 상자 중심끼리 잇는 곧은 선으로 그리고 상자 아래에 둔다. 곡선으로 그리면 식탁 둘레에서 선이 다른 상자를 지나간다.
- 색은 01의 세 갈래다. 주황은 문제에만 쓴다: 동시 호출이 상한을 넘은 가짜 API, 카운터와 반납하지 않은 수의 합이 초깃값보다 큰 세마포어, 오류, 기다림의 고리(고리에 든 선과 락). 그 단계의 문제 이벤트가 가리키는 상자도 그 단계에 주황으로 그린다. 쥔 락과 얻은 스레드가 있는 세마포어, 그 단계에 값이 바뀐 상자(카운터, jobs, flag, 깃발, 잔액)는 파란 테두리다.
- GIL은 기다리는 방법과 이체에만 그린다. 두 장면은 GIL을 넘기는 때가 결과를 바꾼다. 꼬리표는 단계 끝에 GIL을 쥔 스레드 상자의 원 아래에 놓이고, 쥔 스레드가 없으면 관계도 왼쪽 위의 GIL 자리(점선 테두리)로 돌아간다. 다른 장면도 한 단계에 스레드 하나만 실행하지만, 스레드가 블록되는 줄까지 이어서 실행하므로 GIL을 그리지 않는다.
- 계속 도는 애니메이션은 없다. 한 단계씩 넘길 때 GIL 꼬리표가 0.28초 동안 옮겨 가고, 스레드 원과 상자 테두리의 색이 0.28초 동안 바뀐다. 여러 단계를 건너뛰거나 운영체제의 동작 줄이기 설정을 켜면 바로 바꾼다.
- 시점은 01과 같다. 실행 여부(원 채움, 코드 이름표와 옅은 파랑 줄, 단계 띠 칸)는 그 단계 동안의 상태이고, 값과 자원(잠금, 카운터, 대기 목록, jobs, flag, 깃발, 잔액, 연결선, GIL 꼬리표)은 그 단계가 끝난 뒤의 상태다.
- 단계는 이벤트의 순서이고 시간 길이가 아니다. 단계 수를 실측 시간과 견주지 않는다. 기다리는 방법의 결과 문장에만 단계 번호를 적는데, 같은 장면의 구성끼리 순서를 견주려는 것이다.
- 사람이 적을 예상이나 답을 미리 채우지 않는다. 질문에는 답을 적지 않고 "내 예상" 칸은 비워 둔다.
- 좁은 화면에서는 관계도를 보이는 폭에 맞춰 다시 배치해 글자 크기를 유지한다. 관계도에서 가장 작은 글자는 11px이다. 상자 너비와 줄 나눔은 화면의 글꼴로 글자 너비를 재서 정한다. 기다리는 이유나 맡은 일이 스레드 상자에 들어가지 않으면 마지막 빈칸에서 두 줄로 나누고, 단계마다 상자 높이가 바뀌지 않도록 모든 단계를 미리 본다. 선이 들어오는 상자는 늘 첫 줄에 두고, 한 줄에 들어가지 않으면 관계도를 줄이지 않고 관계도 칸 안에서 옆으로 밀어 본다.

## 화면 구성

위에서부터 장면 버튼, 전체 지도와 "이 장면의 개수", 먼저 생각해 볼 질문과 "내 예상" 칸, 단계 이동 막대와 장면별 조절 버튼, 관계도가 이어진다. 관계도 아래에는 설명 한 문장, 접힌 "이 단계의 다른 일", 표시 뜻, 장면별 그림 설명이 있다. 1100px 이상 화면에서는 관계도 오른쪽에 설명 칸(요소를 골랐을 때)과 코드를 두고, 그 아래에 단계 띠를 둔다. 그보다 좁으면 관계도, 설명 칸, 단계 띠, 코드 순서로 한 줄에 놓는다. 맨 아래 접힌 칸에는 구성 더 바꾸기, 볼 것, 실험에서 잰 값, 근거와 복습 카드, 이 단계까지의 기록이 있다.

### 전체 지도와 장면 고르기

- 전체 지도는 움직이지 않는 작은 그림이다. 프로세스 안에 인터프리터가 있고, 인터프리터 안에 GIL, OS 스레드, 동기화 도구(Lock, RLock, Semaphore, BoundedSemaphore, Condition, Event), 공유 자료(jobs, 계좌, ready.flag, 가짜 API)를 놓는다. 고른 구성에 나오는 부분만 진하게 그린다. 지도는 종류만 보이고, 그 구성의 개수는 지도 옆 "이 장면의 개수"에 적는다.
- 장면 버튼은 세 무리다. "락과 세마포어"에 이중 release(), "조건 변수와 기다리기"에 조건 변수 버퍼, 버퍼 크기 1, 기다리는 방법, "교착 상태"에 이체, 식사하는 철학자가 있다.
- 주소 끝에 `#release`, `#buffer`, `#onecond`, `#wait`, `#transfer`, `#phil`을 붙이면 그 장면으로 열린다. 붙이지 않으면 그 브라우저에서 마지막에 본 장면이, 처음이면 이중 release()가 열린다. 장면을 바꾸면 주소 끝도 바뀐다.
- 다른 장면에 다녀와도 장면마다 고른 구성은 남고, 단계는 0으로 돌아간다. "내 예상" 칸의 글은 장면마다 따로 그 브라우저에 저장된다.

### 한 줄 배치: 이중 release(), 조건 변수 버퍼, 버퍼 크기 1, 기다리는 방법, 이체

- 위에 스레드 상자를 같은 너비로 한 줄에 두고, 아래에 스레드들이 함께 쓰는 상자를 둔다. 스레드 상자에는 원과 그 스레드만의 것(쥔 GIL, 기다리는 이유, 맡은 일)이 들어간다. 그래서 무엇을 함께 쓰는지가 위치로 보인다.
- 맡은 일은 스레드 상자의 마지막 줄이다. 이중 release()는 맡은 요청("요청 2"), 버퍼는 꺼낸 작업이나 넣는 작업("작업 1", "업로드 2", "put(1)"), 기다리는 방법은 로더의 계산 진행("계산 2/4")과 sleep으로 쉬는 스레드가 깨는 단계("깨는 단계 13"), 이체는 방향과 몇 번째 이체인지("A→B 1/2 · 다시 1")다.
- 이중 release(): 상한 도구 상자 하나(이름은 고른 도구: Semaphore(2), BoundedSemaphore(2), Lock, RLock)와 가짜 API 상자를 둔다. 가짜 API 상자에는 상한, 동시 호출 수, 지금까지의 호출 수, 나중에 보낼 큐의 길이를 적는다. 좁은 화면에서는 호출 수와 큐를 두 줄로 나눠 상자를 좁힌다.
- 조건 변수 버퍼: 조건 변수 상자 안 왼쪽에 Condition()이 만든 RLock을 두고, 오른쪽에 대기 목록을 먼저 기다린 스레드부터 적는다. jobs는 칸 다섯 개다(실험의 CAPACITY = 5).
- 버퍼 크기 1: 같은 모양에 jobs 칸이 하나다. "조건 변수 둘"은 밖에서 만든 lock 상자 하나와 not_full, not_empty 상자 둘을 따로 그린다. 두 조건 변수가 lock 하나를 함께 쓰기 때문이다.
- 기다리는 방법: Ready 상자 안에 Event 상자를 두고, 그 아래에 `flag = False`를 적는다. pass와 sleep 구성은 Event로 기다리지 않으므로 Event 상자를 흐린 점선으로 그리고 "wait() 안 씀"을 붙인다. 이 두 구성의 모형에는 Event가 없지만, 실험의 Ready는 Event를 늘 만들고 set()에서 flag와 함께 올리므로 깃발은 flag를 따라 그린다.
- 이체: 계좌 상자 안에 그 계좌의 락 상자를 두고 그 아래에 잔액을 적는다. 두 계좌는 보내는 스레드 아래에 하나씩 둔다. t1(A→B)이 A.lock을 쥐고 B.lock을 기다리고 t2가 그 반대이면 두 선이 엇갈리는데, 이 모양이 서로 기다리는 모양이다. 자기 계좌 이체(A→A)는 스레드 하나와 계좌 하나다.
- 선이 들어오는 상자(jobs를 뺀 모든 상자)는 늘 첫 줄에 둔다. 좁은 화면의 크기로도 한 줄에 들어가지 않으면 관계도를 줄이지 않고 옆으로 밀어 본다. 선이 들어오지 않는 jobs는 첫 줄에 들어가지 않으면 다음 줄로 넘긴다. 그래서 선이 다른 상자를 지나가지 않는다.
- 스레드 상자는 58px보다 좁게 그리지 않는다. 그보다 좁아지면 관계도 칸 안에서 옆으로 밀어 본다. 320px 화면에서는 BoundedSemaphore 구성(상자 줄에 265px가 필요하다), 스레드가 다섯인 조건 변수 버퍼(작업자 4개)와 기다리는 방법(요청 처리 스레드 4개)이 그렇고, 360px 화면에서는 뒤의 둘이 그렇다. 390px 이상에서는 옆으로 밀지 않는다.
- 관계도 너비가 480px보다 좁으면 좁은 화면의 간격과 11px 글자를 쓴다.

### 둥근 식탁: 식사하는 철학자

- 철학자 0을 맨 위에 두고 시계 방향으로 72°씩 앉힌다. 포크 i는 철학자 i-1과 철학자 i 사이 안쪽에 둔다. 그래서 철학자 i의 양옆 포크가 포크 i와 포크 i+1이다(철학자 4는 포크 4와 포크 0). 웨이터 구성은 식탁 가운데에 웨이터 상자를 두고 카운터를 적는다.
- 포크 상자에는 이름만 적는다. 쥔 포크는 파란 테두리, 고리에 든 포크는 주황 테두리다. 누가 쥐었는지는 선과 설명 칸에서 본다.
- 철학자 상자의 맡은 일은 먹은 횟수("먹음 0/1")나 "먹는 중"이다.
- 식탁은 320px보다 좁게 그리지 않는다. 그보다 좁으면 철학자와 포크 상자가 겹친다. 그래서 관계도 칸이 이보다 좁은 360px 이하 화면에서는 옆으로 밀어 본다. 식탁 너비가 440px보다 좁으면 11px 글자를 쓴다.

### 설명 한 문장

- 설명 한 문장은 그 단계의 이벤트 가운데 하나를 고른다. 문제를 알리는 이벤트를 먼저 고르는데, 순서는 멈춤, 끝없는 다시 시도, 잡지 않은 예외, 요청의 오류, 남이 잡은 Lock 풀기, 남는 release(), 상한 초과, 자기가 쥔 Lock 다시 기다리기, 작업자가 줄어든 업로드다. 문제 이벤트가 없으면 실행한 스레드가 한 일을 고른다. 나머지 이벤트는 "이 단계의 다른 일"에 접어 두고, 문제 이벤트의 문장은 주황으로 적는다.
- 마지막 단계에는 결과를 덧붙인다. 이중 release()는 동시 호출의 최대 수와 상한, 오류가 난 요청, 끝난 뒤 카운터나 잠금 상태다. 조건 변수 버퍼는 업로드 1·2·3번째 뒤 남은 작업자, IndexError 수, 빈 jobs에서 깨어난 횟수다. 버퍼 크기 1은 처리한 작업과 빈 jobs에서 깨어난 횟수다. 기다리는 방법은 로더가 계산을 시작한 단계와 set()을 부른 단계, 그 사이 요청 처리 스레드가 실행한 단계 수, 마지막 요청 처리 스레드가 기다림을 빠져나온 단계다. 이체는 마친 이체, 다시 시도 수, 잔액이다. 식사하는 철학자는 먹은 횟수다.

### 코드

- 줄 번호 왼쪽에 스레드 이름표를 붙인다. 채운 이름표는 그 단계에 실행한 스레드로, 그 단계에 실행한 마지막 줄에 붙는다. 빈 이름표(실행 차례를 기다림)와 점선 이름표(락, 통지, sleep 같은 이벤트를 기다림)는 다음에 실행할 줄에 붙는다. 그 단계에 예외가 난 스레드의 이름표는 주황이다. 한 줄에 이름표가 셋 이상 몰리면 하나만 보이고 나머지 수를 "+n"으로 적는다. 그 단계에 실행한 스레드를 앞에 둔다. 끝난 스레드에는 이름표가 없다.
- 옅은 파랑 줄은 그 단계에 실행한 스레드가 실행한 줄이다.
- 코드는 실험 코드에서 문서 문자열, 일부 주석, 실행 틀의 기록 줄을 빼고 옮겼다. with 블록을 나가며 락을 놓는 지점을 보이려고 주석 한 줄을 덧붙인 곳이 있고, 코드 아래 설명에 그 줄 번호를 적었다.
- 실험에서 실행하지 않은 코드는 코드 아래 설명에 그렇다고 적었다. 버퍼 크기 1의 "조건 변수 둘"은 실험 README의 고친 모양(에이전트 작성)에서 CAPACITY만 1로 바꾼 설명용 코드다. 버퍼 크기 1의 마지막 두 줄 `put(1)`, `put(2)`도 P가 하는 일을 보이려고 썼다. 이체의 RLock 구성은 Account의 락 줄만 `threading.RLock()`으로 바꿨다. 식사하는 철학자의 생각 시간은 무작위 대신 구성에서 고른 고정 단계 수다.

### 단계 띠

- 줄은 스레드마다 하나와 장면별 값 줄이다. 스레드 줄의 칸 모양은 원과 같다: 채운 칸은 실행, 테두리 칸은 차례 기다림, 점선 칸은 이벤트 기다림, 흐린 칸은 끝이다. 그 단계에 예외가 난 칸은 주황이다.
- 칸 글자는 그 단계에 실행한 스레드가 한 동기화 연산이다: ! 오류, 풀 락 놓기나 세마포어 반납, 깨 notify()나 set(), 꺼 jobs에서 꺼내기, 넣 jobs에 넣기, 잡 락이나 세마포어 얻기, 호 API 호출, 이 잔액 옮기기, 먹 먹기 시작, 다 다시 시도. 여러 개면 이 순서에서 앞의 것을 적는다.
- 값 줄은 그 단계가 끝난 뒤의 값이다. 이중 release()는 동시 호출과 카운터(Lock, RLock이면 잠금 여부), 버퍼는 jobs의 작업 수와 남은 작업자(조건 변수 버퍼만), 기다리는 방법은 GIL과 flag, 이체는 GIL과 마친 이체 수, 식사하는 철학자는 먹기 시작한 횟수의 합이다. 값이 바뀐 칸은 진하게, 상한을 넘었거나 작업자가 줄어든 칸은 주황으로 적는다.

- 관계도의 요소를 누르거나 Tab으로 옮겨 Enter나 Space를 누르면 설명 칸이 열린다. 고를 수 있는 요소는 OS 스레드(원과 스레드 상자), GIL(꼬리표와 GIL 자리), Lock, RLock, Semaphore, BoundedSemaphore, 조건 변수, Event, ready.flag, 가짜 API, jobs, 계좌, 포크, 웨이터다.
- 설명 칸에는 요소의 종류와 이름, 개념 한 문장, "지금 · 단계 k", 주요 특성, 접힌 "근거와 복습 카드"가 있다. 개념, 주요 특성, 근거, 복습 카드는 요소마다 정해져 있고(`content.js`의 `ELEMENTS`), "지금"만 단계마다 바뀐다. "이 단계 동안"은 그 단계에 일어난 실행과 대기이고, "단계 끝"은 그 단계를 마친 뒤의 값이다.
- "지금"에는 그 요소가 단계 끝에 가진 것을 적는다. 스레드는 이 단계에 실행한 줄 번호, 다음에 실행할 줄, 기다리는 것, 쥔 것이다. Lock은 마지막으로 잡은 스레드(Lock이 기억하는 값이 아니라 모형이 따로 적은 값이라고 밝힌다), 기다리는 스레드, 깨웠지만 아직 실행하지 않은 스레드다. 세마포어는 카운터와 초깃값, 얻고 아직 반납하지 않은 스레드이고, 카운터와 반납하지 않은 수의 합이 초깃값보다 크면 그 사실을 적는다.
- 기다리는 방법의 pass·sleep 구성에서 Event를 고르면 설명 맨 위에 기다림에 쓰지 않는 이유가 나온다.
- 단계를 옮겨도 설명 칸은 열린 채로 "지금"만 바뀌고, 펼친 근거 칸도 닫히지 않는다. 구성을 바꿔도 고른 요소가 남아 있으면 새 구성으로 다시 채우고, 없어지거나 장면을 바꾸면 설명 칸을 닫는다. `Esc`나 닫기 단추로 닫으면 초점을 고른 요소에 둔다.
- 고른 요소는 테두리를 진하게 그린다. 근거 링크는 새 탭으로 연다.

## 모형의 가정

- 한 단계는 이벤트 순서를 나누는 구간이다. 시간 길이, 속도 비율, 비용을 뜻하지 않는다. 무작위를 쓰지 않으므로 같은 구성은 언제나 같은 단계 기록을 낸다.
- 한 단계에는 스레드 하나만 실행한다. 실험은 GIL을 켠 CPython 3.14.2라 파이썬 코드를 실행하는 스레드가 한 번에 하나였다. 실행할 스레드는 준비된 순서대로 고른다. 실제로 누가 먼저 실행되는지는 OS 스케줄러와 GIL 넘김이 정한다.
- 한 단계에 실행하는 줄은 장면마다 코드를 따라가기 좋게 나눴다. 블록되는 줄(락·세마포어·조건 변수·Event 대기, sleep, API 호출)에서는 늘 단계가 끝나고, 깨어나 다시 실행되는 단계에 그 줄에서 돌아와 다음 줄을 이어 실행한다.
- GIL 전환 간격: 실행 중인 스레드가 정한 단계 수만큼 이어서 실행하고 기다리는 스레드가 있으면 다음 단계에 GIL을 넘긴다. 기다리는 방법은 1단계, 이체는 7단계이고, 다른 장면은 넘기지 않는다(블록될 때까지 실행한다). 실제로는 `sys.getswitchinterval()`(실험 환경 0.005초)이 정하고, 이 단계 수는 0.005초를 뜻하지 않는다.
  - 기다리는 방법의 1단계는 실행할 수 있는 스레드가 한 단계씩 돌아가며 GIL을 쓰게 하려는 것이다.
  - 이체의 7단계는 메모리 캐시 확인에서 이체가 1번씩이면 끝나고, 2번부터는 t1이 첫 락만 쥔 때에 GIL이 넘어가 멈추도록 고른 값이다. 실험의 2번(스레드마다 1,000번, 멈춤 0회)과 3번(10만 번, 10회 중 9회 멈춤)의 차이를 작은 크기로 보이려는 것이고, 몇 번째 이체에서 멈추는지를 실험과 견주지 않는다.
- 깨우는 순서: 락, 세마포어, 조건 변수에서 기다리는 스레드는 먼저 기다린 스레드부터 깨운다. CPython 3.14.2의 `Condition.notify()`는 대기 목록 앞부터 깨우고, Semaphore와 BoundedSemaphore는 안에서 이 조건 변수를 쓴다. 파이썬 문서는 Lock을 기다리는 스레드 가운데 누가 먼저 진행하는지 정하지 않는다.
- 락 넘김: Lock과 RLock은 놓을 때 기다리던 첫 스레드를 깨운다. 그 스레드가 2단계(`FAIR`) 이상 기다렸으면 락을 바로 넘기고, 아니면 깨우기만 한다. 깨운 스레드가 실행되기 전에 다른 스레드가 먼저 잡으면 깨운 스레드는 대기 줄 끝으로 돌아가 다시 기다린다. 기다리기 시작한 단계는 그대로 둔다. CPython 3.14.2의 PyMutex가 1ms 넘게 기다린 스레드에 락을 넘기는 규칙(`Python/lock.c`의 `TIME_TO_BE_FAIR_NS`)을 단계로 옮겼다. 2단계는 1ms를 뜻하지 않는다.
- 세마포어: `release()`는 카운터를 1 늘리고 기다리던 첫 스레드를 깨운다. 깨운 스레드는 실행될 때 카운터를 줄인다. 그 전에 다른 스레드가 먼저 얻어 카운터가 0이 되면 깨운 스레드는 대기 목록 끝으로 가 다시 기다린다. CPython 3.14.2의 `Semaphore.acquire()`가 while로 카운터를 다시 확인하는 것과 같다. BoundedSemaphore는 `release()`가 카운터를 초깃값보다 크게 만들려 할 때만 ValueError를 낸다.
- 조건 변수: `wait()`는 대기 목록 끝에 서고 연관된 락을 놓는다. RLock이면 수준을 저장했다가 돌아올 때 되돌린다. `notify()`를 받은 스레드는 대기 목록에서 빠져 연관된 락을 기다리고, 락을 얻어 실행되는 단계에 `wait()`에서 돌아온다. 락을 기다리기 시작한 단계는 통지를 받은 단계로 친다.
- Event: 깃발과 블록된 스레드 목록만 둔다. `set()`은 깃발을 올리고 블록된 스레드를 모두 깨운다. CPython의 Event 안에 있는 `Condition(Lock())`은 다루지 않는다.
- 시간을 재는 대기(sleep, API 호출, DB 확인)는 정한 단계 수 뒤 그 단계 끝에 깨어나 실행 차례를 기다린다. 길이는 설명용으로 정했고 실측에서 가져오지 않았다: 가짜 API 호출 4, 썸네일 작업 2, 로더 계산 4, sleep 확인 간격 10, DB 확인 2, 내려놓고 다시의 쉬기 t1 1·t2 2(무작위 대신 스레드마다 고정), 첫 포크를 집고 쉬기 2, 먹기 2, 생각하기 1(모두 같게)이나 철학자 0~4가 1·5·2·6·3(서로 다르게).
- 실험의 `settle()`은 1ms씩 자며 작업자들이 모두 다시 기다리는지 확인한다. 모형은 단계 끝마다 그 조건을 확인하고, 그동안 업로드 스레드 P를 sleep 대기로 그린다. 실험에서 업로드와 `settle()`은 main 스레드가 했고, 화면은 이를 업로드 스레드 P로 그린다.
- 조건 변수 버퍼의 P와 버퍼 크기 1의 t1·t2는 단계 0 전에 첫 대기까지 실행해 둔다. 장면이 그 대기에서 시작하기 때문이다.
- 멈춤 판단: 실행할 스레드도, 깨어날 단계가 정해진 스레드도 없으면 멈춘 것으로 본다. 락을 기다리는 스레드에서 그 락을 잡은 스레드로 가는 기다림이 고리를 이루면 교착 상태, 고리가 없으면 깨워 줄 스레드가 없는 멈춤이다. 세마포어, 조건 변수, Event를 기다리는 것은 고리에 넣지 않는다. 자기 계좌 이체를 Lock과 내려놓고 다시로 하면 다시 시도를 끝없이 되풀이하므로 세 번째 다시 시도에서 멈춘다. 400단계 안에 끝나지 않으면 거기서 자르지만, 지금 구성 가운데 그런 것은 없다(가장 긴 기록이 57단계다). 실험은 10초 안에 끝나지 않으면 멈춘 것으로 봤다.
- 크기를 줄였다.
  - 이중 release(): 요청 40개, 작업자 8개, 상한 4, 5·15·25번째 호출 타임아웃을 요청 4개, 스레드 3개, 상한 2(Lock과 RLock은 1), 1번째 호출 타임아웃으로 줄였다. 요청은 일을 마친 스레드가 다음 번호를 맡는다.
  - 조건 변수 버퍼: 업로드 3번까지만 그리고, 그 뒤 작업 20개를 처리하는 시간 측정 구간은 그리지 않는다.
  - 기다리는 방법: 기다리는 스레드 4·8개를 1~4개로 줄였다.
  - 이체: 스레드마다 이체 1,000번(3번 조건은 10만 번)을 1~3번으로, 잔액 1,000,000을 100으로 줄였다.
  - 식사하는 철학자: 끼니 100번을 1~2번으로 줄이고, 0~2ms 무작위 생각 시간을 고정 단계로 바꿨다.

## 생략한 부분

- 세마포어, BoundedSemaphore, Event 안의 조건 변수와 락은 그리지 않는다. Event의 구성은 설명 칸의 주요 특성에 적었다.
- 작업을 나눠 주는 main 스레드, ThreadPoolExecutor, 멈춤을 감시하고 스택을 남기는 실행 틀, 이체와 철학자를 돌린 자식 프로세스는 그리지 않는다.
- 걸린 시간과 CPU 시간은 모형에 없다. "실험에서 잰 값"에만 있다.
- 무작위로 정하던 생각 시간과 쉬는 시간을 고정했으므로, 실험의 멈춤 비율(모두 왼쪽 먼저의 10회 중 6회 등)은 모형에 없다. 같은 구성은 늘 멈추거나 늘 끝난다.
- 묶음 3의 기준 조건(로더만 도는 조건)과 묶음 3 측정 조건의 마지막 질문(스핀락이 나은 경우), 묶음 2 측정 조건의 마지막 질문(세마포어 둘로 만든 버퍼)은 장면으로 만들지 않았다. 해당 근거와 복습 카드로 이어진다.
- 임계 영역 문제를 푸는 세 조건(질문 10)은 식사하는 철학자의 근거 링크로만 둔다.
- 실험에서 다루지 않은 정해진 순서로 실행·멀티스레드 FizzBuzz는 화면에도 없다.
- 화면의 코드는 실험 코드에서 문서 문자열, 일부 주석, 실행 틀의 기록 줄을 빼고 옮겼다.

## 확인 결과

2026-10-27에 확인했다.

모형 테스트: Node.js 22.22.0에서 `node --test model.test.cjs` 15개 통과. 119개 구성(이중 release() 8, 조건 변수 버퍼 12, 버퍼 크기 1 3, 기다리는 방법 12, 이체 72, 식사하는 철학자 12)을 모두 돌려 다음을 확인한다.

- 모든 구성이 400단계 안에 끝나거나 멈춘 까닭(교착 상태, 깨워 줄 스레드 없음, 끝없는 다시 시도)이 정해지고, 같은 구성은 언제나 같은 기록을 낸다.
- 한 단계에 실행하는 스레드는 하나이고, 실행할 스레드가 없는 단계는 모두 기다리는 중이다. GIL을 쓰는 장면에서는 실행한 스레드가 GIL을 쥐고, 단계가 끝나면 실행을 이어 갈 스레드만 GIL을 남긴다.
- 락은 잠겼을 때만 잡은 스레드가 있고, RLock의 수준은 잠긴 동안 1 이상이다. 도구의 대기 목록과 스레드가 기다리는 것이 서로 맞는다. 세마포어 카운터는 0 아래로 내려가지 않고, BoundedSemaphore의 카운터는 초깃값을 넘지 않는다.
- 교착 상태로 멈춘 기록의 마지막 단계에는 기다림의 고리가 있고, 끝까지 간 기록에는 고리가 없다.
- 이중 release(): Semaphore는 동시 호출이 3(상한 2)까지 늘고 오류가 없으며 끝난 뒤 카운터가 3이다. BoundedSemaphore와 Lock은 타임아웃이 아닌 4번째 호출의 release()에서 ValueError와 RuntimeError를 내고, RLock은 타임아웃 난 1번째 호출에서 RuntimeError를 낸다. with 문으로 고친 코드는 넷 모두 상한을 지키고 오류가 없다. 실험에서 오류가 난 호출의 종류(타임아웃 난 호출인지 아닌지)와 같다.
- 조건 변수 버퍼: 업로드 1·2·3번째 뒤 남은 작업자, IndexError 수, 빈 jobs에서 깨어난 횟수가 실험의 작업자 2개·4개 구성 8가지와 같다. 예를 들어 if·notify()·4개는 3·2·1개, IndexError 3번이고, while·notify_all()·4개는 4·4·4개, 빈 jobs에서 깨어남 9번이다.
- 버퍼 크기 1: 조건 변수 하나와 notify()는 작업 1만 처리하고 세 스레드가 모두 기다린 채 멈춘다. notify_all()과 조건 변수 둘은 끝난다.
- 기다리는 방법: pass는 로더의 set()을 늦춘다(요청 처리 스레드 1~4개에 단계 9·13·17·21). sleep은 set()을 늦추지 않지만(단계 6~9) 마지막 스레드가 알아채는 단계가 늦다(13~16). Event.wait()는 set()을 늦추지 않고(6~9) set() 뒤 스레드마다 한 단계씩 차례로 빠져나온다(마지막 7~13).
- 이체: 보내는 계좌부터·DB 확인은 첫 이체에서 멈춘다. 락 순서 고정과 내려놓고 다시는 모든 구성이 끝나고, 잔액의 합은 그대로다. 자기 계좌 이체는 Lock이면 멈추거나(자기가 쥔 락을 기다리는 고리 하나) 다시 시도를 되풀이하고, RLock이면 다시 시도 없이 끝난다.
- 식사하는 철학자: 모두 왼쪽 먼저와 같은 생각 시간은 아무도 먹지 못한 채 다섯이 고리를 이룬다. 생각 시간이 다르면 끝나고, 큰 번호 먼저와 웨이터는 모든 구성이 끝난다.

모형 테스트가 잘못을 잡는지도 봤다. `notify()`가 대기 목록 맨 뒤 스레드를 깨우게 바꾼 사본은 버퍼 크기 1 테스트 하나가, BoundedSemaphore의 초깃값 검사를 뺀 사본은 세마포어 카운터와 이중 release() 테스트 둘이 실패했다.

- 가짜 API 상자를 선이 들어오지 않는 상자로 둔 사본: 320px에서 1,376곳을 잡았다. 가짜 API 상자가 둘째 줄로 내려가 선이 상한 도구 상자와 그 글자를 지난다. 390px과 1440px에서는 두 상자가 한 줄에 들어가므로 0곳이 맞다.
- 쥔 GIL 꼬리표를 30px 아래에 둔 사본: 세 폭에서 1,314곳, 1,330곳, 1,346곳을 잡았다. 기다리는 방법과 이체에서 꼬리표가 쥔 스레드의 맡은 일 글자("계산 1/4", "A→B 1/1")에 겹친다.

GitHub Pages 경로 확인: `docs/`를 로컬 서버의 `/cs-lab/` 아래에 두어 GitHub Pages와 같은 경로로 열고 33개 항목을 확인했다.

- 첫 화면: 320, 390, 768, 1440px의 밝은 화면과 어두운 화면에서 쪽 가로 넘침이 없고, 화면 링크는 동시성 관계도와 동기화 관계도 둘이다. 배경색이 화면 색 설정을 따른다.
- 주소: 첫 화면의 링크로 이 페이지가 열린다. 폴더 주소에 장면 이름을 붙이면(`02-synchronization-primitives/#phil` 등) 여섯 장면이 모두 제 장면으로 열리고, `index.html#transfer`도 이체 장면으로 열린다.
- 링크: 같은 사이트 링크는 모두 `/cs-lab/` 아래를 가리킨다. "복습 화면 목록"은 첫 화면으로 돌아가고, 첫 화면에서 01 화면도 열린다. 바깥 링크 66곳은 모두 https이고 저장소의 `main`, CPython v3.14.2, 파이썬 3.14 문서 중 하나를 가리킨다.
- 콘솔 오류와 경고, 실패한 요청, 바깥으로 나가는 요청이 없다.

링크 확인: 바깥 링크 66곳은 근거 링크 56곳과 처음 연 화면의 링크다(저장소 48, CPython 10, 파이썬 문서 8).

- 저장소 링크는 파일과 폴더 16곳을 가리키고, 16곳 모두 저장소에 있다. README 제목으로 가는 링크 24곳(실험 README 23, 이 README 1)은 GitHub의 제목 주소 규칙(github-slugger)으로 만든 주소와 맞는다.
- 근거 이름 56개는 모두 정의되어 있고 한 곳 이상에서 쓰인다. 화면에 나오는 복습 카드 32장은 모두 카드 문서에 있다.
- CPython 링크 중 줄 범위가 있는 9곳(`threading.py` 6, `_threadmodule.c` 2, `lock.c` 1)은 v3.14.2 소스에서 그 줄에 설명한 코드가 있는 것을 확인했다. 나머지 하나는 `Lib/queue.py` 파일 전체다.
- 파이썬 문서 링크 중 앵커가 있는 7곳은 v3.14.2의 문서 소스(`Doc/library/threading.rst`, `Doc/library/sys.rst`)에서 그 앵커가 생기는 것을 확인했다. 나머지 하나는 queue 문서의 첫머리다. docs.python.org는 확인한 환경에서 열리지 않아 문서 소스로 대신했다.
