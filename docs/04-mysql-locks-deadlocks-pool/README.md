# 락 관계도

04 MySQL 락·데드락·커넥션 풀 실험을 복습하는 설명용 화면이다. 페이지 하나에 전체 지도와 장면 여덟을 둔다. 장면마다 관계도, SQL, 모든 단계를 한눈에 보는 띠가 같은 단계를 가리키고, 관계도의 요소를 고르면 그 요소의 개념, 지금 상태, 근거가 설명 칸에 나온다. 락을 다루는 장면은 관계도 아래에 그 단계 끝의 락을 `performance_schema.data_locks`와 `data_lock_waits`의 꼴로 함께 적는다.

화면의 단계는 설명용 모형(`model.js`)이 만든 순서다. 순서표 장면(묶음 ①②와 ③의 두 요청)의 문장 결과, 기다림, 미룸, 오류와 기다리는 동안 읽은 락은 실험의 원자료와 같고, 동시 요청 장면(문제 상황 2-1, ③)은 요청 10개일 때 결과별 수, 오류, 다시 시도 수, 끝난 뒤 값이 원자료와 같다(아래 "확인 결과"). 실측값은 "실험에서 잰 값" 칸과 `실측 기록` 표시가 붙은 근거에만 있고, 모두 [실험 README](../../experiments/04-mysql-locks-deadlocks-pool/README.md)의 결과에서 옮겼다.

페이지의 틀과 조작은 [03 MVCC 관계도](../03-mysql-isolation-mvcc/README.md)와 같다. 2026-11-04에 만들었다.

## 그림 규칙

[01 화면](../01-concurrency-models/README.md#그림-규칙), [02 화면](../02-synchronization-primitives/README.md#그림-규칙), [03 화면의 그림 규칙](../03-mysql-isolation-mvcc/README.md#그림-규칙)을 따른다. 아래는 이 화면에서 정하거나 바꾼 것이다. 다음 실험의 복습 화면도 InnoDB의 인덱스 레코드와 락을 그리면 이 규칙을 쓴다.

- 모양: DB 세션(연결)은 03처럼 원이다. 순서표 장면은 원에 A, B를, 동시 요청 장면은 요청 번호를 적고, 동시 요청은 요청 하나가 연결 하나다. 세션 상자에는 원과 그 세션만의 것을 적는다. 순서표 장면은 상태, 트랜잭션, 마지막 결과(`→ id 2, 3`)나 오류(`오류 1213`)이고, 동시 요청 장면은 트랜잭션 줄 없이 상태와 마지막 결과다. 요청이 끝난 단계에는 상태 줄에 요청의 결과(지급, 이미 받음, 오류, 포기 등)를 적는다.
- 인덱스 줄: 03은 표 안의 칸 하나를 행 하나로 그렸지만, 이 화면은 표 상자 안을 인덱스마다 한 줄로 나눈다. 위가 보조 인덱스(secondary index), 아래가 행 데이터를 담은 클러스터형 인덱스(clustered index, `PRIMARY`)다. 줄 이름은 인덱스 이름과 레코드 키다(`idx_user (user_id, id)`, `PRIMARY (id) · 행 데이터`). 유니크 인덱스는 이름 뒤에 `UNIQUE`를 붙인다. 표 이름(`entries · InnoDB`)은 03처럼 표 상자 아래쪽 왼편에 적는다.
- 레코드와 갭: 줄 안의 실선 칸이 인덱스 레코드(index record)이고 키 순서로 놓는다. 칸 위의 이름은 `data_locks`의 `LOCK_DATA`와 같은 꼴(`2`, `7, 2`, `7, 1, 1`)이다. 레코드 칸 앞의 점선 칸이 그 레코드 앞의 갭(gap)이고, 맨 끝 칸이 supremum(마지막 레코드 뒤의 갭을 나타내는 가짜 레코드)이다. 03의 "행 사이" 칸 하나를 키 구간마다 나눈 것이다.
- 갭 칸은 그 인덱스에 갭 쪽 락이나 갭을 기다리는 일이 한 번이라도 있으면 그린다. 범위를 잠그는 장면(잠근 응모 사이, 인덱스가 없을 때, SERIALIZABLE의 1.74초, 두 지급 요청)은 첫 인덱스의 갭 칸을 늘 그려, 갭을 잠그지 않는 조건(READ COMMITTED)과 견줄 수 있게 한다.
- 칸 자리: 모든 단계를 미리 보고, 한 번이라도 나오는 레코드의 칸 자리를 잡아 둔다. 그 단계에 없는 레코드(아직 넣기 전이거나, 지워졌거나, 되돌려진 것)는 칸과 앞 갭 칸을 숨기고, 다음 갭 칸이 그 자리까지 넓어진다. 그래서 레코드가 들어오면 갭 하나가 둘로 나뉘는 것이 보인다. 커밋 전에 넣은 레코드는 진한 점선 테두리로, 지우고 커밋하기 전인 레코드는 옅게 그리고 이름에 줄을 긋는다.
- 행의 값: `PRIMARY` 칸 안의 작은 상자가 그 행의 값이다. 맨 위가 가장 새 값이고, 점선은 커밋하지 않은 트랜잭션이 쓴 값, 그 아래 회색은 커밋된 값이다. 03과 달리 이전 버전을 모두 그리지 않고 커밋된 값 하나만 남긴다.
- 보유(hold)한 락: 03은 보유한 락을 세션에서 칸으로 가는 파란 선으로 그렸지만, 이 화면은 칸 안의 이름표로 적는다. 문장 하나가 여러 칸(레코드 여럿과 그 앞 갭, supremum)에 락을 걸어, 선으로 그리면 선이 칸을 가리기 때문이다. `X A`는 A가 보유한 배타 락(exclusive lock), `S A·B`는 A와 B가 보유한 공유 락(shared lock), `II B`는 B의 삽입 의도 락(insert intention lock)이다. 동시 요청은 `X 1~3`처럼 요청 번호를 적는다. 넥스트 키 락(next-key lock)은 레코드 칸과 그 앞 갭 칸에 함께, 갭 락(gap lock)과 삽입 의도 락은 갭 칸에, 레코드 락(record lock)은 레코드 칸에, supremum의 락은 supremum 칸에 적는다. 보유한 락이 걸린 칸은 파란 테두리와 옅은 파랑 채움이다. 표 락(`IX`, `IS`)은 관계도에 그리지 않고 아래 `data_locks` 표에만 적는다.
- 연결선은 기다림만 그린다. 기다리는 세션 상자의 아래 가장자리에서 그 락의 칸 위 가장자리로 회색 점선을 긋고, 기다리는 칸은 점선 테두리다. 기다림의 고리(데드락)를 이룬 기다림은 주황 선이다. 데드락 탐지가 켜져 있으면 InnoDB가 고리가 생긴 단계 안에서 고리를 닫은 쪽을 1213으로 되돌리므로 그 단계에만 그리고, 꺼져 있으면 1205로 풀릴 때까지 단계마다 그린다. 인덱스 이름은 선 위에 바탕색 테두리를 둘러 적어, 선이 지나가도 읽힌다.
- 커넥션 풀 장면은 그림이 다르다. 앱 프로세스 상자 안에 요청 50개를 점으로, 그 아래 커넥션 풀 상자에 미리 만든 연결을 칸으로 두고(칸 안 글자는 그 연결을 빌린 요청), 앱 상자 아래 MySQL 상자에 서버에 열린 연결 수를 적는다. NullPool은 연결 칸 대신 "풀 없음" 설명을 적는다. 점의 색은 연결 기다림, 새 연결 여는 중, 연결을 쓰는 중, 끝, 풀 타임아웃이다. 풀에서 MySQL로 가는 화살표는 연결을 쓰는 요청이 있을 때 파랗다.
- 색은 01의 세 갈래다. 주황은 문제에만 쓴다: 오류(1213, 1205), 갱신 손실(lost update), 중복 지급, 아무도 받지 못한 지급, 반만 반영된 이체, 데드락 탐지를 끈 채 남은 고리, 풀 타임아웃. 유니크 제약 판에서 "이미 받음"으로 처리한 1062는 주황으로 칠하지 않는다.
- 시점은 01~03과 같다. 실행 여부(원 채움, 코드 이름표와 옅은 파랑 줄, 단계 띠 칸)는 그 단계 동안의 상태이고, 락, 기다림, 레코드, 값, 연결선은 그 단계가 끝난 뒤의 상태다.
- 단계는 이벤트의 순서이고 시간 길이가 아니다. 순서표 장면은 실험의 순서표 한 줄이 한 단계이고, 마지막 줄을 보낸 뒤에도 끝나지 않은 문장이 있으면 "끝" 단계를 더한다(둘이면 "끝1", "끝2"). 동시 요청 장면은 요청마다 문장을 하나씩 보내는 한 차례가 한 단계다. 커넥션 풀 장면만 한 단계가 모형의 0.2초이고, 단계에 모형의 시각을 붙인다.
- 사람이 적을 예상이나 답을 미리 채우지 않는다. 질문에는 답을 적지 않고 "내 예상" 칸은 비워 둔다. 질문이 앞의 문제 상황을 가리키면 그 표, 처음 행, 문장 순서, 조건을 처음 낸 그대로 다시 적는다.
- 좁은 화면 배치는 03과 같다. 가장 작은 글자는 11px이고, 글자 너비는 화면의 글꼴로 재며, 모든 단계를 미리 보고 상자 높이와 칸 자리를 정한다. 세션이 많아 세션 상자가 64px보다 좁아지거나 표가 한 줄에 들어가지 않으면 관계도를 줄이지 않고 관계도 칸 안에서 옆으로 밀어 본다. 풀 장면의 상자 이름과 설명은 들어가지 않으면 여러 줄로 쓴다.

## 화면 구성

위에서부터 장면 버튼, 전체 지도와 "이 장면의 개수", 먼저 생각해 볼 질문과 "내 예상" 칸, 단계 이동 막대와 장면별 조절, 관계도가 이어진다. 관계도 아래에 설명 한 문장과 락 표가 있다. 배치와 접힌 칸은 03 화면과 같다.

### 전체 지도와 장면 고르기

- 전체 지도는 움직이지 않는 작은 그림이다. 앱 프로세스(웹 서버 · SQLAlchemy) 안에 요청과 커넥션 풀을, 그 아래 MySQL 서버(mysqld · InnoDB) 안에 연결·세션, 트랜잭션, 스냅숏, 레코드 락, 갭·넥스트 키 락, 삽입 의도 락, 데드락 탐지, 락 대기 한도, 클러스터형 인덱스(`PRIMARY`), 보조 인덱스, 유니크 제약을 둔다. 고른 구성에 나오는 부분만 진하게 그린다.
- 장면 버튼은 네 무리다. "범위를 잠그는 락"에 잠근 응모 사이, 인덱스가 없을 때, SERIALIZABLE의 1.74초, "데드락"에 반대로 보낸 두 이체, 두 지급 요청, "동시 요청"에 동시 차감, 중복 지급 막기, "커넥션 풀"에 커넥션 풀이 있다.
- 주소 끝에 `#gap`, `#noidx`, `#serial`, `#transfer`, `#pair`, `#deduct`, `#reward`, `#pool`을 붙이면 그 장면으로 열린다. 붙이지 않으면 그 브라우저에서 마지막에 본 장면이, 처음이면 잠근 응모 사이가 열린다.
- 순서표 장면은 실험에서 돌린 22개 조건만 고를 수 있다. SERIALIZABLE의 1.74초와 두 지급 요청은 조건이 하나라 조절 단추 대신 그 조건을 적는다.

| 장면 | 보는 것 | 실험 README |
|---|---|---|
| 잠근 응모 사이 | A가 user 7의 응모를 `FOR UPDATE`로 잠근 동안 B가 넣는 응모 (가)~(마)가 기다리는지, 그때 `idx_user`와 `PRIMARY`의 어느 레코드와 갭에 락이 걸렸는지, READ COMMITTED에서는 어떻게 다른지 | 문제 상황 1 |
| 인덱스가 없을 때 | 같은 잠금을 `user_id`의 인덱스 없이 할 때 B의 `INSERT` 둘과 `DELETE`가 기다리는지, 잠기는 범위가 어디까지인지 | 문제 상황 1-1 |
| SERIALIZABLE의 1.74초 | 03 실험에서 미뤄 둔 기다림(B의 `INSERT`가 1.74초 기다림)에서 A의 평범한 `SELECT`가 거는 락과 B의 `INSERT`를 막은 락 | 문제 상황 1-2 |
| 반대로 보낸 두 이체 | 두 이체가 두 계좌 행을 서로 반대 순서로 고칠 때 생기는 기다림, 데드락 탐지를 켰을 때와 껐을 때, 둘 다 작은 id부터 고칠 때 | 문제 상황 2와 그 이어서 |
| 두 지급 요청 | 빈 `rewards`에서 두 요청이 `COUNT(*) ... FOR UPDATE`로 확인하고 지급 행을 넣을 때 서로를 막는 락 | 문제 상황 3의 (가) 처음 판을 두 요청으로 줄임 |
| 동시 차감 | 같은 잔액을 읽고 쓰는 요청 2~10개의 결과를 격리 수준 셋에서 | 문제 상황 2-1 |
| 중복 지급 막기 | 판 열 개(막지 않음, (가) 비관적 락 셋, (나) 낙관적 락 넷, (다) 유니크 제약, (가)와 (다)를 함께)마다 지급 행 수, 잔액, 오류, 다시 시도 | 문제 상황 3 |
| 커넥션 풀 | 요청 50개가 QueuePool(풀 5, 10, 50, 풀 5에 `pool_timeout` 0.5초)과 NullPool에서 연결을 기다리고 쓰는 차례 | 문제 상황 4 |

### 관계도

- 위에 세션 상자를 같은 너비로 한 줄에 두고, 아래에 표 상자를 한 줄로 둔다. 선이 들어오는 표를 모두 한 줄에 두어, 선이 다른 표 상자를 지나가지 않게 한다.
- 순서표 장면의 두 세션은 A, B다. 동시 요청 장면은 요청 1~n이고, 동시 차감은 `points` 표, 중복 지급 막기는 `points`와 `rewards` 표를 둔다.
- 커넥션 풀 장면은 위 그림 규칙의 앱, 풀, MySQL 상자다.

### 설명 한 문장

관계도 아래 한 문장은 그 단계의 문제 이벤트(오류, 갱신 손실, 중복 지급, 아무도 받지 못한 지급, 풀 타임아웃, 데드락 탐지를 끈 채 생긴 고리)를 먼저 고르고, 없으면 그 단계의 첫 이벤트를 고른다. 나머지는 접힌 "이 단계의 다른 일"에 있다. 마지막 단계에는 결과를 붙인다. 순서표 장면은 읽은 값, 기다린 문장, 미룬 문장, 오류, 데드락과 되돌린 쪽, 끝난 뒤 표를 원자료와 같은 모양으로, 동시 요청 장면은 결과별 수, 오류, 다시 시도 수, 끝난 뒤 값을, 커넥션 풀 장면은 성공, 타임아웃, 다 끝난 시각, 가장 오래 기다린 요청이 연결을 받은 시각(모형)을 적는다.

### 락 표

순서표 장면과 동시 요청 장면은 관계도 아래 접을 수 있는 칸에 그 단계 끝의 락을 `performance_schema.data_locks`처럼 적는다. 열은 세션, `OBJECT_NAME`, `INDEX_NAME`, `LOCK_TYPE`, `LOCK_MODE`, `LOCK_STATUS`, `LOCK_DATA`이고, 세션마다 표 락, 인덱스, 레코드 순이다. 앞 단계에 없던 줄은 옅은 파랑, 기다리는 줄은 굵게 적는다. 그 아래 `data_lock_waits` 줄은 기다리는 락과 그 락을 막는 락의 쌍이다. 순서표 장면에서 실험이 락을 읽은 단계는 이 표가 원자료와 같다(아래 "확인 결과").

### 코드

실험 코드가 보내는 SQL을 순서대로 적는다. 순서표 장면은 준비 SQL, 데드락 탐지·락 대기 한도·격리 수준 설정, 그리고 `A: SELECT …;`처럼 보내는 세션을 앞에 붙인 `lock_timelines.py`의 순서표 줄이다. 줄 끝 주석의 번호는 문제 상황의 번호다. 동시 요청 장면은 `burst_lab.py`의 요청 코드이고, `<>` 안은 앱이 앞 문장의 결과로 채우는 값이며, 앱이 50ms 일하는 것과 결과에 따라 갈리는 처리(이미 받음, 다시 시도, DB 오류)는 주석 줄이다. 커넥션 풀 장면은 `pool_lab.py`의 `burst()`를 줄여 옮겼고, 이름표의 숫자는 그 줄에 있는 요청 수다. 이름표 규칙은 02, 03과 같다.

### 단계 띠

세션마다 한 줄, 그 아래 장면별 값 줄이 있다. 칸 글자는 시(트랜잭션 시작), 읽(락 없이 읽기), 잠(잠그며 읽기), 일(앱이 50ms 일함), 쓰(쓰기), 기(락을 기다리기 시작), 확(커밋), 되(ROLLBACK), !(오류)다. 점선 칸은 락을 기다리는 단계, 주황 칸은 오류가 난 단계다. 값 줄은 커밋된 행 수(잠근 응모 사이, 인덱스가 없을 때), A가 읽은 id(SERIALIZABLE의 1.74초), 두 계좌의 잔액과 합(이체), `rewards` 행 수(두 지급 요청), 잔액(동시 차감), 지급 행·잔액·version(중복 지급 막기)이다. 커넥션 풀 장면은 세션 줄 없이 시각, 쓰는 요청, 기다리는 요청, 끝난 요청, 타임아웃, 열린 연결 줄만 둔다. 값 줄에 네 자리 수가 있으면 칸을 넓힌다.

## 요소 설명

세션, 요청, 표, 클러스터형 인덱스(`PRIMARY`), 보조 인덱스, 유니크 보조 인덱스, 인덱스 레코드(`PRIMARY`와 보조 인덱스), 갭, supremum, 앱 프로세스의 요청, 커넥션 풀(QueuePool), NullPool, MySQL 서버의 연결을 고를 수 있다(14종). 고정된 개념, 주요 특성, 근거, 복습 카드는 `content.js`의 `ELEMENTS`에 있고, "지금"은 단계마다 만든다. 칸을 고르면 레코드의 키나 행의 값, 갭이 덮는 범위, 그 칸에서 보유 중인 락과 기다리는 락, 막는 세션이 나온다. 인덱스를 고르면 단계 끝의 레코드와 그 인덱스의 락이 나온다.

## 모형의 가정

순서표(묶음 ①②, ③의 두 요청)

- 실험처럼 한 단계에 순서표 한 줄을 보낸다. 한 세션은 앞 문장이 돌아와야 다음 문장을 보낸다. 앞 문장이 락을 기다리는 중이면 그 세션의 줄은 미루고, 앞 문장이 끝난 단계에 보낸다. 기다리는 문장은 매 단계 끝에 다시 실행해 본다. 실험의 "0.5초 안에 끝나지 않은 문장은 기다림"을 "그 단계 안에 락을 얻지 못한 문장"으로 옮긴 것이다. 이체 문제의 "4번은 3번을 보내고 2초 뒤"처럼 줄 사이의 시간은 그리지 않는다.
- 순서표를 다 보낸 뒤에도 기다리는 문장이 있고 풀어 줄 일이 없으면, 가장 먼저 기다리기 시작한 문장이 락 대기 한도(`innodb_lock_wait_timeout` 5초)에 닿아 1205를 받는다. 1205는 그 문장만 되돌리고 트랜잭션과 앞서 얻은 락은 그대로 둔다(`innodb_rollback_on_timeout=OFF`). 이 화면에서 꼬리 단계가 생기는 구성은 데드락 탐지를 끈 반대 순서 이체 하나이고, 꼬리 단계는 "끝1", "끝2"다.
- 조건에 쓸 인덱스: 기본 키 하나와 같으면 `PRIMARY`, 보조 인덱스의 앞 열과 같으면 그 인덱스, 아니면 `PRIMARY` 전체를 훑는다. 옵티마이저의 비용 판단은 옮기지 않았다.
- 잠그며 읽기(`FOR UPDATE`, `FOR SHARE`, SERIALIZABLE이 바꾼 평범한 `SELECT`): REPEATABLE READ 이상은 훑은 레코드마다 넥스트 키 락을 걸고, 마지막 레코드 뒤까지 훑으면 supremum에도 건다. 보조 인덱스를 같음 조건으로 찾으면 조건에 맞지 않는 첫 레코드에서 멈추고 그 레코드에는 갭 락만 건다. 기본 키 하나나 유니크 인덱스의 모든 열을 같음 조건으로 찾으면 레코드가 있을 때 그 레코드에만 레코드 락을 걸고, 없으면 들어갈 자리의 갭을 잠근다. READ COMMITTED는 조건에 맞는 레코드만 레코드 락으로 잠근다. 보조 인덱스로 찾으면 `PRIMARY`의 그 행에도 레코드 락을 건다.
- `UPDATE`, `DELETE`는 기본 키로 찾은 `PRIMARY` 레코드에 X 레코드 락을 걸고 커밋된 최신 버전(또는 자기가 쓴 버전) 위에 쓴다. 스냅숏은 03 화면과 같은 규칙이다.
- 암묵적 락(implicit lock): 다른 트랜잭션이 넣거나 지우고 아직 커밋하지 않은 레코드는 락 구조 없이 잠긴 것으로 본다. 다른 트랜잭션이 그 레코드에 락을 요청(request)하면 주인의 X 레코드 락으로 바꿔 적는다.
- `INSERT`: 표에 `IX`를 걸고 `PRIMARY`, 보조 인덱스 순으로 넣을 자리의 다음 레코드에 삽입 의도 락을 요청한다. 충돌(conflict)하면 기다리는 락으로 남고(`data_locks`에 WAITING), 충돌하지 않으면 확인만 하고 락으로 남기지 않는다. 기다리다 받은 삽입 의도 락은 GRANTED로 남는다. 유니크 인덱스는 같은 키의 레코드가 있으면 S 락(REPEATABLE READ는 넥스트 키 락)을 걸고 중복을 확인해, 그 레코드가 살아 있으면 1062를 낸다. 1062는 그 문장이 넣은 행만 되돌리고, 확인에 쓴 S 락과 트랜잭션은 남긴다. 새 레코드는 다음 레코드에 걸린 갭 쪽 락(넥스트 키 락, 갭 락, supremum의 락)을 같은 주인의 갭 락으로 물려받는다.
- 레코드를 지울 때(넣은 행을 되돌리거나 지운 행을 정리할 때) 그 레코드에 걸린 다른 트랜잭션의 락은 다음 레코드의 갭 락으로 옮긴다. 지운 행은 커밋할 때 바로 정리한다(purge를 줄임).
- 충돌 규칙은 InnoDB 소스의 `lock_rec_has_to_wait`를 옮겼다. 같은 트랜잭션의 락끼리와 S 락끼리는 충돌하지 않는다. 삽입 의도가 아닌 갭 쪽 락(갭 락, supremum의 락)을 요청할 때는 아무것도 기다리지 않는다. 레코드를 잠그는 요청은 갭 락을 기다리지 않고, 갭 락이나 삽입 의도 락의 요청은 레코드 락을 기다리지 않는다. 삽입 의도 락은 아무것도 막지 않는다. 나머지는 충돌한다.
- 대기열: 기다리는 락은 같은 레코드에서 충돌하는 보유 중인 락 전부(기다리기 시작한 뒤에 다른 트랜잭션이 기다림 없이 얻은 갭 쪽 락 포함)와 먼저 기다리기 시작한 락에 막힌다. 락이 해제(release)되면 대기열 앞에서부터, 막는 락이 없어진 기다림에 락을 부여(grant)한다. `data_lock_waits`도 같은 규칙으로 막는 락을 적는다. InnoDB 소스를 읽고 옮긴 규칙이고, 원자료로 확인한 것은 실험이 락을 읽은 단계뿐이다. SERIALIZABLE의 1.74초 6·7단계에서 B의 삽입 의도 락을 A의 S 락과 X 락이 함께 막는 것으로 적는 것은 실험이 락을 읽지 않은 단계다.
- 데드락 탐지가 켜져 있으면 락을 기다리게 될 때마다 기다림의 고리를 찾고, 고리를 닫은 쪽(락을 요청한 쪽)을 1213으로 되돌린다(트랜잭션 전체). 실험에서 되돌려진 쪽(B)과 같다. 실제 InnoDB는 되돌릴 트랜잭션을 고친 행 수 등으로 고른다. 탐지가 꺼져 있으면 고리가 남다가 꼬리 단계의 1205로 풀린다.

동시 요청(문제 상황 2-1, ③)

- 요청 n개가 같은 순간에 출발한다. 한 단계에 요청마다 다음 문장을 하나씩 요청 번호 순으로 보내고, 앱이 50ms 일하는 것도 한 단계로 센다. 기다리던 문장은 락을 받으면 같은 단계 안에서 이어서 실행한다. 실제 요청은 거의 같은 때 문장을 보내 누가 먼저 락을 얻는지가 실행마다 다를 수 있다.
- 다시 시도는 `burst_lab.py`의 `serve`와 같다. 바꾼 행이 0이면 정한 횟수(최종판은 3번)까지 처음부터 다시 하고, DB 오류(1213 등)는 다시 하지 않는다.
- 실험은 요청 10개로 돌렸다. 이 장면은 2~10개(처음은 3개)를 고를 수 있고, 10개일 때 결과별 수, 오류, 다시 시도 수, 끝난 뒤 값이 원자료와 같다. 동시 요청에서는 락 대기 한도에 닿는 문장이 없어 1205 꼬리 단계를 두지 않는다.

커넥션 풀(묶음 ④)

- 요청 50개가 같은 순간에 출발해 연결을 빌리고, 트랜잭션 안에서 `SELECT 1` 뒤 0.2초를 쓰고 돌려준다. 모형은 0.2초 단위로 나눠, 돌려받은 연결을 기다리는 요청에 요청 번호 순으로 빌려준다. `pool_timeout`이 되는 시각은 따로 한 단계로 둔다.
- 실측은 차례마다 약 0.216초를 써서, 다 끝난 시간이 모형(차례 수 × 0.2초)보다 5~7% 길었다. 화면의 시각은 모형의 값이고 실측은 "실험에서 잰 값"에 있다.
- QueuePool은 연결 `pool_size`개를 미리 만들어 둔 상태에서 시작하고 `max_overflow`는 0이다. NullPool은 요청마다 새로 연결하고 돌려줄 때 끊는다. 새 연결에 드는 시간은 `c`로 적고 길이를 그리지 않는다(이 맥에서 50개를 동시에 열 때 요청마다 약 19~76ms).
- MySQL 상자의 열린 연결 수는 앱의 연결만 센다. 실측의 동시 최대 연결에는 관찰용 연결 1개가 더해졌고(풀 50과 NullPool 51), 2초쯤 걸린 풀 5는 Docker 상태 검사 연결까지 더해져 7이었다.

## 생략한 부분

- 시간: 기다린 시간, 요청 시간, 처리량은 그리지 않는다. "실험에서 잰 값"에만 있다.
- AUTO-INC 락: `rewards`의 `id`는 `AUTO_INCREMENT`지만, MySQL 8.4의 기본값 `innodb_autoinc_lock_mode=2`에서는 표 단위 AUTO-INC 락을 쓰지 않으므로 그리지 않는다. 실험 서버는 이 값을 바꾸지 않았다(환경 파일에는 남기지 않았다).
- READ COMMITTED의 semi-consistent read: READ COMMITTED에서 도는 `UPDATE`(동시 차감)는 기본 키로 찾은 한 행이 늘 조건에 맞아, 맞지 않는 행의 락을 해제하는 일이 없다.
- 락 구조의 메모리와 페이지 단위 비트맵, 데드락 희생자를 고르는 가중치, 데드락 탐지 자체의 비용은 그리지 않는다.
- 행의 이전 버전(undo log)과 purge는 03 화면에서 다룬다. 이 화면은 커밋된 값과 커밋 전 값만 보인다.
- SQLAlchemy가 연결을 돌려받을 때 하는 ROLLBACK(reset on return), `pool_pre_ping`, 풀에서 꺼내는 순서, `max_overflow`가 0보다 클 때는 그리지 않는다.

| `model.js` | 실행 규칙 모형. 구성마다 모든 단계의 상태를 미리 계산한다. |
| `content.js` | 요소 설명, 장면 안내(질문, 볼 것, 실험에서 잰 값), 근거 링크, 복습 카드 앞면 |
| `model.test.cjs` | 모형 테스트. 실험 원자료와 견준다. |

## 확인 결과

2026-11-04에 확인했다.

모형 테스트: Node.js 22.23.4에서 `node --test model.test.cjs` 15개 통과.

- 순서표 22개 조건(조건마다 3회)에서 모든 문장의 결과 행, 행 수, 오류 코드, 기다림, 미룸, 보낸 단계와 끝난 단계가 원자료(`results/…-locks-…jsonl`)와 같다. 기다리는 동안 읽은 `data_locks`와 `data_lock_waits` 78개(26개 단계 × 3회)가 그 단계의 모형 상태와 같고(표 락 포함), 끝난 뒤 행과 데드락 보고(되돌린 쪽, 보유한 락, 기다린 락)도 같다. 화면의 장면이 22개 조건을 모두 한 번씩 그린다.
- 동시 요청 13개 판(요청 10개, 판마다 3회)의 결과별 수, 오류, 다시 시도 수, 끝난 뒤 값이 원자료(`results/…-burst-…jsonl`)와 같다. 이긴 요청이 하나인 판 여섯에서, 나머지 요청이 모두 이긴 요청보다 늦게 끝나는지(그 커밋을 기다렸는지)도 원자료의 요청별 시간과 같다. 요청 2~10개의 모든 구성이 끝나고 실험의 검사 규칙(지급 행 수와 잔액, 차감)을 지키며, 판마다 지급 수가 요청 수와 상관없이 정해진 대로 나온다.
- 락 충돌 규칙 13가지가 InnoDB 소스의 `lock_rec_has_to_wait`와 같고, 기다리는 락이 먼저 기다린 락에도 막힌다.
- 같은 구성은 언제나 같은 기록을 낸다. 세션 상태는 넷 중 하나이고, 기다리는 세션에는 기다리는 칸과 막는 세션이 있으며, 서로 충돌하는 락을 함께 보유한 단계가 없다. 락과 기다림이 가리키는 칸은 모두 그 단계의 인덱스 레코드나 갭이다.
- 데드락: 탐지를 켜면 고리를 닫은 쪽(B)이 1213을 받는다. 끄면 고리가 남다가 1205가 문장만 되돌리고, A는 id 1의 락을 계속 보유한다. 끝난 뒤 두 계좌의 합은 탐지를 끈 반대 순서에서만 1900이고 나머지는 2000이다.
- 커넥션 풀: 다섯 경우 × 3회의 성공과 타임아웃 수가 원자료(`results/…-pool-…jsonl`)와 같다. QueuePool의 다 끝난 시간과 가장 오래 기다린 시간은 모형(차례 수 × 0.2초)보다 길고, 그 차이가 차례마다 25ms 안이다. 빌린 연결 수는 풀 크기를 넘지 않는다.

모형 테스트가 잘못을 잡는지도 봤다. `model.js`를 한 곳씩 틀리게 고친 사본 10개(갭 락끼리 충돌함, 레코드 락이 갭 락을 기다림, 삽입 의도 락이 다른 락을 막음, 먼저 기다린 락을 무시함, READ COMMITTED도 갭을 잠금, 새 레코드가 갭 쪽 락을 물려받지 않음, 암묵적 락을 바꿔 적지 않음, 1205가 트랜잭션 전체를 되돌림, 데드락 탐지를 켜도 고리를 찾지 않음, 풀 타임아웃이 나지 않음)에서 모두 테스트가 1~5개 실패했다.

브라우저 확인은 Playwright 1.63.0과 Chromium 153.0.8010.12로 했다.

- 구조: 144개 구성(잠근 응모 사이 10, 인덱스가 없을 때 6, SERIALIZABLE의 1.74초 1, 반대로 보낸 두 이체 4, 두 지급 요청 1, 동시 차감 27, 중복 지급 막기 90, 커넥션 풀 5)의 모든 단계(1,635개)에서 단계 끝에 있는 레코드의 칸만 보이고, 칸의 이름표가 그 칸에서 보유 중인 락과 같으며(락이 없는 칸에는 이름표가 없음), 기다리는 칸에는 점선 테두리가 있다. 기다림 선과 고리 선은 모형의 기다림 수만큼 그리고, 코드 이름표 수가 끝나지 않은 세션 수와 같으며, 세션이 실행한 줄과 다음 줄이 화면 SQL에 있다. 락 표와 `data_lock_waits`의 줄 수가 모형과 같다. 커넥션 풀은 점 50개의 상태, 빌려 간 연결 칸, 열린 연결 수가 모형과 같다.
- 겹침과 넘침: 1,635개 단계를 320, 360, 390, 480, 540, 600, 768, 1024, 1440px 폭에서 그렸다(14,715개 화면). 글자끼리 겹치지 않고, 세션 글줄은 세션 상자 안에, 칸 글자와 값 상자는 칸 안에, 칸은 표 상자 안에, 풀의 연결 칸과 점은 풀 상자와 앱 상자 안에 있다. 갭 칸이 있는 인덱스 줄에서 보이는 칸 사이에 6px 넘는 빈자리가 없고, 기다림 선은 다른 칸과 세션 상자를 지나가지 않는다. 가장 작은 글자는 11px이고 쪽 가로 넘침이 없다. 콘솔 오류와 경고가 없다. 390px에서는 어두운 화면도 같은 확인을 했다.
- 그림을 한 곳씩 틀리게 고친 사본 9개(고리 선을 빼기, 코드 줄 키 하나를 바꾸기, S 락 이름표를 빼기, 기다리는 칸 표시를 빼기, 없는 레코드 자리를 갭이 채우지 않게 하기, 세션 상자 높이를 줄이기, 락 이름표 글자를 크게 하기, 세션 글줄을 9px로 하기, 장면별 조절 줄의 너비 규칙을 빼기)는 이 확인이 모두 잡았다. 마지막 사본은 390px과 1024px에서는 넘치지 않았고 320px에서 넘침을 잡았다.
- GitHub Pages 경로: `docs/`를 로컬 서버의 `/cs-lab/` 아래에 두고 320, 390, 768, 1440px의 밝은 화면과 어두운 화면에서 열었다(176쪽). 첫 화면의 링크 넷(01~04)으로 각 화면이 열리고, 여덟 장면의 주소(`#gap` 등)와 `index.html#gap` 꼴의 주소가 제 장면으로 열리며, 네 화면의 "복습 화면 목록"이 첫 화면으로 돌아간다. 이 화면의 접힌 칸을 모두 펼치고 설명 칸을 연 채 마지막 단계로 가도 쪽 가로 넘침이 없다. 같은 사이트 링크는 모두 `/cs-lab/` 아래이고 바깥 링크는 모두 https다. 실패한 요청, 바깥으로 나가는 요청, 콘솔 오류와 경고가 없다.
- 요소 설명: 장면마다 구성 몇 개(40개 구성, 292개 단계)에서 14종 요소를 3,147번 골라 개념, 지금, 주요 특성, 근거가 모두 채워지는 것을 봤다.
- 조사: 관계도와 설명에 나오는 글 3,520개에서 괄호, 숫자, 영문 뒤의 조사(을/를, 이/가, 은/는, 과/와)가 앞말의 받침과 맞는지 봤다. 맞지 않는 것이 없었다.

링크 확인: 근거 링크 39곳 중 저장소 파일 28곳은 저장소에 있고, 그중 README 제목으로 가는 링크 20곳은 GitHub의 제목 주소 규칙(github-slugger)으로 만든 주소와 맞는다. 화면에 나오는 복습 카드 33장은 모두 카드 문서에 있다. 앞면 31장은 카드 문서와 글자가 같고, 2장(04-016, 04-027)은 카드 문서의 데드락 보고와 결과 표를 화면에 옮기지 않아 "카드 문서에 있음"으로 가리킨다. 바깥 링크 11곳(MySQL 8.4 문서 10곳, SQLAlchemy 2.1 문서 1곳)은 확인한 환경에서 바로 열리지 않아, 다른 경로로 페이지가 있는 것을 확인했다.
