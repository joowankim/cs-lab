# MVCC 관계도

03 MySQL 격리 수준과 MVCC 실험을 복습하는 설명용 화면이다. 페이지 하나에 전체 지도와 장면 일곱을 둔다. 장면마다 관계도, SQL, 모든 단계를 한눈에 보는 띠가 같은 단계를 가리키고, 관계도의 요소를 고르면 그 요소의 개념, 지금 상태, 근거가 설명 칸에 나온다.

화면의 단계는 설명용 모형(`model.js`)이 만든 순서다. 순서표 장면(묶음 1·3)의 문장 결과, 기다림, 미룸, 오류는 실험의 원자료와 같다(아래 "확인 결과"). 실측값은 "실험에서 잰 값" 칸과 `실측 기록` 표시가 붙은 근거에만 있고, 모두 [실험 README](../../experiments/03-mysql-isolation-mvcc/README.md)의 결과에서 옮겼다.

페이지의 틀과 조작은 [02 동기화 관계도](../02-synchronization-primitives/README.md)와 같다. 2026-10-28에 만들었다.

## 그림 규칙

[01 화면의 그림 규칙](../01-concurrency-models/README.md#그림-규칙)과 [02 화면의 그림 규칙](../02-synchronization-primitives/README.md#그림-규칙)을 따른다. 아래는 이 화면에서 정하거나 더한 것이다. 다음 실험의 복습 화면도 DB의 세션, 행 버전, 락을 그리면 이 규칙을 쓴다.

- 모양: DB 세션(연결)은 원이다. 세션 상자에는 원과 그 세션만의 것(상태, 트랜잭션, 스냅숏, 마지막 결과)을 적는다. 백그라운드 스레드(purge, 로그 스레드, WAL writer)와 VACUUM을 돌리는 관찰 세션, 앱의 연결도 같은 원으로 그리고, 트랜잭션 줄에 맡은 일을 적는다.
- 표는 바깥 상자이고 이름(`entries · InnoDB`)은 아래쪽 왼편에 적는다. 표 안의 칸 하나가 행 하나이고, 칸 위에 기본 키(`id 1`, `user_id 7`)와 그 행에 쥔 락(`X A`, `S A·B`)을 적는다. MySQL에서 행 사이 범위를 잠그는 표(`entries`)에는 점선 테두리의 "행 사이" 칸을 하나 더 둔다. 표의 모든 범위를 칸 하나로 그린다.
- 행 칸 안의 작은 상자가 그 행의 버전이다. 맨 위가 가장 새 버전이다. 실선은 커밋된 버전, 점선은 커밋하지 않은 트랜잭션이 쓴 버전, 회색 채움은 더 새 커밋 버전이 있는 이전 버전이다. MySQL은 이전 버전을 undo log에, PostgreSQL은 표 안에 dead tuple로 두지만, 같은 칸에 그리고 그림 설명과 요소 설명에서 자리를 밝힌다.
- 버전 오른쪽의 `←A`는 A의 스냅숏이 이 행에서 보는 버전이다. 트랜잭션 끝까지 쓰는 스냅숏(REPEATABLE READ 이상)만 표시한다. 문장마다 만들고 버리는 스냅숏(READ COMMITTED, 자동 커밋, MySQL SERIALIZABLE의 잠그며 읽기)은 단계 끝에 남지 않으므로 표시하지 않는다. 세션 상자의 "스냅숏 단계 k"는 그 스냅숏을 만든 단계다.
- MyISAM 표는 위쪽에 표 락 줄(`표 락 R A · 기다림 W B`)을 둔다. 표 락은 문장이 끝나면 놓는다.
- 열어 둔 트랜잭션 장면은 남은 이전 버전 수를 따로 상자에 적는다. MySQL은 "History list length", PostgreSQL은 "dead tuple"이라 이름 붙이고, A의 스냅숏 때문에 지우지 못하면 "A의 스냅숏이 붙잡음"을 주황으로 적는다.
- 커밋 장면의 로그 상자(redo log, binary log, WAL)는 기록이 있는 곳을 위에서부터 DB 메모리, OS 페이지 캐시, 디스크 칸으로 나눈다. 칸 안 상자는 커밋 번호다. 장애를 고르면 사라진 기록을 "사라짐" 칸에 주황으로 옮긴다.
- 연결선은 02와 같은 곡선으로, 세션 상자 아래 가장자리에서 받는 칸 위 가장자리로 긋는다. 쥔 락은 파란 실선, 기다리는 락이나 fsync는 회색 점선, purge·VACUUM의 정리와 백그라운드 fsync는 회색 실선이다. 행 락은 행 칸으로, 범위 락은 "행 사이" 칸으로, 표 락과 정리는 표 상자로, fsync는 로그 상자로 간다.
- 기다림의 고리: MySQL SERIALIZABLE의 동시 차감은 고리가 생긴 단계 안에서 InnoDB가 B를 오류 1213으로 되돌린다. 단계 끝에는 고리가 남지 않지만, 그 단계에만 고리를 이룬 두 기다림을 주황 점선으로 그린다.
- 색은 01의 세 갈래다. 주황은 문제에만 쓴다: 오류, 갱신 손실, dirty read, 같은 트랜잭션에서 같은 조건으로 읽은 결과가 바뀐 읽기, MyISAM 경고 1196, 지우지 못한 이전 버전, 잃은 커밋 기록. 그 단계에 바뀐 행 칸과 로그 칸, 쥔 락이 있는 칸은 파란 테두리, 기다리는 칸은 점선 테두리다.
- 시점은 01, 02와 같다. 실행 여부(원 채움, 코드 이름표와 옅은 파랑 줄, 단계 띠 칸)는 그 단계 동안의 상태이고, 트랜잭션, 스냅숏, 행 버전, 락, 로그 위치, 연결선은 그 단계가 끝난 뒤의 상태다.
- 단계는 이벤트의 순서이고 시간 길이가 아니다. 순서표 장면은 실험의 순서표 한 줄이 한 단계다. 마지막 줄을 보낸 뒤에도 끝나지 않은 문장이 있으면 "끝" 단계를 하나 더 둔다.
- 사람이 적을 예상이나 답을 미리 채우지 않는다. 질문에는 답을 적지 않고 "내 예상" 칸은 비워 둔다.
- 좁은 화면에서는 관계도를 보이는 폭에 맞춰 다시 배치해 글자 크기를 유지한다. 가장 작은 글자는 11px이다. 상자 너비와 줄 나눔은 화면의 글꼴로 글자 너비를 재서 정하고, 단계마다 상자 높이와 칸 자리가 바뀌지 않도록 모든 단계를 미리 본다(아직 없는 행의 칸 자리도 비워 둔다). 선이 들어오는 상자는 한 줄에 두고, 들어가지 않으면 관계도를 줄이지 않고 관계도 칸 안에서 옆으로 밀어 본다.

## 화면 구성

위에서부터 장면 버튼, 전체 지도와 "이 장면의 개수", 먼저 생각해 볼 질문과 "내 예상" 칸, 단계 이동 막대와 장면별 조절 버튼, 관계도가 이어진다. 배치와 접힌 칸은 02 화면과 같다.

### 전체 지도와 장면 고르기

- 전체 지도는 움직이지 않는 작은 그림이다. DB 서버 안에 세션, 트랜잭션, 스냅숏, 락, InnoDB 표, MyISAM 표, 이전 버전, purge·VACUUM, 로그 버퍼를 두고, 그 아래 운영체제의 페이지 캐시, 그 아래 디스크를 둔다. 고른 구성에 나오는 부분만 진하게 그린다.
- 장면 버튼은 네 무리다. "스냅숏과 읽기"에 스냅숏을 만드는 때, 잔액 세 번 읽기, "잠금과 쓰기"에 잠그며 읽기, 동시 차감, "이전 버전"에 열어 둔 트랜잭션, "엔진과 지속성"에 InnoDB와 MyISAM, 커밋을 디스크에가 있다.
- 주소 끝에 `#count`, `#report`, `#locking`, `#deduct`, `#hold`, `#engine`, `#commit`을 붙이면 그 장면으로 열린다. 붙이지 않으면 그 브라우저에서 마지막에 본 장면이, 처음이면 스냅숏을 만드는 때가 열린다.
- 실험에서 돌리지 않은 DB와 격리 수준의 조합(예: 문제 상황 1의 PostgreSQL)은 단추를 누를 수 없다. 커밋 장면의 설정 단추는 고른 DB의 것만 보인다.

|---|---|---|
| 스냅숏을 만드는 때 | 같은 조건을 다시 셀 때 스냅숏으로 읽는지 최신 행을 읽는지, 스냅숏을 만드는 단계(첫 읽기, WITH CONSISTENT SNAPSHOT, 첫 문장) | 문제 상황 1, 1-1, 1-2, 1-2 변형 |
| 잔액 세 번 읽기 | 격리 수준 넷에서 B가 고친 잔액을 A가 언제부터 보는지, MySQL SERIALIZABLE의 공유 락과 기다림 | 문제 상황 2 |
| 잠그며 읽기 | FOR UPDATE가 돌려주는 행과 잠그는 행·범위, SERIALIZABLE에서 B의 INSERT가 기다리는지 | 문제 상황 1-3 |
| 동시 차감 | 두 요청이 같은 잔액을 읽고 고칠 때의 기다림, 갱신 손실, 오류 40001, 데드락 | 문제 상황 3 |
| 열어 둔 트랜잭션 | A가 해 둔 일(경우 (가)~(바))에 따라 B가 고친 이전 버전이 지워지는지, A와 C가 읽는 값 | 문제 상황 4, 4 변형, 4-1, 4-3 |
| InnoDB와 MyISAM | 되돌린 트랜잭션에 남는 MyISAM 행과 경고 1196, 오래 걸리는 읽기 중 차감의 기다림 | 문제 상황 5, 5-1 |
| 커밋을 디스크에 | 설정마다 커밋 하나가 기다리는 fsync 수, 장애 때 잃을 수 있는 커밋 | 문제 상황 6 |

### 관계도

- 위에 세션 상자를 같은 너비로 한 줄에 두고, 아래에 표, 이전 버전 상자, 로그 상자를 둔다. 세션 상자의 글줄은 상태(실행 중이면 비움), 트랜잭션, 스냅숏, 마지막 결과(`→ 3`) 또는 오류(`오류 1213`)다. 커밋 장면은 트랜잭션과 스냅숏 줄 대신 맡은 일만 적는다.
- 순서표 장면의 두 세션은 A, B다. 열어 둔 트랜잭션은 A(열어 둔 쪽), B(고치는 쪽), C(새로 읽는 쪽)에 MySQL은 purge 스레드 P, PostgreSQL은 VACUUM을 돌리는 관찰 세션 V를 더한다. 커밋 장면은 앱과 로그 스레드(MySQL) 또는 WAL writer(PostgreSQL)다.

### 설명 한 문장

관계도 아래 한 문장은 그 단계의 문제 이벤트(오류, 갱신 손실, dirty read, 바뀐 읽기, 경고, 지우지 못한 이전 버전, 장애)를 먼저 고르고, 없으면 그 단계에 보낸 문장의 결과를 고른다. 커밋 장면은 fsync, 완료 응답, 백그라운드 fsync 순으로 고른다. 나머지는 접힌 "이 단계의 다른 일"에 있다. 마지막 단계에는 결과를 붙인다. 순서표 장면의 결과는 원자료와 같은 모양(읽은 값, 기다린 문장, 미룬 문장, 오류)이다.

### 코드

실험 코드가 보내는 SQL을 순서대로 적는다. 순서표 장면은 준비 SQL, 격리 수준 설정, 그리고 `A: SELECT …;`처럼 보내는 세션을 앞에 붙인 순서표 줄이다. 열어 둔 트랜잭션은 `history_lab.py`, 커밋 장면은 `durability_lab.py`의 SQL이고, DB가 스스로 하는 일(purge, 로그 스레드)은 주석 줄로 적는다. 이름표 규칙은 02와 같다.

### 단계 띠

세션마다 한 줄, 그 아래 장면별 값 줄이 있다. 칸 글자는 시(트랜잭션 시작), 읽(읽기), 잠(잠그며 읽기), 쓰(쓰기), 확(커밋), 되(ROLLBACK), !(오류), 정(이전 버전 정리), 내(fsync), 완(커밋 완료 응답)이다. 값 줄은 A가 센 수, A가 읽은 잔액, A가 읽은 행, 커밋된 잔액, B가 센 수, id 2 재고, 이전 버전, fsync 끝과 디스크다. 값 줄에 네 자리 수가 있으면 칸을 넓힌다.

## 요소 설명

세션, purge 스레드, VACUUM, 앱, 로그 스레드, 표(InnoDB, PostgreSQL, MyISAM), 행, 행 사이 범위, History list length, dead tuple, 로그(redo log, binary log, WAL)를 고를 수 있다. 고정된 개념, 주요 특성, 근거, 복습 카드는 `content.js`의 `ELEMENTS`에 있고, "지금"은 단계마다 만든다. 행을 고르면 버전 목록(누가 썼는지, 커밋했는지), 그 행을 보는 스냅숏, 쥔 락과 기다리는 세션이 나온다.

## 장면 더하기

- 순서표 장면은 `model.js`의 `TIMELINES`에 실험의 순서표와 같은 SQL과 연산을 적고, `SCENE_TIMELINES`, `SCENARIOS`, `CHOICES`, `DEFAULTS`에 장면을 더한다. 원자료가 있으면 `model.test.cjs`의 원자료 대조 테스트가 그 조건을 함께 본다.
- `board.js`의 `SCENES`, `OPTS`, `EXTRAS`, 장면별 함수(`objectList`, `codeFor`, `valueRows`, `resultText`, `partsFor`, `renderCounts`)와 `BOARD_NOTE`, `STRIP_NOTE`에 장면을 더한다. 순서표 장면은 `TIMELINE_SCENES`에 이름만 더하면 배치와 코드가 따라온다.
- `content.js`의 `SCENES`에 같은 이름으로 질문, 볼 것, 실험에서 잰 값, 근거, 복습 카드를 적는다. 질문의 답과 "내 예상"은 채우지 않는다.

## 모형의 가정

순서표(묶음 1·3)

- 실험처럼 한 단계에 순서표 한 줄을 보낸다. 한 세션은 앞 문장이 돌아와야 다음 문장을 보낸다. 앞 문장이 락을 기다리는 중이면 그 세션의 줄은 미루고, 앞 문장이 끝난 단계에 보낸다. 기다리는 문장은 매 단계 끝에 다시 실행해 본다. 실험의 "0.5초 안에 끝나지 않은 문장은 기다림"을 "그 단계 안에 락을 얻지 못한 문장"으로 옮긴 것이다.
- 스냅숏: MySQL READ UNCOMMITTED는 스냅숏 없이 커밋하지 않은 것까지 가장 새 버전을 읽는다. READ COMMITTED(두 DB)와 자동 커밋 문장은 문장마다 스냅숏을 만든다. MySQL REPEATABLE READ는 트랜잭션의 첫 consistent read에서, `WITH CONSISTENT SNAPSHOT`이면 트랜잭션을 열 때 만든다(REPEATABLE READ에서만). MySQL SERIALIZABLE은 트랜잭션 안의 평범한 SELECT를 공유 락을 거는 읽기로 바꾼다. PostgreSQL REPEATABLE READ 이상은 트랜잭션 제어문이 아닌 첫 문장에서 만든다.
- 락: 행 공유(S)·배타(X) 락, MySQL에서 REPEATABLE READ 이상의 기본 키가 아닌 조건으로 잠그며 읽을 때의 범위 락(GS·GX), INSERT가 범위 락과 부딪히는지 확인하는 넣기 의도 락(쥐지 않는다), MyISAM의 문장 단위 표 읽기·쓰기 락을 둔다. 범위는 표마다 하나로 본다. READ COMMITTED는 조건에 맞는 행만 잠근 것으로 그린다.
- UPDATE: MySQL은 행에 배타 락을 걸고 커밋된 최신 버전 위에 쓴다. PostgreSQL은 스냅숏으로 대상 행을 찾아 락을 걸고, 그 사이 다른 트랜잭션이 고치고 커밋했으면 READ COMMITTED는 최신 버전으로 다시 확인해 고치고, REPEATABLE READ 이상은 40001로 끝낸다.
- 기다림의 고리가 생기면 고리를 닫은 쪽(락을 요청한 쪽)을 1213으로 되돌린다. 실험에서 되돌려진 쪽(B)과 같다. 실제 InnoDB는 되돌릴 트랜잭션을 고친 행 수 등으로 고른다.
- SLEEP으로 오래 걸리는 재고 읽기는 결과가 시작할 때 정해지고, 순서표의 다른 줄을 모두 보낸 뒤 "끝" 단계에 끝난다.

열어 둔 트랜잭션(묶음 2)

- B의 UPDATE 1만 번을 2~6번으로 줄였다. 이전 버전은 그 버전을 덮은 트랜잭션이 아직 커밋하지 않았거나, 열린 스냅숏 하나에라도 그 커밋이 보이지 않으면 남긴다. 버전마다 누가 보는지 따지지 않고 가장 오래된 스냅숏 뒤에 덮인 버전을 모두 남기는 것이다(InnoDB purge가 가장 오래된 read view, PostgreSQL이 xmin horizon을 기준으로 지우는 것과 같다).
- MySQL purge는 B가 커밋할 때마다 돈다고 줄였다. 실제로는 주기적으로 돌아 (가)에서도 수십~300여 개가 잠시 남는다. PostgreSQL은 accounts의 페이지를 읽거나 고치는 문장 앞에 HOT pruning이 한 번 돌고, 관찰 세션이 VACUUM을 돌린다. 파일 크기는 그리지 않는다.
- MySQL이 오래된 스냅숏으로 읽을 때 되짚는 undo log 단계 수는 표의 최신 버전에서 그 스냅숏이 보는 버전까지의 버전 수다.

커밋을 디스크에(묶음 4)

- 로그 기록이 있는 곳을 DB 메모리, OS 페이지 캐시, 디스크 셋으로 본다. 커밋은 로그마다 OS에 쓰고, 커밋마다 fsync하는 설정(innodb_flush_log_at_trx_commit=1, sync_binlog=1, synchronous_commit=on)의 로그는 fsync가 끝날 때까지 기다린다. MySQL은 redo log, binary log 순으로 그린다.
- innodb_flush_log_at_trx_commit=2의 redo log는 로그 스레드가, synchronous_commit=off의 WAL은 WAL writer가 나중에 fsync한다. sync_binlog=0의 binary log는 OS가 정한 때에 내리므로 그리지 않는다.
- 장애는 마지막 커밋 응답 직후, 백그라운드 fsync 전에 난다. DB 프로세스만 죽으면 DB 메모리의 기록을 잃고 OS 페이지 캐시의 기록은 OS가 디스크에 내린다. OS까지 죽으면 디스크에 내린 것만 남는다.

## 생략한 부분

- 시간: 기다린 시간, 처리량, 지연은 그리지 않는다. "실험에서 잰 값"에만 있다.
- 행 사이 범위를 키 구간마다 나누는 규칙, 인덱스, 넣기 의도 락의 대기열은 04 실험에서 다룬다.
- InnoDB의 undo log 세그먼트, read view의 내부 필드(m_low_limit_id 등), PostgreSQL의 xmin·xmax 값과 페이지 구조, 표 파일 크기는 그리지 않는다.
- binary log와 redo log의 2단계 커밋, 그룹 커밋, doublewrite buffer, 데이터 페이지의 flush는 그리지 않는다.

## 확인 결과

2026-10-28에 확인했다.

모형 테스트: Node.js 22.22.0에서 `node --test model.test.cjs` 9개 통과.

- 묶음 1·3의 41개 조건(순서표 11개 × 돌린 DB와 격리 수준)에서 모든 문장의 결과 행, 오류 코드, 기다림, 미룸, 보낸 단계와 끝난 단계가 원자료(`results/…-isolation-…jsonl`)와 같다. 화면의 장면이 41개 조건을 모두 한 번씩 그린다.
- 같은 구성은 언제나 같은 기록을 낸다. 세션 상태는 넷 중 하나이고, 기다리는 세션이 원하는 락은 다른 세션이 쥐고 있으며, 서로 부딪히는 락을 함께 쥔 단계가 없다.
- dirty read, 바뀐 읽기, 갱신 손실, 오류, MyISAM 경고는 실험에서 그 일이 난 조건에서만 나온다.
- 묶음 2: 이전 버전을 모두 남기는 경우가 원자료에서 History list length나 dead tuple이 1만 개 가까이 남은 경우와 같고, A와 C가 읽은 값이 원자료와 같다. MySQL에서 A가 되짚는 단계 수는 B의 UPDATE 수와 같다.
- 묶음 4: 커밋마다 기다리는 fsync 수(MySQL 기본값 2, (2, 1)과 (1, 0) 1, (2, 0) 0, PostgreSQL on 1, off 0)가 적은 설정일수록 원자료의 처리량 중앙값이 크다. 장애가 나면 fsync를 기다리지 않은 로그의 기록만 잃는다.

모형 테스트가 잘못을 잡는지도 봤다. REPEATABLE READ도 문장마다 스냅숏을 만들게 바꾼 사본은 테스트 4개가, 이전 버전을 커밋만 보고 지우게 바꾼 사본과 MySQL UPDATE가 가장 오래된 버전 위에 쓰게 바꾼 사본은 각각 2개가 실패했다.

브라우저 확인은 Playwright 1.63.0과 Chromium 153.0.8010.12로 했다.

- 코드 줄과 연결선: 101개 구성(스냅숏을 만드는 때 16, 잔액 세 번 읽기 8, 잠그며 읽기 6, 동시 차감 8, 열어 둔 트랜잭션 24, InnoDB와 MyISAM 3, 커밋을 디스크에 36)의 모든 단계(878개)에서 세션이 실행한 줄과 다음 줄이 화면 SQL의 줄에 붙고, 이름표 수가 끝나지 않은 세션 수와 같다. 쥔 락과 기다림의 대상은 모두 관계도에 칸이 있고, 그 수만큼 선을 그린다. 선 하나를 빼거나 줄 키 하나를 바꾼 사본은 이 확인이 잡았다.
- 겹침: 878개 단계를 320, 360, 390, 480, 540, 600, 768, 1024, 1440px 폭에서 그렸다(7,902개 화면). 글자끼리 겹치지 않고, 세션 글줄은 세션 상자 안에, 버전 글자는 버전 상자 안에, 칸의 글자와 스냅숏 표시는 칸 안에, 칸은 표 상자 안에, 로그 칸 상자는 로그 상자 안에 있다. 가장 작은 글자는 11px이고 쪽 가로 넘침이 없다. 콘솔 오류와 경고가 없다. 버전 글자, 칸 머리, 로그 칸 글자를 크게 한 사본, 세션 글줄을 9px로 한 사본, 쪽을 넓힌 사본은 이 확인이 잡았다.
- GitHub Pages 경로: `docs/`를 로컬 서버의 `/cs-lab/` 아래에 두고 320, 390, 768, 1440px의 밝은 화면과 어두운 화면에서 열었다. 첫 화면의 링크 셋(01, 02, 03)으로 이 페이지가 열리고, 일곱 장면의 주소와 `index.html#deduct`가 제 장면으로 열리며, "복습 화면 목록"이 첫 화면으로 돌아간다. 접힌 칸을 모두 펼쳐도 쪽 가로 넘침이 없다. 같은 사이트 링크는 모두 `/cs-lab/` 아래이고 바깥 링크는 모두 https다. 실패한 요청, 바깥으로 나가는 요청, 콘솔 오류와 경고가 없다.
- 요소 설명: 장면마다 구성 한두 개의 모든 단계에서 고를 수 있는 요소 78개의 설명 칸을 열어 개념, 지금, 주요 특성, 근거가 모두 채워지는 것을 봤다.

링크 확인: 근거 링크 61곳 중 저장소 파일은 저장소에 있고, README 제목으로 가는 링크는 GitHub의 제목 주소 규칙(github-slugger)으로 만든 주소와 맞는다. 화면에 나오는 복습 카드 38장은 모두 카드 문서에 있다. MySQL 8.4 문서와 PostgreSQL 18 문서 링크는 확인한 환경에서 바로 열리지 않아 다른 경로로 페이지가 있는 것을 확인했다.
