# 조인 관계도

06 MySQL 조인과 SQL 실험을 복습하는 설명용 화면이다. 페이지 하나에 장면 넷을 두고, 장면마다 작은 표로 쿼리를 한 단계씩 따라간다. 단계마다 관계도(두 테이블과 결과, 또는 해시 테이블·인덱스, 또는 앱과 DB 사이의 왕복), 코드, 모든 단계를 한눈에 보는 띠가 같은 단계를 가리킨다. 2026-11-18에 만들었다.

화면의 단계는 설명용 모형(`model.js`)이 만든 순서다. 장면 1·2의 결과 행은 맥 본 측정(2026-11-17) 묶음 ①의 결과 행과 같고, 장면 3의 계획 모양(드라이빙·드리븐, 빌드·프로브)은 묶음 ②의 `EXPLAIN ANALYZE`와 같으며, 장면 4의 쿼리 수는 묶음 ③의 규칙과 같다(아래 "확인 결과"). 실측값은 "실험에서 잰 값" 칸에만 있고, 모두 [실험 README](../../experiments/06-mysql-joins/README.md)의 결과에서 옮겼다.

01~05 화면보다 작게 만들었다. 전체 지도, 요소를 눌러 여는 설명 칸, 재생 버튼은 두지 않았고, 관계도는 SVG가 아니라 HTML 표로 그렸다. 조인은 행과 행의 짝을 보는 것이라 표가 가장 읽기 쉽다고 봤다.

## 그림 규칙

[01 화면의 그림 규칙](../01-concurrency-models/README.md#그림-규칙)을 따른다. 아래는 이 화면에서 정하거나 바꾼 것이다.

- 테이블은 표 하나, 행은 줄 하나다. 위에 테이블 이름과 그 장면에서의 역할(왼쪽, 드라이빙, 드리븐, 빌드 입력, 프로브 입력)을 적는다.
- 지금 따지는 행은 굵은 파랑 테두리, 조건이 TRUE인 짝은 옅은 파랑, 읽고 비교했지만 짝이 아닌 행은 회색 글자와 `FALSE` 꼬리표, NULL과 비교해 UNKNOWN인 행은 옅은 주황과 `UNKNOWN` 꼬리표다. 결과 표에서 이 단계에 들어간 행은 옅은 파랑 굵은 글자, WHERE로 빠진 행은 줄을 긋는다.
- 3값 논리는 조건마다 `TRUE`·`FALSE`·`UNKNOWN`을 적고, NOT IN·IN은 목록의 값마다 비교를 늘어놓은 뒤 AND·OR로 묶은 값을 적는다.
- 색은 세 갈래다. 파랑은 지금 행과 TRUE·결과, 주황은 UNKNOWN, 나머지는 회색이다. 어두운 테마도 같다.
- 단계는 이벤트의 순서이고 시간 길이가 아니다. 사람이 적을 예상은 미리 채우지 않는다. "내 예상" 칸은 비워 두고, 적은 글은 그 브라우저에만 남는다.
- 좁은 화면에서는 표를 세로로 쌓아 옆으로 밀지 않는다.

## 화면 구성

위에서부터 장면 버튼, 먼저 생각해 볼 질문과 "내 예상" 칸, 구성 버튼, 단계 이동 막대(방향키, Home, End로도 옮김), 관계도와 설명 한 문장·개수 칸, 코드, 모든 단계 띠가 이어진다. 아래 접힌 칸에 볼 것, 실험에서 잰 값, 근거와 복습 카드가 있다. 주소 끝에 `#left`, `#semi`, `#algo`, `#n1`을 붙이면 그 장면으로 열린다.

| 장면 | 구성 | 보는 것 | 실험 README |
|---|---|---|---|
| 조인의 종류와 조건의 자리 | JOIN, LEFT JOIN, LEFT JOIN + WHERE, LEFT JOIN + ON, RIGHT JOIN, FULL OUTER(UNION) | 회원마다 짝을 찾고, 짝이 없을 때 NULL로 채우는지, WHERE가 결과 행에 적용될 때 UNKNOWN으로 빠지는 행 | 문제 상황 1, 질문 1·2 |
| 세미 조인·안티 조인과 NOT IN | IN, EXISTS, JOIN, NOT EXISTS, NOT IN, NOT IN + IS NOT NULL | 짝을 하나 찾으면 멈추는 EXISTS, 짝마다 행을 만드는 JOIN, 목록의 값마다 <>를 AND로 묶는 NOT IN | 문제 상황 1-1, 질문 4, 처음 보는 문제 2 |
| 조인 방식 | 해시 조인, 중첩 루프(인덱스 없음), 중첩 루프(idx_code) × 주문 전부, 주문 2건만 | 빌드·프로브, 드리븐 테이블을 끝까지 읽기, B+트리를 내려가 한 항목 읽기와 그 개수 | 문제 상황 2, 질문 5·6 |
| N+1 | N+1, JOIN 한 번, IN 두 번 × 회원 3·5·10명 × 왕복 0.277ms, 1ms | 쿼리마다 왕복 하나, 쿼리 수와 받은 행, 쿼리 수 × 왕복으로 셈한 왕복 합 | 문제 상황 3, 질문 7 |

## 모형의 가정

- 장면 1·2는 실험의 작은 표(회원 5명, 주문 5건, user_id에 NULL 한 건)를 그대로 쓴다. 관계도는 쿼리의 뜻대로 왼쪽 행(회원)부터 따진다. 실제 계획에서 LEFT JOIN + WHERE는 내부 조인으로 바뀌어 orders를 먼저 읽었고, IN·EXISTS도 orders를 먼저 읽었다. 이 차이는 코드 칸 아래 "실험의 계획"에 적었다.
- 장면 2의 EXISTS·NOT EXISTS는 짝을 하나 찾으면 그 회원에 대해 멈춘다(세미 조인·안티 조인의 동작). IN은 목록의 값마다 비교를 OR로 묶어 보였다.
- 장면 3은 회원 6명·주문 6건(code는 101~106의 순열)이다. 실험은 각 1만 행이다. 해시 조인의 빌드 쪽은 실험 계획을 따랐다. 주문 전부면 users로 빌드하고 orders로 프로브하며, 주문 2건만이면 작은 orders로 빌드하고 users로 프로브한다(실험은 10건). 중첩 루프(인덱스 없음)는 실험 (나)처럼 users가 드라이빙, orders가 드리븐이고, 중첩 루프(idx_code)는 실험 (다)처럼 orders가 드라이빙이다. idx_code는 루트 1장과 리프 2장의 2층으로 그렸다(실험의 1만 행은 2~3장을 내려감). "읽은 행"은 드라이빙 행과 드리븐에서 읽은 행을 더한 모형의 수이고, 실험의 `Handler_read_*`와 비교하지 않는다.
- 장면 4는 회원마다 주문 10건(실험과 같음)이다. "왕복 합"은 쿼리 수 × 왕복 시간이고, DB 안의 일과 행을 받는 시간은 넣지 않았다. 실험의 n = 1000에서 N+1의 399ms 가운데 왕복은 약 277ms였다.

## 확인 결과

`node --test model.test.cjs`(Node.js 18 이상, 따로 설치할 것 없음)로 아래 8개를 확인했다(2026-11-18, 모두 통과).

1. 원자료(`2026-11-17T164211743263-join`)의 모든 기록이 검증을 통과했다.
2. 장면 1의 JOIN·LEFT JOIN·LEFT JOIN + WHERE·LEFT JOIN + ON 결과가 원자료의 결과 행과 같다.
3. 장면 2의 IN·EXISTS·JOIN·NOT EXISTS·NOT IN 결과가 원자료의 결과 행과 같고, NOT IN + IS NOT NULL은 4, 5다.
4. 장면 1의 RIGHT JOIN과 FULL OUTER가 손으로 센 결과와 같다.
5. 3값 논리에서 NOT IN 목록에 NULL이 있으면 UNKNOWN이다.
6. 장면 3의 비교 수(6 × 6), 내려간 페이지 수(6 × 2), 빌드·프로브 수와, 원자료 계획의 모양((나) 안쪽 `Table scan on o … loops=10000`, (다) `index lookup on u using idx_code … loops=10000`, (가) users로 빌드, 주문 10건은 orders로 빌드)이 같다.
7. 장면 4의 쿼리 수가 원자료 묶음 ③의 쿼리 수(N+1은 n + 1, JOIN 1, IN 두 번 2)와 같은 규칙이다.
8. "실험에서 잰 값" 칸의 시간이 원자료의 중앙값과 같다. 이 점검에서 실험 README의 n = 10 JOIN 값을 0.84에서 0.836으로 바로잡았다(1 미만은 소수 셋째 자리로 적는 규칙).

브라우저에서는 장면 넷의 모든 구성(36개)을 데스크톱 폭(1024px)과 휴대폰 폭(375px)에서 처음과 끝 단계로 넘겨 보고, 콘솔 오류가 없고 페이지가 옆으로 밀리지 않는 것을 확인했다.
