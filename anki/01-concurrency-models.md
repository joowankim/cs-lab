## 실행 단위와 GIL

### 01-001

**앞면:** 동시성(concurrency)과 병렬성(parallelism)은 어떻게 다른가?

**뒷면:** 동시성은 여러 작업이 진행 중인 상태를 함께 다루는 것이고, 병렬성은 여러 작업이 같은 순간에 실제로 실행되는 것이다. 작업을 번갈아 실행하거나 대기를 겹치는 것으로도 동시성을 만들 수 있다.

**근거:** [실험의 개념 문답][experiment]

### 01-002

**앞면:** CPython의 `threading.Thread`로 시작한 스레드는 OS 스레드와 별개의 실행 단위인가?

**뒷면:** 아니다. `threading.Thread`는 OS 스레드를 사용하는 Python API다. CPython은 그 스레드에서 Python 코드를 실행하기 위한 스레드 상태를 함께 관리한다.

**근거:** [CPython 스레드 상태][gil]

### 01-003

**앞면:** 논리 CPU가 4개이면 OS 스레드를 10개 생성할 수 없는가?

**뒷면:** 자원이 허용하면 생성할 수 있다. 논리 CPU 수는 생성 가능한 스레드 수가 아니라 같은 순간에 CPU에서 실행할 수 있는 스레드 수의 한도와 관련된다. 나머지 스레드는 실행 순서를 기다리거나 대기 상태에 있을 수 있다.

**근거:** [스레드 수와 CPU 수에 대한 문답][experiment]

### 01-004

**앞면:** GIL을 켠 같은 CPython 인터프리터의 스레드 4개는 순수 Python 계산을 동시에 실행할 수 있는가?

**뒷면:** Python 바이트코드는 한 번에 한 스레드만 실행할 수 있다. 계산을 번갈아 진행할 수는 있지만 네 스레드가 그 계산을 병렬 실행하지는 못한다.

**근거:** [GIL과 Python 실행][gil]

### 01-005

**앞면:** CPython에서 서로 다른 인터프리터는 반드시 서로 다른 GIL을 사용하는가?

**뒷면:** 아니다. GIL을 켠 구성에서도 인터프리터가 자체 GIL을 쓰거나 메인 인터프리터의 GIL을 공유하도록 설정할 수 있다. 같은 인터프리터의 스레드들은 그 인터프리터에 연결된 GIL을 공유한다.

**근거:** [인터프리터의 GIL 설정][interpreters], [실험의 소스 조사][experiment]

### 01-006

**앞면:** GIL을 켠 일반 CPython에서 프로세스 4개가 각각 인터프리터 하나를 실행하면, 순수 Python 계산을 병렬 실행할 수 있는 이유는 무엇인가?

**뒷면:** 각 프로세스가 독립적인 인터프리터와 GIL을 사용하기 때문이다. 한 프로세스가 GIL을 가지고 있어도 다른 프로세스의 Python 실행을 막지 않는다. 실제 병렬 실행에는 사용할 CPU와 OS 스케줄링도 필요하다.

**근거:** [프로세스 비교의 코드와 결과][experiment]

### 01-007

**앞면:** free-threaded CPython 빌드로 실행했다는 사실만으로 GIL이 꺼져 있다고 판단할 수 있는가?

**뒷면:** 아니다. free-threaded 빌드도 GIL을 켜서 실행할 수 있다. 빌드 종류와 실제 실행 중 GIL 활성 상태를 구분해야 한다. 이번 실험은 실행 상태를 `sys._is_gil_enabled()`로 확인했다.

**근거:** [free-threading 설명][free-threading], [환경 기록 방법][experiment]

## 계산·대기 중 GIL의 동작

### 01-008

**앞면:** GIL을 켠 같은 CPython 인터프리터에서 스레드 A가 긴 순수 Python 계산을 하면, B는 A의 계산 전체가 끝나야 Python 계산을 시작할 수 있는가?

**뒷면:** 아니다. 계산 도중에도 GIL 교대가 일어날 수 있으므로 B는 A가 끝나기 전에 계산을 시작할 수 있다. 두 계산은 번갈아 진행한다.

**근거:** [GIL 교대 구현][gil-source]

### 01-009

**앞면:** CPython 3.14.2에서 GIL을 기다리는 B는 어떤 조건에서 보유 스레드 A에게 해제 요청을 표시하는가?

**뒷면:** 설정된 간격만큼 기다리는 동안 교대가 없고 GIL이 여전히 잠겨 있으면, B 쪽 CPython 내부 코드가 A의 스레드 상태에 GIL 해제 요청을 표시한다.

**근거:** [ceval_gil.c의 `take_gil()`][gil-source]

### 01-010

**앞면:** GIL을 가진 스레드가 해제 요청을 받으면 CPython은 계산을 어떻게 교대시키는가?

**뒷면:** 인터프리터가 반복문의 뒤로 이동하는 지점 같은 확인 지점에서 요청을 처리한다. GIL을 해제하고 대기 스레드에 신호를 보내며, 원래 스레드는 다시 GIL을 얻어야 Python 계산을 이어갈 수 있다. 사용자 코드에 `await`가 없어도 동작한다.

**근거:** [요청 처리와 GIL 해제][gil-source], [확인 지점][bytecodes]

### 01-011

**앞면:** `sys.getswitchinterval()`이 `0.005`이면 스레드가 정확히 5ms마다 교대하는가?

**뒷면:** 아니다. 교대에 사용하는 간격 설정이며 실제 교대 시각을 보장하지 않는다. 긴 내부 함수 실행과 요청 확인 시점, OS 스케줄링에 따라 교대가 늦어질 수 있다.

**근거:** [교대 간격 설명][switch-interval]

### 01-012

**앞면:** GIL을 켠 CPython에서 CPU 계산을 하는 스레드는 항상 GIL을 가지고 있어야 하는가?

**뒷면:** 아니다. Python 바이트코드 실행에는 GIL이 필요하지만, GIL을 명시적으로 해제한 네이티브 코드는 같은 OS 스레드에서 CPU 계산을 계속할 수 있다. C 함수를 호출한다는 사실만으로 GIL이 자동 해제되는 것은 아니다.

**근거:** [네이티브 코드에서 스레드 상태 분리][gil]

### 01-013

**앞면:** GIL을 켠 같은 CPython 인터프리터에서 여러 스레드의 `time.sleep()` 대기가 겹칠 수 있는 이유는 무엇인가?

**뒷면:** CPython의 `time.sleep()`이 호출 스레드를 대기시키면서 GIL을 해제하기 때문이다. 다른 스레드도 GIL을 얻어 실행하다가 자신의 대기에 들어갈 수 있다.

**근거:** [CPython의 sleep 구현][sleep-source]

### 01-014

**앞면:** GIL을 켠 CPython에서 `time.sleep()`의 대기 시간이 끝나면 해당 스레드는 곧바로 Python 코드를 실행할 수 있는가?

**뒷면:** Python 코드로 돌아가기 전에 GIL을 다시 획득해야 한다. 다른 스레드가 GIL을 가지고 있으면 추가로 기다릴 수 있다.

**근거:** [스레드 상태 복구와 GIL 재획득][gil]

## asyncio와 실행 위치

### 01-015

**앞면:** 이벤트 루프 스레드에서 실행하는 함수를 `async def`로 선언하면, 그 안의 긴 순수 Python 계산도 다른 Task와 자동으로 교대하는가?

**뒷면:** 아니다. 계산은 그 이벤트 루프 스레드에서 실행된다. Task가 실제로 실행을 중단하거나 완료하지 않으면 같은 루프의 다른 Task를 실행할 기회가 생기지 않는다.

**근거:** [이벤트 루프의 실행 방식][asyncio-threads], [CPU Task 실험][experiment]

### 01-016

**앞면:** `await` 표현식은 항상 현재 Task의 실행을 중단시키는가?

**뒷면:** 아니다. 이미 완료된 Future를 기다리는 등 즉시 결과를 얻을 수 있는 경우에는 중단 없이 이어서 실행할 수 있다. `await`의 존재와 실제 실행 중단을 구분한다.

**근거:** [실험의 `Future.__await__()` 확인 기록][experiment]

### 01-017

**앞면:** CPython 3.14.2에서 `await asyncio.sleep(1)`은 별도 작업자 스레드에 대기를 맡기는가?

**뒷면:** 아니다. 이벤트 루프에 타이머를 등록하고, 대기 완료를 나타내는 Future를 기다리며 현재 Task의 실행을 중단한다. 그동안 이벤트 루프는 다른 준비된 Task를 실행할 수 있다.

**근거:** [asyncio.sleep 구현][asyncio-sleep-source]

### 01-018

**앞면:** 같은 이벤트 루프의 Task A가 `time.sleep(1)`을 호출하면, GIL을 해제하는데도 Task B가 지연되는 이유는 무엇인가?

**뒷면:** A를 실행하는 OS 스레드 자체가 대기하기 때문이다. 이벤트 루프도 그 스레드에서 실행되므로 B를 재개하지 못한다. 다른 OS 스레드가 GIL을 얻을 수 있다는 것과 같은 루프의 Task 교대는 별개다.

**근거:** [이벤트 루프의 실행 스레드][asyncio-threads], [블로킹 대기 실험][experiment]

### 01-019

**앞면:** GIL을 끈 CPython에서도, 단일 이벤트 루프의 Task A가 중단 없이 긴 CPU 계산을 하면 Task B가 지연되는가?

**뒷면:** 지연된다. GIL을 꺼도 이벤트 루프를 실행하는 OS 스레드는 하나다. A가 실행을 중단하거나 완료해야 그 스레드가 다른 준비된 Task를 실행할 수 있다.

**근거:** [GIL 조건을 바꾼 학습 문답][experiment]

### 01-020

**앞면:** GIL을 켠 같은 CPython 인터프리터에서 A가 먼저 긴 순수 Python 계산을 시작했다. A에 `await`나 I/O가 없을 때, B가 A 완료 전에 시작할 수 있는 것은 어느 경우인가? ① OS 스레드 2개에서 각각 실행 ② 단일 루프 스레드의 Task 2개로 실행.

**뒷면:** ①이다. 스레드는 계산 중에도 GIL 교대로 번갈아 진행할 수 있다. ②에서는 GIL을 놓았다 다시 얻어도 실행하던 A의 계산을 이어가므로, 그것만으로 Task B를 실행하지 않는다.

**근거:** [최종 학습 문답][experiment], [GIL 교대 구현][gil-source]

### 01-021

**앞면:** Task 40개를 만들고 각 Task가 `async with asyncio.Semaphore(4)` 안에서 작업하도록 했다. 여기서 4는 무엇의 상한인가?

**뒷면:** 세마포어를 획득해 보호 구간 안에서 아직 완료하지 않은 작업 수의 상한이다. Task의 총개수나 OS 스레드 수가 아니다.

**근거:** [실험의 실행 함수][models], [Semaphore 설명][semaphore]

### 01-022

**앞면:** 각각 0.1초 기다리는 독립 작업 40개를 최대 4개씩 겹쳐 실행하면, 부대비용을 무시한 전체 시간은 얼마인가?

**뒷면:** 약 `40 ÷ 4 × 0.1 = 1초`다. 작업이 끝나 자리가 나면 다음 작업이 시작할 수 있다. 반드시 네 작업이 모두 끝나야 다음 묶음을 시작한다는 뜻은 아니다.

**근거:** [동시 대기 상한과 전체 시간에 대한 문답][experiment]

## 공유 상태와 락

### 01-023

**앞면:** 초기 카운터가 0이다. 두 스레드가 모두 0을 각자의 지역 변수에 읽어 둔 뒤, 각각 `읽은 값 + 1`을 저장했다. 두 호출이 완료됐는데 최종값이 1인 이유는 무엇인가?

**뒷면:** 두 스레드 모두 같은 이전 값 0을 기준으로 1을 저장해 증가 한 번이 유실됐다. 두 저장이 차례로 실행돼도 이 문제가 발생한다.

**근거:** [카운터 실험][experiment], [카운터 코드][counter]

### 01-024

**앞면:** GIL을 켠 CPython에서 공유 카운터의 증가가 읽기·계산·저장으로 나뉘어 있다. 저장 부분에만 락을 걸면 충분한가?

**뒷면:** 충분하지 않다. 두 작업이 갱신 전의 같은 값을 읽을 수 있으므로, 같은 락으로 읽기부터 계산·저장까지 전체 구간을 보호해야 한다. GIL은 이 일련의 작업 전체를 하나로 묶어 보호하지 않는다.

**근거:** [수정한 카운터 함수][counter]

### 01-025

**앞면:** `with lock:` 안에서 `return`하거나 예외가 발생하면 락은 어떻게 되는가?

**뒷면:** 블록을 벗어나면서 락이 해제된다. 정상 경로에서만 `release()`를 직접 호출하는 코드와 달리 예외 경로에서도 해제한다.

**근거:** [카운터·싱글톤 수정본의 예외 검사][experiment], [락의 with 문 지원][lock-with]

### 01-026

**앞면:** 초기 `state.instance`는 `None`이고 두 스레드가 같은 락을 사용한다. 다음 코드가 객체를 한 번만 생성하도록 보장하지 못하는 이유는 무엇인가?

```python
if state.instance is None:
    with lock:
        state.instance = factory()
```

**뒷면:** 두 스레드가 첫 저장 전에 `None` 검사를 통과하면, 락을 차례로 얻어 각각 생성할 수 있다. 검사부터 생성·저장까지 같은 락으로 보호하면 뒤의 요청은 이미 저장된 객체를 확인한다.

**근거:** [싱글톤 변형 문제와 답][experiment], [수정한 싱글톤 함수][singleton]

### 01-027

**앞면:** 경쟁 상태가 의심되는 코드를 1,000회 실행했지만 모두 정상 결과였다. 이것만으로 안전성을 보장할 수 있는가?

**뒷면:** 보장할 수 없다. 문제가 생기는 실행 순서가 이번 반복에서 나타나지 않았을 수 있다. 코드가 허용하는 순서와 공유 락의 적용 범위를 함께 확인해야 한다.

**근거:** [오류 미재현의 한계에 대한 학습 문답][experiment]

## 실행 방식과 추가 비용

### 01-028

**앞면:** 실제 실험에서 GIL을 켠 일반 CPython으로 N=200,000의 소수 계산 8개를 처리했다. 작업자 4개일 때 중앙값은 스레드 1.610381초, 프로세스 0.495228초였다. 전체 시간을 줄이기 위해 선택할 방식은 무엇인가?

**뒷면:** 이번 조건에서는 프로세스다. 독립적인 인터프리터와 GIL로 순수 Python 계산을 병렬 실행할 수 있고, 실제 전체 시간도 더 짧았다. 모든 작업 크기에서 더 빠르다는 뜻은 아니다.

**근거:** [CPU 비교 원자료][cpu-data], [실험 환경과 집계][experiment]

### 01-029

**앞면:** 독립적인 CPU 작업 8개를 유지한 채 프로세스를 4개에서 8개로 늘리면 전체 시간이 반드시 절반이 되는가?

**뒷면:** 아니다. 사용할 CPU, 스케줄링, 작업자 생성·전달 등의 비용에 영향을 받는다. 이번 실험에서도 큰 작업은 빨라졌지만 작은 작업은 더 느려졌다. 총작업량은 여전히 8개다.

**근거:** [작업자 4개·8개 비교 원자료][cpu-data]

### 01-030

**앞면:** 병렬 처리에 추가 비용이 생길 때, 속도 이득을 판단하려면 추가 비용을 무엇과 비교해야 하는가?

**뒷면:** 병렬화로 절약한 시간과 비교한다. 단순한 모델에서 `추가 비용 < 순차 계산 시간 − 병렬 계산 시간`이면 전체 시간이 줄어든다. 추가 비용이 순차 계산 전체보다 작다는 조건만으로는 충분하지 않다.

**근거:** [추가 비용 해석의 피드백][experiment]

### 01-031

**앞면:** 가상의 조건에서 순차 계산은 100ms, 병렬 계산은 70ms, 병렬 방식의 추가 비용은 40ms다. 어느 방식이 더 빠른가?

**뒷면:** 순차 방식이 더 빠르다. 병렬 방식은 `70 + 40 = 110ms`이고, 절약한 30ms보다 추가 비용 40ms가 크기 때문이다. 이 숫자는 실측값이 아니다.

**근거:** [학습 확인의 가상 예][experiment]

### 01-032

**앞면:** 가상의 예에서 프로세스 방식의 전체 시간이 순차 실행보다 40ms 길었다. 프로세스 생성에 40ms가 걸렸다고 결론 내릴 수 있는가?

**뒷면:** 결론 내릴 수 없다. 두 전체 시간의 차이에는 계산 시간의 변화와 생성·작업 전달·결과 수집·종료 등 여러 효과가 함께 들어 있다. 생성 시간만 알려면 별도 측정이 필요하다. 문제의 40ms는 가상 값이다.

**근거:** [측정 구간과 원인 추정에 대한 피드백][experiment]

### 01-033

**앞면:** 실제 N=20,000 실험에서 순차 실행은 0.075601초, 프로세스 4개는 0.118923초였다. 작은 작업에서 프로세스가 더 느린 이유를 어떻게 해석할 수 있는가?

**뒷면:** 병렬화로 절약한 시간보다 추가 비용이 더 컸던 것으로 추정할 수 있다. 더 느렸다는 것은 실측 사실이지만, 각 비용을 따로 재지 않았으므로 생성 시간이 계산 시간보다 길었다고 확정할 수는 없다.

**근거:** [CPU 비교 원자료][cpu-data], [수정한 해석과 그 한계][experiment]

### 01-034

**앞면:** 실제 대기 실험에서 GIL을 켠 일반 CPython으로 `time.sleep(0.1)` 작업 40개를 실행했다. 스레드 4개는 1.036234초, 프로세스 4개는 1.167388초였다. 두 방식 중 이번 전체 시간 기준으로 선택할 방식은 무엇인가?

**뒷면:** 스레드다. 이번 측정에서 더 짧은 전체 시간을 보였다. 다만 시간 차이 전체를 프로세스 생성 비용으로 단정하거나, 측정하지 않은 메모리 효율까지 결론 내리지는 않는다.

**근거:** [I/O 비교 원자료][io-data], [사람의 선택과 피드백][experiment]

### 01-037

**뒷면:** `1.0 − 0.1 = 0.9초`다. 시작부터 재개까지의 시간 1.0초와 예정 시각을 넘긴 지연 0.9초를 구분한다. 이 값은 설명용 조건이다.
