# 05 MySQL 인덱스와 실행 계획

100만 행 주문 표 하나로 보조 인덱스 조건마다 같은 쿼리의 실행 계획(`EXPLAIN`)과 실제 실행(`EXPLAIN ANALYZE`)을 보고, 읽은 행 수와 버퍼 풀에서 읽은 페이지 수로 B+Tree 구조를 설명한다. 인덱스가 있어도 쓰이지 않는 쿼리, 최신순 목록의 정렬과 OFFSET·커서 페이지네이션을 보고, 보조 인덱스 수와 기본 키 종류(AUTO_INCREMENT, UUIDv4, UUIDv7)에 따른 쓰기 비용(INSERT 시간, 페이지 분할, 인덱스 크기)을 버퍼 풀 크기를 바꿔 가며 잰다. MySQL에서만 한다. 공통 규칙은 [작업 지침](../../AGENTS.md)을 따른다.

2026-11-09에 목표와 범위를 정했고, 2026-11-09~11에 문제 상황마다 측정 전 예상을 받았다. 문제 상황마다 클라우드 컨테이너에서 임시로 돌린 값으로 피드백하고 해석을 물었으며, 2026-11-11에 맥에서 본 측정을 했다. 시작 전 기록은 측정 전의 예상과 그 뒤의 문답이고, 맥 측정값과 판정은 [결과 정리](#결과-정리)에 있다. 2026-11-12~14에 학습 확인을 했고, 그 문답은 [완료 후 학습 확인](#완료-후-학습-확인)에, 정리한 결론은 [정리한 결론과 선택 기준](#정리한-결론과-선택-기준)에 있다.

복습할 때는 [앞면·뒷면으로 정리한 카드](../../anki/05-mysql-indexes-explain.md)와 [복습 화면](https://joowankim.github.io/cs-lab/05-mysql-indexes-explain/)을 쓴다.

## 목표

실험을 마치면 다음을 할 수 있어야 한다.

1. **예측:** 표·인덱스·쿼리를 보고 `EXPLAIN`의 `type`·`key`·`rows`·`Extra`와 걸린 시간의 크기(몇 ms대인지)를 실행 전에 맞힌다.
2. **설명:** 실행 계획을 B+Tree 구조(클러스터형 인덱스와 보조 인덱스의 리프에 무엇이 어떤 순서로 있는지, 페이지 16KB와 팬아웃으로 정해지는 층 수, 보조 인덱스에서 클러스터형 인덱스로 다시 찾아가기)와 읽은 행·페이지 수로 설명한다. 층 수를 페이지 크기와 키 크기로 셈하고 실제 값과 견준다.
3. **고르기:** 복합 인덱스의 칼럼 순서, 커버링 인덱스를 둘지, 인덱스를 몇 개 둘지(쓰기 비용), 페이지네이션 방식, 기본 키 종류(AUTO_INCREMENT·UUIDv4·UUIDv7)를 직접 잰 숫자(읽은 행 수, 걸린 시간, INSERT 시간, 인덱스 크기)로 고른다.

확인 방법은 03·04와 같다. 측정 전에 적은 예상을 실측과 대조해 맞힌 수를 센다. 완료 후에는 아래 질문 11개에 해설 없이 답하고, 직접 잰 숫자를 넣어 답한 수와 "왜?"에 두 번까지 답한 수를 센다. 목표값은 두지 않고 03(예상 31/63, 숫자를 넣어 혼자 답한 질문 1/9)·04(40/57, 3/8)의 값과 나란히 기록한다. 이번에는 질문마다 답하기 전에 맞힐 것 같은지를 한 줄로 먼저 말한다.

### 확인할 질문

1. 인덱스란 무엇이고 왜 빠른가.
2. B-Tree, B+Tree, 해시 인덱스는 무엇이 다르고, DB 인덱스는 왜 대부분 B+Tree인가.
3. 트리의 층 수는 왜 낮은가(페이지 크기와 팬아웃).
4. 인덱스의 비용은 무엇인가(쓰기 때 갱신, 두 번 읽기, 크기).
5. 클러스터형 인덱스와 보조 인덱스는 무엇이 다른가. 보조 인덱스의 리프에는 무엇이 있는가.
6. 복합 인덱스의 칼럼 순서는 어떻게 정하는가.
7. 커버링 인덱스란 무엇인가.
8. 인덱스가 있어도 쓰이지 않는 경우는 언제인가(함수, 묵시적 형변환, `LIKE '%x'`, TEXT 칼럼).
9. `EXPLAIN`에서 전체 읽기, 범위 읽기, `rows`를 어떻게 읽는가.
10. 인덱스로 정렬을 생략하는 것은 언제 되는가. OFFSET과 커서 페이지네이션은 무엇이 다른가.
11. 기본 키로 UUID를 쓰면 어떻게 되는가(AUTO_INCREMENT·UUIDv7과 비교).

사람의 답은 원문 그대로 옮겼다(메시지의 줄 바꿈은 번호 앞에서는 띄어 쓰고 그 밖에서는 " / "로 적음). 문답 중 에이전트가 처음에 쓴 "페이지 요청"은 논리적 읽기(logical read, `Innodb_buffer_pool_read_requests`), "디스크 읽기"는 물리적 읽기(physical read, `Innodb_buffer_pool_reads`)와 같은 뜻이고, 페이지 수를 세는 말로 섞어 쓴 "쪽"은 페이지와 같다(2026-11-11에 표준 용어로 맞춤). 에이전트의 글은 표준 용어로 고쳐 적었고 사람의 원문은 그대로 두었다. 옵티마이저가 내놓은 숫자는 추정, 에이전트가 확인하지 못한 설명은 추측으로 적는다.

### 지난 실험의 변형 문제 (2026-11-09)

- 문제(에이전트): 04의 "다시 확인할 내용"인 클러스터형 인덱스의 정렬 기준과 갭 락을 묻는다. 표 `orders (id BIGINT PRIMARY KEY AUTO_INCREMENT, user_id INT NOT NULL, amount INT NOT NULL, KEY idx_user (user_id))`에 (id, user_id, amount) = (1, 7, 100) (2, 3, 200) (3, 7, 300) (4, 12, 400) (5, 3, 500) (6, 7, 600)을 이 순서로 넣었다. (1) `PRIMARY` 리프에 행이 놓이는 순서를 (id, user_id)로 (2) `idx_user` 리프의 항목마다 들어 있는 것과 순서 (3) REPEATABLE READ에서 A가 `START TRANSACTION; SELECT * FROM orders WHERE user_id = 7 FOR UPDATE;`를 하고 둔 뒤 B가 `INSERT INTO orders (id, user_id, amount) VALUES (7, 5, 700);`을 하면 기다리는지와 까닭.
- 사람의 답(원문): "1. (1, 7) (2, 3) (3, 7) (4, 12) (5, 3) (6, 7) 2. user_id, id가 들어있어. user_id의 오름차순으로 정렬되어서 저장되: (3, 2), (3, 5), (7, 1), (7, 3), (7, 6), (12, 4) 3. RR에서는 현재 SELECT 문이 조회 중인 행 (7, 1) 앞의 갭부터 (12, 4) 앞의 갭까지 모두 배타락 모드로 락이 걸리기 때문에 (3, 5)와 (7, 1) 사이의 삽입 의도락을 요청했다가 갭락과 충돌한 트랜잭션 B는 대기 상태에 돌입해."
- 에이전트 피드백: 셋 다 맞다. 컨테이너에서 A의 `data_locks`는 `idx_user`에 `X` (7, 1)·(7, 3)·(7, 6)과 `X,GAP` (12, 4), `PRIMARY`에 `X,REC_NOT_GAP` 1·3·6이었고, B는 `idx_user` (7, 1)에 `X,GAP,INSERT_INTENTION` WAITING으로 기다렸다. 1은 행이 id 순서로 들어가 "들어간 순서"로 답해도 같은 답이 나오는, 정렬 기준을 가려내지 못하는 문제였다. 3에서 (7, 1) 앞의 갭을 잠근 것은 따로 걸린 갭 락이 아니라 (7, 1)의 넥스트 키 락의 갭 부분이다.
- 이어서 낸 물음: (가) 같은 표를 비우고 id를 직접 지정해 (9, 4, 100), (2, 8, 200), (5, 4, 300) 순서로 넣으면 두 리프의 순서는 (나) 3번에서 A가 `FOR UPDATE` 대신 `FOR SHARE`로 읽으면 B는 기다리는가, 까닭은.
- 사람의 답(원문): "(가) PRIMARY: (2, 8, 200), (5, 4, 300), (9, 4, 100) idx_user: (4, 5), (4, 9), (8, 2) (나) 기다리지 않아. RR 격리수준에서 공유락을 사용하면 해당 시점의 read view를 참조해서 데이터를 조회해. 그래서 배타락을 사용하는 insert 문과는 충돌하지 않기 때문이야."
- 에이전트 피드백: (가)는 맞다. 04에서 두 번 놓친 클러스터형 인덱스의 정렬 기준을 이번에는 가려서 답했다. (나)는 빗나갔다. `FOR SHARE`는 스냅숏을 읽는 일관된 읽기가 아니라 최신 버전을 읽고 `S` 락을 거는 잠금 읽기다. 컨테이너에서 A의 락은 모드만 `S`로 바뀌었고 B는 같은 자리에서 기다렸다. 이 표를 보이고 락을 걸었는지와 그래도 기다린 까닭을 다시 물었다.
- 사람의 답(원문): "1. 락을 걸었네. 2. 공유락 모드에서도 갭락과 삽입 의도락은 서로 충돌해서 그런가봐. 이건 스냅샷이랑은 관련이 없나?" 둘 다 맞다. 갭 락은 `S`든 `X`든 똑같이 삽입 의도 락과 충돌한다. 질문에는 같은 REPEATABLE READ 트랜잭션 안에서 평범한 `SELECT`와 `FOR SHARE`를 번갈아 돌린 컨테이너 확인으로 답했다. B가 id 1을 150으로 고치고 (8, 7, 800)을 넣어 커밋한 뒤, A의 평범한 `SELECT`는 100과 user_id 7의 1·3·6을, `FOR SHARE`는 150과 1·3·6·8을 읽었다. 평범한 읽기는 스냅숏을, 잠금 읽기는 최신 버전을 읽고 락을 건다.
- 사람의 질문(원문): "공유락은 평범한 읽기라고 오해했어. 그럼 공유락과 배타락은 어떤 차이가 있는거야?" 에이전트는 둘 다 락이고, 차이는 같은 레코드에 다른 트랜잭션의 락과 함께 보유할 수 있는지(S와 S는 호환, S와 X, X와 X는 충돌) 하나라고 설명했다. READ COMMITTED·REPEATABLE READ의 평범한 `SELECT`는 락을 요청하지 않는다.
- 셈: 처음 답 3/3(1은 가려내지 못한 문제), 이어서 낸 물음 1/2. 실험 5의 예상 적중에는 넣지 않았다.
- 확인한 부분: 클러스터형 인덱스와 보조 인덱스의 정렬 기준은 혼자 가려 답했다. 잠금 읽기와 일관된 읽기의 구분(04 질문 1과 같은 내용), 갭 락의 모드와 삽입 충돌은 학습 확인에서 다시 묻는다.

### 문제 상황 1: 느려진 "내 최근 주문" 화면 (2026-11-09)

- 표: `orders (id BIGINT PRIMARY KEY AUTO_INCREMENT, user_id INT NOT NULL, status VARCHAR(10) NOT NULL, amount INT NOT NULL, phone VARCHAR(20) NOT NULL, memo TEXT NOT NULL, created_at DATETIME NOT NULL)`. 실험 내내 쓰는 표다.
- 데이터: 100만 행이 시간 순서대로 들어 있다(id 1이 가장 오래됨). created_at은 2025-11-10 ~ 2026-11-09에 고르게, user_id 1은 기업 고객이라 5만 건, 나머지 95만 건은 user_id 2 ~ 100,000에 고르게(평균 9.5건) 있다. status는 paid 90%, cancelled 7%, refunded 3%다. 버퍼 풀은 1GB이고 표 전체가 메모리에 올라간 상태다.
- 쿼리: `SELECT created_at, amount FROM orders WHERE user_id = 4242 AND created_at >= '2026-08-10';`("최근 3개월 내 주문")
- 경우(`PRIMARY` 말고는 그 인덱스 하나만): (가) 없음 (나) `CREATE INDEX idx_user ON orders (user_id);` (다) user_id 앞 복합 (라) created_at 앞 복합 (마) 이 쿼리가 클러스터형 인덱스를 다시 읽지 않고 끝나게 하는 인덱스. (다)(라)(마)는 사람이 쓴다.
- 물은 것: 처음에는 경우마다 `type`·`rows`·`Extra`와 `EXPLAIN ANALYZE` 시간의 크기를 물었다. 사람이 (다)(라)를 적은 뒤 "(마) 모르겠어. 2. EXPLAIN이 뭐야? 아예 모르겠어."라고 해서, 에이전트가 변형 문제의 6행 표로 `EXPLAIN`(실행하지 않고 옵티마이저가 고른 계획을 보임)과 `EXPLAIN ANALYZE`(실행까지 해서 단계마다 실제 행 수와 시간을 붙임)를 보여 설명하고, 예상을 경우마다 읽는 행 수의 크기와 걸린 시간의 크기 두 칸으로 줄였다. (마)는 특별한 문법이 있느냐는 물음에 "보통의 `CREATE INDEX`에 넣는 칼럼만 다르다, 쿼리가 쓰는 칼럼과 (다) 인덱스 리프의 칼럼을 견줘 빠진 것을 찾으라"는 힌트를 준 뒤 받았다.
- 사람의 예상과 이유(원문): (다)(라) "1. (다) CREATE INDEX (user_id, created_at) (라) CREATE INDEX (created_at, user_id)", (마)와 크기 "1. ### 문제 상황 1-2: 100만 행의 클러스터형 인덱스는 몇 층일까 (2026-11-10)

- 준 숫자: 페이지 16KB, 항목을 담는 공간 약 15KB(15,360바이트). 리프 항목은 행 전체로 머리말까지 약 100바이트, 루트·중간 항목은 키 id 8 + 자식 페이지 번호 4 + 항목 머리말 5 = 약 17바이트. 루트는 한 장이고, 루트가 가리킬 수 있는 수보다 리프가 많으면 중간 층이 생긴다.
- 물은 것: (1) 리프 한 장의 행 수와 100만 행의 리프 수 (2) 루트·중간 한 장이 가리킬 수 있는 자식 수 (3) 층 수(100만 행, 1억 행) (4) 1-1의 "항목 하나에 약 4번"을 층 수로 설명.
- 사람의 답(원문): "1. 리프 한 장이 페이지 한 장이라면 약 150개의 행이 들어가. 100만 행이면 약 6666장의 리프로 구성될거야. 2. 약 900장을 가리킬 수 있어. 16000 / 17 3. 밑이 900, 값이 6666인 로그 올림 = 2층, 1억 행이면 밑이 900이고 값이 666666인 로그 올림 = 2층 4. user_id 인덱스를 타고 탐색할 때 1번 id를 가지고 클러스터형 인덱스를 타고 탐색하는 1번에 2층을 곱해서 4번의 페이지를 요청했다고 생각해."
- 에이전트 피드백: 컨테이너에서 `FLUSH TABLES orders FOR EXPORT` 뒤 `orders.ibd`를 페이지마다 읽었다. `PRIMARY` 루트는 PAGE_LEVEL 2·레코드 8, 그 아래 중간 페이지 8장(레코드 합 6,303, 꽉 찬 장은 928), 리프 6,303장(한 장 평균 158.7행, 최대 165)이라 루트에서 리프까지 3장이다. `idx_user`는 루트 PAGE_LEVEL 2, 리프 1,078장(한 장 평균 927.6 항목)이었다. 1·2는 맞았다(6,666 대 6,303, 900 대 928). 3은 셈법이 맞지만 리프 층을 빼먹었다. 밑 900 로그 올림 2는 리프 위의 층 수이고, 루트에서 리프까지는 2 + 1 = 3이다. 100만 행과 1억 행의 층 수가 같다는 결론은 맞다(주어진 숫자로 3층은 약 1.2억 행, 4층은 약 1,100억 행까지). 문제 상황 1의 "로그 연산이라 1000 정도"의 로그가 이 층 수에 붙는다. 4는 숫자가 맞고 셈이 달랐다. 클러스터형 인덱스로 행 하나를 찾는 데 3번이었고(`id = 상수` 3번, `IN` 두 개 6번, 열 개 30번, 무작위 1,000개 3,192번), 보조 인덱스는 처음 한 번만 루트에서 내려가고 리프를 옆으로 읽는다(`COUNT(*)` 5만 항목에 77번). 1-1 (나)를 다시 돌리면 5만 항목에 201,286번(항목당 4.03)이라, 클러스터형 인덱스 3번에 보조 인덱스에서 약 1번(클러스터형 인덱스에 다녀와 보조 인덱스 리프의 제자리를 다시 여는 몫, 추측)을 더한 값이다.
- 예상 적중(컨테이너 기준): 2/3(리프 수, 자식 수). 1억 행의 층 수는 셈만 했고(재지 않음, 주어진 숫자로도 실측한 158.7·928로도 3층) 4는 설명이라 셈에서 뺐다.

(다)는 2번 답에서 결과를 보기 전에 "다 읽는다"로 고쳐 고친 답으로 셌다. (마)는 실패는 맞고 까닭이 달랐다. (라)는 자동형변환을 한 걸로 보이고 (나)는 INT로 읽어서 1009234282로 읽히지 않았을까 추정만 할 수 있어. 이유는 모르겠어. 3. `SELECT id, amount FROM orders WHERE created_at = DATE('2026-08-10');` `SELECT id, amount FROM orders WHERE phone = '01009234282';`" 컨테이너에서 (나) 고친 판은 `ref`·`idx_phone`·1행·0.008~0.010ms로 맞았다. (가)는 하루치 행이 리프에 붙어 있어도, 옵티마이저가 "칼럼 그대로 대 상수" 꼴만 범위로 바꾸고 함수가 순서를 지키는지는 따지지 않는다(요일 함수처럼 순서를 지키지 않는 함수도 있다). 2는 (라)가 상수를 정수로 한 번 바꾼 것이고(`user_id = 4242`), (나)는 숫자로 읽혔다는 추측이 맞다. 문자열과 숫자를 비교하면 둘 다 숫자로 바꿔 행마다 phone을 바꿔야 하고, 같은 숫자가 되는 다른 문자열('1009234282', '01009234282.0' 등)이 문자열 순서에서 떨어져 있어 범위를 정하지 못한다(Note 1739). 칼럼에 함수·형변환이 걸리면 범위를 못 정하고, 상수가 바뀌는 것은 괜찮다. 작은 힌트(created_at은 그대로 두고 상수로 하루 구간을 만들기) 뒤 사람(원문): "`SELECT id, amount FROM orders WHERE created_at >= DATE('2026-08-10') and created_at < DATE('2026-08-11');`" 맞았다. 컨테이너에서 `range`·`idx_created`·rows 2,831·`Using index condition`·2.55~3.94ms, 결과는 원래 (가)와 건수·id 합·amount 합이 같았다(같은 판에서 원래 (가) 175~176ms). `DATE()`가 상수에 걸려 괜찮고, 문자열 상수만 써도 같은 계획이다. 쿼리를 고칠 수 없을 때는 함수 인덱스 `((DATE(created_at)))`(MySQL 8.0.13부터)로 원래 (가)가 `ref`·2.41~2.53ms였고, 대신 쓰기마다 고칠 인덱스가 하나 는다.

### 문제 상황 2: 최신순 주문 목록 20개 (2026-11-11)

- 장면: 같은 표·데이터·버퍼 풀, 경우마다 보조 인덱스는 하나만. 관리자 전체 목록 `SELECT id, user_id, amount, created_at FROM orders ORDER BY created_at DESC LIMIT 20;` (가) 보조 인덱스 없음 (나) `idx_created (created_at)`. 고객 1의 내 주문 `SELECT id, amount, created_at FROM orders WHERE user_id = 1 ORDER BY created_at DESC LIMIT 20;` (다) `idx_user (user_id)` (라) `idx_user_created (user_id, created_at)`. "정렬을 따로 한다"는 인덱스 순서를 쓰지 못해 읽은 행을 모아 직접 정렬하는 것이고, `EXPLAIN` Extra의 `Using filesort`(메모리 안에서 끝나기도 함)라고 알렸다.
- 물은 것: (1) 경우마다 실제로 읽는 행(인덱스 항목) 수 (2) 정렬을 따로 하는지(`Using filesort`) (3) 이유. 행 수는 실제의 10분의 1 ~ 10배 안이면 맞힘이고, 판정은 `EXPLAIN ANALYZE`의 실제 행 수와 `Handler_read_*`로 한다(`EXPLAIN`의 ref 추정 rows는 LIMIT을 반영하지 않음).
- 사람의 예상과 이유(원문): "1. 100만 행, 인덱스가 없어서 전체 행을 정렬한 후에 20행을 조회함 / 160행(1페이지), 이미 인덱스로 정렬되어 있어서 한 페이지에 해당하는 행만 조회함 / 5만 행, created_at 인덱스는 없어서 user_id가 1인 행을 모두 조회한 후 정렬함 / 160행, created_at 이 인덱스 컬럼에 포함되어 있어서 한 페이지만 조회함. 1. 따로 함, 인덱스가 없어서 정렬이 필요함 / 따로 하지 않음, 인덱스 존재 / 따로 함, 인덱스 없음 / 따로 하지 않음, 인덱스 존재"(둘째 "1."은 2번 답)
- 에이전트 피드백: 컨테이너에서 (가) `ALL`·`Using filesort`·240~283ms, `Handler_read_rnd_next` 1,000,001, 논리적 읽기 약 7,473 (나) `index`·`idx_created`·`Backward index scan`·0.029~0.035ms, `Handler_read_last` 1·`Handler_read_prev` 19, 논리적 읽기 87 (다) `ref`·`idx_user`·`Using filesort`·55.7~83.0ms, `Handler_read_next` 50,000, 논리적 읽기 200,073 (라) `ref`·`idx_user_created`·`Backward index scan`·0.81~0.87ms, `Handler_read_key` 1·`Handler_read_prev` 19, 논리적 읽기 3,448이었다. 이유의 줄기는 다 맞았다. 다듬을 곳은 셋이다. (나)(라)는 한 페이지가 아니라 LIMIT 20을 채우면 멈추고(Handler 20번), 오름차순 인덱스를 리프의 앞뒤 연결로 거꾸로 읽는다. (가)(다)의 정렬은 전부를 줄 세우지 않고 최신 20개만 쥐고 읽는다(트리의 "limit input to 20 row(s) per chunk"). 그래도 다 읽어서 느리고, (다)는 5만 번 클러스터형 인덱스를 다시 찾는다. (라)가 (나)보다 25배쯤 느린 것은, 서버가 ref의 추정 행 수(100,652, LIMIT을 반영하지 않음)로 레코드 버퍼(최대 128KB) 크기를 정해 InnoDB가 첫 읽기 때 약 850행을 클러스터형 인덱스까지 미리 읽기 때문으로 봤다(추측, 소스는 확인하지 않음). 논리적 읽기 3,448은 LIMIT 1·20·200, 정순·역순에서 같았고, 커버링이면 21이었으며, 읽는 마지막 칼럼에 따라 status 9,917·amount 9,221·phone 3,819·created_at 3,447로 128KB ÷ 레코드 앞부분 길이 × 4와 맞았다.
- 예상 적중(컨테이너 기준): 8/8((가)(다)의 행 수, (나)(라)의 160은 실제 20의 8배라 10배 안).
- 확인한 부분: 인덱스 순서가 ORDER BY와 맞으면 정렬 없이 앞에서 멈춘다는 것과, 같은 값으로 찾는 칼럼 다음에 정렬 칼럼이 오는 인덱스((라))를 혼자 맞혔다. LIMIT에서 멈추는 단위(행)와 페이지를 섞었다.

### 문제 상황 2-1: 5,001번째 목록 페이지, OFFSET과 커서 (2026-11-11)

- 장면: 페이지 번호로 넘기는 관리자 화면이다(여기서 페이지는 20행씩 보여 주는 목록 페이지다). n번째 페이지는 `OFFSET (n-1) × 20`이고, 보조 인덱스는 `idx_created (created_at)` 하나다. (가) `SELECT id, user_id, amount, created_at FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 100000;` (나) 커서 방식(어디까지 봤는지 기억해 그다음부터). 5,000번째 페이지의 마지막 행은 `created_at = '2026-10-04 10:09:05'`, `id = 900001`이다.
- 물은 것: (1) (가)의 실제로 읽는 행 수와 정렬을 따로 하는지, 이유 (2) (나) 쿼리를 사람이 쓴다((가)와 같은 20행을 같은 순서로, 쓴 문장 그대로 잼) (3) (나)가 읽는 행 수.
- 사람의 예상과 이유(원문): "1. 20행, 정렬은 따로 안해, created_at 인덱스가 이미 있으니까. 2. `SELECT id, user_id, amount, created_at FROM orders WHERE created_at < '2026-10-04 10:09:05' ORDER BY created-at LIMIT 20;` 3. created_at 인덱스가 있으니까 20행만 읽을거라 생각해"
- 에이전트 피드백: 컨테이너에서 (가)는 `ALL`·`Using filesort`·346~397ms, 트리 "limit input to 100020 row(s) per chunk", `Handler_read_rnd_next` 1,000,001이었다. `FORCE INDEX (idx_created)`로 쓰게 하면 `index`·`Backward index scan`·131~159ms, `Handler_read_prev` 100,019, 논리적 읽기 401,307이었다. OR 꼴은 5,001번째와 170번째 모두 OFFSET과 같은 행이고, `idx_created`에서 20개만 읽어 1.2~2.1ms였다(OFFSET의 346~397ms보다 약 200배 빠르고 페이지 번호와 상관없음). 보조 인덱스 리프가 (created_at, id) 순서라 이 조건이 경계 앞부터 이어진 한 구간이 된다.

MySQL 8.4 옵티마이저는 이 행 생성자 비교로 범위를 만들지 못해(1-3의 "칼럼 그대로 대 상수 꼴에서만 범위"와 같은 줄기) OR 꼴로 풀어 써야 한다. 덧붙여 이 데이터처럼 id 순서가 시간 순서이면 id 커서(`id < 900001 ORDER BY id DESC`)로도 같은 20행이 나오고 기본 키라 보조 인덱스도 필요 없지만, created_at이 id 순서와 어긋날 수 있는 표(다른 시스템에서 옮겨 온 주문 등)에서는 (created_at, id) 커서가 안전하다.

- 확인한 부분: 크기 넷은 규칙상 맞혔지만 (마)와 (바)를 같은 2배로 봤다. 행 크기로 리프 수 배수를 셈하는 것((바) 1.08배)은 힌트 뒤 혼자 했다. 페이지 분할(끝 대 가운데)과 채움 비율, 넣는 시간에서 인덱스와 상관없는 몫은 설명을 들었고, 학습 확인에서 다시 묻는다.

### 문제 상황 3-1: 버퍼 풀이 표보다 작을 때 (2026-11-11)

- 물은 것: 버퍼 풀을 128MB로 줄여 ④를 다시 재면 (마)(바)의 넣는 시간이 (라)의 몇 배인지 두 칸과 이유. 실제 배수의 절반 ~ 두 배 안이면 맞힘이다. 다 넣은 뒤 파일 크기((라) 140MiB, (마) 224MiB, (바) 172MiB)를 알려 줬다.
- 사람의 예상과 이유(원문): "(마) 5배 (바) 2.2배, 버퍼풀이 1/8로 줄면서 디스크에서 읽어야 하는 쪽 수가 각각 12, 4쪽으로 늘어서 한 쪽이 늘었을 때 0.34배가 추가되었다고 생각했어."
- 에이전트 피드백: 컨테이너(세 번의 중앙값)에서 (라) 29.51초, (마) 66.34초(2.25배), (바) 33.34초(1.13배)였다(1GB 때 1.34배·1.12배). 물리적 읽기는 1GB에서 2페이지씩, 128MB에서 (라) 273~424 (마) 85,925~87,658 (바) 146~630페이지였고, 데이터 파일에 쓴 양은 128MB에서 658 / 5,409 / 872MiB였다. 크기는 1GB 때와 같았다. 방향은 맞다((마)만 크게 느려지고, 버퍼 풀에서 끝나던 논리적 읽기가 물리적 읽기로 바뀜). (마)의 쓰기가 1GB 때의 3.4배인 것은 자리를 만들려고 바뀐 페이지를 써서 내보내고 다시 읽기를 되풀이해서다. 12와 4를 어떻게 셌는지 물었다.
- 판정: (마) ✗(맞힘 범위 1.13~4.5) (바) ✓(맞힘 범위 0.57~2.26 바로 안. 이유는 빗나감: (바)의 물리적 읽기는 늘지 않음). 맥 본 측정에서는 (바)가 1.099배라 빗나감이다([결과 정리](#결과-정리)).
- 용어 문답: 사람(원문): "버퍼 풀이 뭐야? 그리고 한 쪽이랑 페이지랑 다른게 뭐야? 너무 헷갈려." "버퍼 풀이 한 쪽의 크기 단위가 아니었어?" "표준 용어로 설명해줘" 에이전트는 같은 것을 "쪽"과 "페이지"로 섞어 쓴 것이 원인이라고 인정하고 표준 용어로 다시 설명했다. 페이지는 InnoDB가 읽고 쓰는 크기 단위(16KB)이고, 버퍼 풀은 페이지를 담아 두는 메모리 영역이다(1GB = 65,536페이지, 128MB = 8,192페이지). 쿼리가 페이지를 들여다보는 것이 논리적 읽기이고, 그 페이지가 버퍼 풀에 있으면 적중(hit), 없으면 미스라 디스크에서 읽어 오는 물리적 읽기가 된다. 버퍼 풀에서 바뀐 페이지는 더티 페이지가 되어 페이지 클리너가 나중에 디스크에 쓰고(플러시), 자리가 없으면 오래 쓰지 않은 페이지부터 내보낸다(축출, LRU). 더티 페이지를 내보내려면 먼저 써야 한다. 이후 문답은 이 용어로만 했다. 이어서 사람(원문): "설명한 구조를 그림이나 인터렉티브 ui로 텍스트를 최소화해서 설명해줘" "다이어그램도 조항" 에이전트는 구조 그림과, 순서대로 키와 무작위 키에 같은 수의 행을 넣으며 버퍼 풀 크기를 바꿔 보는 시뮬레이션 화면을 만들어 보였다.
- 해석 질문(표준 용어로 다시 냄): (1) (바)도 표(172MiB)가 버퍼 풀보다 큰데 물리적 읽기가 수백 페이지뿐인 까닭 (2) (마)가 100만 행을 넣는 동안 물리적 읽기가 약 8.6만 페이지뿐인(행마다 일어나지 않은) 까닭.
- 사람의 해석(원문): "1. 그건 이미 행 순서가 정해져있어서 페이지 분할이 덜 발생했기 때문인거 아니야? 2. 페이지가 모두 차지 않으면 페이지 분할이 일어나지 않는데.. 페이지 분할이랑 물리적 읽기는 관련이 없나//?"
- 에이전트 피드백: 1은 순서가 열쇠라는 것은 맞고 까닭을 분할 수로 봤다((바)의 분할 8,955는 (라)의 8,025보다 많다). 새 행이 늘 맨 끝 리프(방금 쓴 페이지)에 들어가 그 페이지와 위층이 버퍼 풀에 있어 논리적 읽기가 모두 적중하고, 무작위로 들어가는 `idx_user`는 2,470페이지라 버퍼 풀 8,192페이지에 다 들어간다. 2(질문)에는 분할과 물리적 읽기는 조건이 다르다고 답했다. 분할은 페이지가 꽉 찰 때 일어나고 새 페이지는 버퍼 풀 안에서 만들어 읽을 것이 없다. 물리적 읽기는 필요한 페이지가 버퍼 풀에 없을 때 일어난다. 간접적으로는 분할로 표가 커져(`PRIMARY` 1.53배) 버퍼 풀에 덜 들어간다. (마)에서 행마다 미스가 나지 않은 것은, 표가 작을 때(셈으로는 처음 약 55만 행까지, 확인하지 않음)는 표가 버퍼 풀에 다 들어가고, 커진 뒤에도 버퍼 풀이 표의 상당 부분(128MB 대 약 213MB)을 들고 있어 무작위로 고른 리프가 버퍼 풀에 있을 때가 많기 때문이다(행 100개에 9번꼴로 미스).
- 예상 적중(컨테이너 기준): 1/2. 해석 질문은 셈에서 뺐다.
- 확인한 부분: (마)만 크게 느려진다는 방향은 맞혔고, 이유를 디스크에서 읽을 페이지 수로 셈하려 했다. 버퍼 풀, 논리적·물리적 읽기, 더티 페이지·플러시·축출은 이번에 처음 정리했고 분할과 물리적 읽기를 섞어, 학습 확인에서 다시 묻는다.

`--smoke`는 조건마다 워밍업 1회와 검증 2회만 돌려(`write_lab.py`는 ③ 5,000행, ④ 2만 행으로 줄여) `results/validation/`에 저장하며, 가설 판단에 쓰지 않는다. `index_lab.py`는 `--cases`, `--reload`로, `write_lab.py`는 `--parts`로 조건을 고르고, 둘 다 `--trials`, `--buffer-pool-mb`, `--mysql`, `--password`, `--output-dir`을 받는다. 두 실행 틀은 서버 설정(버퍼 풀 크기, `INNODB_METRICS`)을 바꾸고 같은 표를 쓰므로 하나씩 돌린다. `index_lab.py`는 처음 표를 넣는 데 맥에서 13초쯤 더 걸린다. 의존성(PyMySQL 1.2.3)은 스크립트 머리의 PEP 723 블록과 [`index_lab.py.lock`](python/index_lab.py.lock), [`write_lab.py.lock`](python/write_lab.py.lock)에 고정했다. `3.14.2+gil`은 03·04와 같이 GIL이 있는 일반 빌드를 고르라는 uv 요청이다.

결과는 측정 한 번을 JSON 한 줄로 남긴다. 공통 필드에 더해 실행 틀마다 아래를 쓴다.

조회(`index_lab.py`): `variant`·`case`는 조건, `task`·`query`는 쿼리 이름, `sql`, `situation`·`label`(문제 상황 번호와 그 안의 이름), `size`는 표의 행 수, `params`는 DDL과 쓴 사람이다. `applied`는 만든 인덱스(`indexes`, `build_s`, `ddl_errors`, `index_stats`의 인덱스별 `size`·`n_leaf_pages`), `explain`은 `EXPLAIN`의 줄들, `explain_warnings`, `tree`는 트리 형식 계획이다. `measure`는 `analyze`(`first_ms`, `last_ms`, `rows`, `loops`, `est_cost`, `est_rows`, `top`), `analyze_text`, `client_s`(쿼리 그대로의 응답 시간), `result_rows`, `handler_reads`, `pool_read_requests`(논리적 읽기 증가분), `pool_disk_reads`(물리적 읽기 증가분)다. `check`는 `EXPLAIN ANALYZE`를 읽었으면 1이다.

쓰기(`write_lab.py`): `part`(`indexes` 또는 `pk`), `variant`는 조건, `task`(`insert-more-rows`, `insert-pk`), `size`는 넣은 행 수, `params`는 DDL이나 기본 키 정의와 묶음 크기, `wall_s`는 넣는 구간의 경과 시간이다. `measure`는 `batches`, ③의 `copy_s`·`build_s`, `counters`(위 카운터의 증가분), ④의 `sizes`(`index_pages`, `data_length`, `index_length`, `file_size`, `allocated_size`)다. `check`는 넣은 뒤 표의 행 수, `expected_check`는 기대 행 수다.

환경 파일에는 공통 항목에 더해 DB 버전과 주요 설정(`databases`), 띄운 이미지(`docker_images`), 조건 목록, 적용한 버퍼 풀 크기와 처음 크기, 표의 지문을 남긴다.

### 측정하며 본 것

- `ref`·`range`로 읽고 추정 rows가 큰(10만, 50만) 비커버링 읽기는 LIMIT 20에서 멈췄는데도 논리적 읽기가 약 3,450이었다. 2 (라) 3,448, 2-1의 커서 쿼리 3,461~3,481로, 오름차순(하이픈만 고친 판)과 내림차순에서 같았다. 같은 20행을 추정 rows 20인 `index` 읽기로 가져온 2 (나)는 87이었고, 시간도 0.020~0.031ms 대 0.435~0.505ms로 약 22배 차이였다. 문제 상황 2 피드백에 적은 레코드 버퍼 설명(추측)과 맞는다.
- 2-1의 OFFSET은 건너뛸 행 수에 따라 계획이 바뀌었다. 3,380행(170번째 페이지)에서는 `idx_created`를 거꾸로 읽어 2.02~2.06ms(논리적 읽기 13,689, 항목 3,400개에 약 4번)였고, 100,000행에서는 표 전체 읽기 + 정렬을 골라 233~234ms였다. 같은 100,000행을 `FORCE INDEX`로 읽으면 58.4~61.5ms였다.
- 1-1 (다)(마)를 쿼리 그대로 돌려 클라이언트에서 잰 응답 시간은 34~39ms로, 서버 안 시간(9.90~10.2ms, 2.37~2.39ms)보다 길었다. 12,656행을 파이썬으로 받는 시간이 대부분이라 판정은 서버 안 시간으로 했다.
- ③ (나)(다)는 넣는 동안 물리적 읽기가 1,845~2,163 / 3,851~3,970페이지였다(컨테이너에서도 1,621~1,929 / 2,993~3,289). 인덱스를 막 만든 뒤라 새 인덱스 페이지 일부가 버퍼 풀에 없었던 것으로 봤다(추측, 확인하지 않음).
- ④ 128MB에서 (라)(바)의 넣는 시간은 1GB 때와 거의 같았다((라) 11.82초 대 11.78초, (바) 12.99초 대 12.91초). 컨테이너에서는 둘 다 1.17~1.19배 느려졌다. (마)는 1GB 때의 1.44배였다(컨테이너 1.96배).
- ④ 페이지 재구성은 (라) 1, (마) 9,199, (바) 59번이었다. 분할로 행을 옮겨 낸 페이지에 빈 공간이 조각나 남고, 무작위로 들어오는 새 행이 그 페이지에 들어갈 때 페이지를 다시 짜는 것으로 봤다(추측, 확인하지 않음).
- Python 빌드에 따라 넣는 시간이 달랐다. (1) free-threading 빌드에서 ③은 1.04 / 1.89 / 2.63초(1.82배, 2.53배), ④ 1GB는 11.66 / 15.32 / 12.94초(1.31배, 1.11배), 128MB는 11.62 / 22.59 / 12.87초(1.94배, 1.11배)였고, (2) 일반 빌드는 위 표대로 ③ 1.12 / 1.74 / 2.41초, ④ 1GB 11.78 / 14.98 / 12.91초, 128MB 11.82 / 21.55 / 12.99초다. 넣는 시간에는 PyMySQL이 INSERT 문을 만드는 시간이 들어 있다([쓰기 측정 규칙](#쓰기-측정-규칙)). 판정은 3-1 (바) 한 칸만 달랐다((1) 1.107배로 맞힘 범위 위끝 2.214배 안이라 적중, (2) 1.099배로 위끝 2.197배 밖이라 빗나감).

### 질문 1: 인덱스란 무엇이고 왜 빠른가

- 사람의 답(원문): "인덱스는 인덱스 컬럼 순으로 정렬된 데이터가 B+ tree 구조로 저장된 데이터야. 각 데이터는 인덱스가 가리키는 특정 행에 O(1)로 접근할 수 있는 포인터? 위치정보?를 가지고 있어. 이게 뭐가 빠르다고 하는건지는 불확실하지만 검색이 왜 빠르냐면 B+ tree 자료구조로 저장되어 있기 때문에 각 인덱스 컬럼에 해당하는 값을 알면 O(logN) 시간 복잡도로 해당 인덱스를 찾을 수 있기 때문에 검색이 빨라."
- 에이전트 피드백: 정렬된 B+Tree에서 O(log N)으로 자리를 찾는다는 것은 맞다. 리프 항목이 행으로 O(1)에 가는 위치 정보를 가진다는 것은 InnoDB에서 맞지 않다고만 하고 질문 5로 미뤘다. 무엇과 견줘 빠른지와 숫자가 빠졌다.
- 왜? 1(에이전트): 문제 상황 1의 (가)(나)를 처음 낸 글 그대로 다시 적고 맥 측정((가) `ALL`, `rnd_next` 1,000,001, 143~154ms, 논리적 읽기 7,473 / (나) `ref` · `idx_user`, key 1 · next 5, 0.006~0.008ms, 논리적 읽기 30)을 보인 뒤 물었다. (1) (가)는 5건을 찾고도 왜 100만 행을 끝까지 읽었나 (2) (나)는 첫 항목의 자리를 어떻게 찾았고, 다섯 번째 뒤에 더 없다는 것을 어떻게 알았나.
- 사람의 질문(원문): "맞힐 것 같은지가 뭔데? 왜 적는데?" 에이전트는 답하기 전에 맞힐 것 같은지를 말로 한 줄(% 없이) 적는 것이고, 안다는 느낌과 실제를 견줘 자신 있게 틀린 곳을 찾으려는 것이며, 2026-11-09에 범위를 정할 때 고른 확인 방법이라고 답했다.
- 사람의 답(원문): "(1) 맞힐 것 같아. / 5건은 찾았지만 그 뒤에 조건에 맞는 행이 더 없다는 사실을 created_at을 포함한 보조 인덱스가 없기 때문에 알 수 없기 때문에 100만 행을 끝까지 읽었어. (2) 못 맞힐 것 같아. / 첫 항목의 자리는 보조 인덱스의 user_id 인덱스 컬럼이 조건문에 조건으로 작성되었기 때문에 해당 인덱스를 사용해서 가장 앞선 항목을 찾을 수 있었어. 다섯 번째 뒤에 더 없다는 건 어떻게 알았는지 모르겠어."
- 에이전트 피드백: (1)에서 끝까지 봐야 안다는 것은 맞고, 까닭은 빗나갔다고만 했다((나)는 created_at 없이도 다섯 개에서 멈췄다). 이어 클러스터형 인덱스는 무엇의 순서로 놓이고 그 순서에서 4242의 5건이 어디 있는지 물었다. (2)에는 `idx_user`가 3층(루트 1장, 중간 2장, 리프 1,078장. 층 구성은 1-2 컨테이너 확인)이라는 것을 주고, 첫 자리는 무엇을 비교하며 몇 장을 읽었는지, 끝은 리프 순서로 다섯 번째 다음에 어떤 user_id가 오는지 물었다(작은 힌트).
- 사람의 답(원문): "(1) 맞힐 것 같아. / id의 순서로 정렬되어 있어. 어디에 있을지는 몰라. (2) 못 맞힐 것 같아. / user_id의 크기를 비교하면서 페이지는 3장 읽었어. / (user_id, id)의 크기 순서로 놓여있어. user_id 4242 다음에는 4243이 있을거야. 그냥 4242가 created_at에 관계없이 총 5건 만 있었던 걸까?"
- 에이전트 피드백: 둘 다 맞다. 04에서 두 번 놓친 클러스터형 인덱스의 정렬 기준(id)을 혼자 말했다. 4242의 5건은 id 51,510·172,436·338,024·553,396·788,746으로 흩어져 있다(데이터를 만드는 코드의 씨앗으로 다시 만들어 셈). 그래서 (가)는 끝까지 읽어야 다 찾았는지 안다. `idx_user`는 (user_id, id) 순이라 층마다 키를 비교해 한 장씩 3장을 내려가 첫 4242에 닿고, 다섯 번째 다음 항목이 4243 이상이라 멈춘다(04 질문 2의 (12, 4)와 같은 일). 물은 것도 맞다. 4242는 표 전체에 5건이고, `idx_user`에 created_at이 없어 다섯 건을 다 읽은 뒤 서버가 걸러 1행을 돌려줬다(`Using where`).
- 왜? 2(에이전트): (나)는 왜 루트부터 다섯 번 내려가지 않았나(key 1 · next 5). 1-1 (나)(key 1 · next 50,000)는 `idx_user`의 리프 1,078장, 항목 100만 개에서 리프를 몇 장쯤 읽었나.
- 사람의 답(원문): "(1) 맞힐 것 같아. / 인덱스는 컬럼의 값의 크기 순서로 정렬되어 있기 때문에 하나의 user_id만 찾는다면 한 번만 내려가서 첫 항목을 찾고 그 다음 항목으로 넘어가면서 user_id가 달라지는 부분까지만 찾으면 user_id = ? 조건에 맞는 행을 모두 찾을 수 있기 때문이야. (2) 반반 / 대략 한 페이지에 900행 정도 포함되어 있을테니까 약 55장 정도 읽었을거라 생각해."
- 에이전트 피드백: 둘 다 맞다. 5만 ÷ (100만 ÷ 1,078 ≈ 928) ≈ 54장이다. 컨테이너 확인(판정용 아님)에서 `idx_user`만 읽는 `COUNT(*)`(user_id 1)의 논리적 읽기는 77이었다(내려가는 3장과 리프 54장의 합 57보다 20쯤 많고, 그 나머지는 확인하지 않았다). 페이지 끝에서 루트로 돌아가지 않고 다음 리프로 가는 방법은 질문 2에서 물었다.
- 셈: 처음 답에는 비교 대상과 숫자가 없었다. 왜? 1은 측정값과 작은 힌트 뒤에 맞혔고, 왜? 2는 물음에 준 1,078장과 100만 항목으로 약 55장을 셈해 혼자 맞혔다(숫자를 넣어 혼자 답한 질문으로 셈). 맞힐 것 같은지 6번: 맞힐 것 같아 3번(반쯤, 맞음, 맞음), 반반 1번(맞음), 못 맞힐 것 같아 2번(빗나감, 힌트 뒤 맞음). 처음 답은 이 방식을 알기 전이라 적지 않았다.

### 질문 2: B-Tree, B+Tree, 해시 인덱스

- 사람의 답(원문): "전혀 모르겠어"
- 에이전트(설명과 줄인 물음): 기초가 없어 짧게 설명하고 물음을 줄였다. B-Tree는 중간 노드에도 행이 있다. B+Tree는 행을 리프에만 두고 중간 페이지에는 키와 자식 페이지 번호만 두며, 리프는 키 순서로 놓인다. 해시 인덱스는 같은 키를 한 번에 찾지만 해시값은 키의 순서와 상관없이 흩어진다(MySQL에서는 MEMORY 엔진이 쓰고, InnoDB 표의 인덱스는 B+Tree다). 물음은 셋이었다. (1) user_id·created_at·phone에 해시 인덱스만 있다면 (가) `user_id = 4242` (나) 하루 구간 (다) `ORDER BY created_at DESC LIMIT 20` (라) `phone LIKE '0100923%'` 중 빨리 되는 것과 까닭(괄호에 맥의 B+Tree 값을 줌) (2) 1-1 (나)가 리프 약 54장을 루트로 돌아가지 않고 이어 읽으려면 리프에 무엇이 있어야 하나 (3) 1-2의 숫자(항목을 담는 곳 15,360B, 행 100B, 중간 항목 17B)로 B+Tree와 B-Tree의 중간 페이지 자식 수와 1억 행의 층 수.
- 사람의 답(원문): "(1) 반반 / (가) 빨라. (나) 느려. (다) 느려. (라) 느려. 위와 같이 판단한 이유는 해시 함수로 특정값을 특정 인덱스로 변환하는건 빠르지만 범위나 비교 연산이 포함되면 여러 행을 찾아야하기 때문에 느릴거라 생각해. (2) 맞힐 것 같아. / 다음 리프에 위치한 페이지의 첫 행의 인덱스 키야. (3) 맞힐 것 같아. / 키의 크기: 약 17바이트 / 행의 크기: 약 100바이트 / B+Tree: 키만 약 900개, 1억 행이면 층수는 4층 (루트, 중간*2, 리프) / B-Tree: 키와 행을 모두 포함, 약 120개, 1억 행이면 층수는 6층 (루트, 중간*4, 리프)"
- 에이전트 피드백: (1)의 판정 넷은 맞고, 까닭은 "여러 행"보다 해시값이 순서를 잃어 시작 자리를 찾거나 이어 읽을 수 없다는 것이라고 고쳤다(B+Tree로는 하루 구간 2,831행도 1.69~1.70ms, 해시로는 (다)가 100만 행을 읽고 정렬해야 함). (2)는 빗나갔다. 리프에는 앞뒤 리프의 페이지 번호가 있다(InnoDB 페이지 머리의 `FIL_PAGE_PREV`·`FIL_PAGE_NEXT`, MySQL 8.4.6 소스 `storage/innobase/include/fil0types.h`의 주석으로 확인). 중간 항목이 자식 페이지 번호를 가진 것과 같은 꼴이다. (3)은 자식 수(약 900, 약 120)와 방향은 맞고 층 수가 빗나갔다. B+Tree는 리프 1억 ÷ 150 ≈ 66.7만 장, 그 위 중간이 약 741장, 그 위가 루트라 3층이다. B-Tree는 자식이 약 148(15,360 ÷ (100 + 4))이라 148³ ≈ 324만 < 1억 < 148⁴ ≈ 4.8억으로 4층이다.
- 왜? 1(에이전트): B-Tree는 중간에서 찾기가 끝날 수 있는데도 DB 인덱스가 B+Tree를 쓰는 까닭을, 1-1 (나)의 리프 약 54장 이어 읽기와 2 (나)의 정렬 없는 20행, 층 수 셈으로.
- 사람의 답(원문): "맞힐 것 같아. / 인덱스는 크기 순으로 정렬되어 있고 한 리프 페이지에서 다음 리프 페이지로 바로 갈 수 있는 방법도 존재해. 그러면 그 리프까지 도달하는 가장 짧은 층수를 가지는게 검색에 더 유리하기 때문이야."
- 에이전트 피드백: 맞다. 1-1 (나)는 리프 약 54장을 옆으로, 2 (나)는 `idx_created`의 끝에서 20개를 거꾸로 읽었다(논리적 읽기 87, 0.020~0.031ms). B-Tree라면 범위를 읽을 때 위아래 층을 오르내린다. 빠진 것은 숫자와, 중간에서 끝나는 이득이 작다는 것이다. 자식이 148이면 항목의 약 99%가 맨 아래 층에 있고, 대신 1억 행에서 B+Tree 3층 대 B-Tree 4층이라 찾을 때마다 한 장을 더 읽는다.
- 왜? 2(에이전트): 해시는 등치를 O(1)로 찾는데, InnoDB가 등치에도 B+Tree를 쓰고 해시 인덱스를 따로 두지 않아도 되는 까닭을 1 (나)(`idx_user` 3층, 논리적 읽기 30, 0.006~0.008ms)로.
- 사람의 답(원문): "반반 / O(logN) 시간 복잡도나 O(1)이나 실질적인 시간이 많이 차이나지 않아서 그런거 아니야?" 이어서 피드백을 보기 전에(원문): "그리고, 항상 등치조회 요청이 있는게 아니라 다른 조회 요청까지 생각하면 B+Tree만 운용하는게 비용 면에서 더 효율적이지 않나?"
- 에이전트 피드백: 둘 다 맞다. 덧붙인 답이 피드백보다 5초 먼저 와서, 피드백에 "빠진 것"으로 적었던 내용을 혼자 말한 것으로 고쳐 셌다. 팬아웃이 약 900이라 100만 행도 1억 행도 내려가는 데 3장이고, 약 1.2억 행(900² × 150)을 넘어야 4장이 된다. (나)는 논리적 읽기 30번에 0.006~0.008ms라 해시가 아낄 몫은 내려가는 3장 중 두어 장, 1µs가 안 된다. 해시는 범위·정렬·앞부분 일치를 못 해 B+Tree가 어차피 있어야 하고, 따로 두면 쓸 때마다 고칠 구조가 하나 는다(③ 보조 인덱스 0·3·6개에 새 주문 10만 건 1.12 / 1.74 / 2.41초). InnoDB가 자주 찾는 키에 해시를 스스로 만드는 적응형 해시 인덱스는 8.4에서 기본으로 꺼져 있다(1-2 컨테이너 확인).
- 셈: 처음 답이 "모르겠어"여서 줄인 물음의 셈은 숫자를 넣어 혼자 답한 것으로 세지 않았다. 왜? 1·2는 혼자 맞혔고 숫자는 없었다. 맞힐 것 같은지 5번: 맞힐 것 같아 3번(빗나감, 빗나감, 맞음), 반반 2번(반쯤, 맞음). 자신 있게 틀린 둘은 리프를 잇는 것의 내용(첫 키 대 페이지 번호)과 층 수 세기였다.

### 질문 3: 트리의 층 수(페이지 크기와 팬아웃)

- 사람의 답(원문): "못 맞힐 것 같아. / 한 노드(페이지)에서 그 아래층 노드를 가리키는 정보를 충분히 많이 담을 수 있기 때문이야. 그래서 노드 하나만 있어도 그 다음 층의 노드가 충분히 많아서 적은 노드로도 많은 데이터의 위치 정보를 알 수 있기 때문이야. 팬아웃 용어는 들어봤는데 정확한 뜻은 몰라서 답변에 사용하진 못했어"
- 에이전트 피드백: 핵심은 맞다. 노드 하나가 가리키는 아래층 노드 수를 팬아웃(fan-out)이라고 한다. 왜 그렇게 많이 담기는지(페이지 크기와 항목 크기)와 숫자가 빠졌다.

### 질문 5: 클러스터형 인덱스와 보조 인덱스

- 사람의 답(원문): "못 맞힐 것 같아. / 클러스터형 인덱스는 id에 부여되는(?표준 용어로 뭐라고 하지) 인덱스고 보조 인덱스는 그 이외의 인덱스를 말해. / 보조 인덱스의 리프에는 인덱스 컬럼으로 이루어진 행이 있지 않아? 약 100바이트의 정보를 가진 행"
- 에이전트 피드백: 찾던 말은 기본 키(primary key)다. 클러스터형은 기본 키의 인덱스, 보조는 그 밖의 인덱스라는 것은 맞고, 클러스터형 리프에 무엇이 있는지가 빠졌다. 보조 인덱스의 리프는 빗나갔다고만 했다.
- 왜? 1(에이전트, 측정값과 작은 힌트): 맥의 리프 수 `PRIMARY` 6,303장·`idx_user` 1,078장(둘 다 100만 행, 항목을 담는 곳 약 15,360B)과 user_id가 INT 4B라는 것을 주고 물었다. 보조 리프에 100B 행이 있다면 `idx_user` 리프는 몇 장이어야 하나, 실제 1,078장이면 항목 하나는 몇 바이트이고 무엇이 들었나, 100B 행 전체는 어디 있나.
- 사람의 답(원문): "idx_user 리프는 계산상 (100만 / 150 = )0.66만 행이었어야 해. / 실제로는 한 페이지에 900행 정도라 행 하나는 17바이트 쯤 해. / 그 안에는 user_id, id, 실제 100바이트 행을 가리키는 포인터?, 머릿말 정도 들어있나. / 100바이트짜리 행 전체는 디스크에 있나?"
- 에이전트 피드백: 약 6,666장과 약 17B, user_id·id·머리말은 맞다. 포인터와 행의 자리는 맞고 틀림을 말하지 않고 다음 물음으로 넘겼다. "디스크에 있나"는 메모리와 디스크 이야기라 뒤로 미루고, 여기서는 어느 인덱스의 어느 페이지인지를 묻는다고 했다.
- 왜? 2(에이전트, 작은 힌트): 17B에서 user_id 4B, id 8B, 머리말 5B를 빼면 포인터 자리가 남나. 6,666장은 어느 인덱스의 리프 수와 비슷한가(질문 3에서 3층으로 센 것). 이 둘로 `idx_user` 항목 하나에서 created_at·amount를 얻기까지 어느 인덱스의 어떤 페이지를 몇 장 읽는지 순서대로, 질문 4의 "항목 하나에 약 4번"과 맞춰서.
- 사람의 답(원문): "못 맞힐 것 같아. / 안 남네. / primary index 리프 수와 비슷해. / idx_user 인덱스의 루트 > 중간 > 리프 > primary index의 리프 페이지?"
- 에이전트 설명: 포인터 자리가 없다는 것과 6,666장이 `PRIMARY`의 리프 수와 비슷하다는 것은 맞고, 순서는 빗나가 설명했다. 행 전체는 `PRIMARY`의 리프에 있고, 클러스터형 인덱스가 곧 표(id 순)다. 보조 항목에는 행의 자리 없이 id만 있어 `PRIMARY`도 루트부터 id를 비교하며 3장을 읽는다(1-2 컨테이너 확인: `id IN`으로 열 행을 찾는 데 논리적 읽기 30). 1-1 (나)는 처음 한 번 `idx_user`의 루트·중간·리프를 내려가고, 항목마다 `PRIMARY` 3장과 나머지 약 1번으로 약 4번 × 5만 = 200,073이다. `idx_user`만 읽는 `COUNT(*)`는 5만 항목에 77번이라(컨테이너 확인) 20만은 거의 `PRIMARY`의 몫이다. 나머지 약 1번이 `PRIMARY`에 다녀온 뒤 `idx_user` 리프를 다시 여는 몫이라는 것은 추측이다. 보조 인덱스가 행의 자리 대신 기본 키를 두기 때문에, 페이지 분할로 행이 옮겨도 보조 인덱스를 고치지 않아도 된다.
- 사람의 질문(원문): "저게 왜 페이지 4개야? idx_user 인덱스에서 페이지 3개, primary 인덱스에서 페이지 3개해서 6개 를 읽은거 아니야?" 에이전트는 `idx_user` 3장은 첫 항목 때 한 번뿐이고 다음 항목은 같은 리프의 옆이라 루트로 돌아가지 않는다고, 질문 1 왜? 2의 답을 그대로 짚었다. 항목마다 6장이면 5만 × 6 = 30만인데 잰 값은 200,073이다.
- 셈: 처음 답의 보조 리프와 왜? 2의 순서가 빗나가 설명으로 넘어갔다. 질문 1 처음 답의 "O(1) 포인터", 질문 4의 네 장, 질문 5의 보조 리프는 모두 "보조 항목이 행의 자리를 가리킨다"는 한 오해였다. 문제 상황 1-1의 확인 문제(2026-11-10)에서는 "id를 참고해 클러스터형 인덱스를 타고 다시 루트부터 리프까지"라고 혼자 말했었다. 숫자는 물음에 준 값으로 셈했다. 맞힐 것 같은지 2번: 못 맞힐 것 같아 2번(빗나감, 빗나감). 왜? 1은 적지 않았다.

### 질문 11: UUID 기본 키

- 사람의 답(원문): "맞힐 것 같아. / 일단 페이지에 저장되는 행과 키의 크기가 늘어나. 왜냐하면 id가 8바이트에서 16바이트가 되니까 / 그리고 쓰기 시간이 늘어나. uuid는 앞에 추가된 id가 항상 뒤에 추가된 id보다 작다는게 보장되지 않거든. / AUTO_INCREMENT, UUIDv7은 추가되는 순서대로 그 크기 순서가 결정되기 때문에 쓰기 시간이 느리지 않아. / 숫자는 기억나지 않아."

- 왜? 1(에이전트, 측정값): ④의 맥 측정 표(AUTO_INCREMENT / UUIDv4 / UUIDv7의 넣는 시간 1GB 11.78 / 14.98 / 12.91초, 128MB 11.82 / 21.55 / 12.99초, `PRIMARY` 리프 6,303 / 9,664 / 6,832, `idx_user` 리프 1,713 / 2,114 / 2,110, 1GB 데이터 파일 쓰기 422~442 / 1,179~1,195 / 533~564MiB, 128MB 물리적 읽기 298~397 / 87,573~87,963 / 320~456. 분할 수는 넣지 않음)를 보이고 물었다. - 사람의 답(원문): "1. 못 맞힐 거 같아. / 항상 메모리에 올려두진 않아. 일부는 디스크에 뒀다고 페이지 미스가 발생하면 메모리로 로드해. / 2. 모르겠어"
- 에이전트 피드백(설명): 1은 맞다. 질문 4의 "항상 메모리에"를 스스로 고쳤다. 덧붙이면 자리가 모자라면 오래 쓰지 않은 페이지를 내보내고(축출, LRU), 더티 페이지면 먼저 디스크에 쓴다(플러시). 2는 설명했다. AUTO_INCREMENT는 순서대로 채워지지만 번호로 건수를 짐작할 수 있고, UUIDv4는 무작위로 끼어들어 버퍼 풀을 빨리 넘기며, UUIDv7은 넣는 순서가 곧 키 순서라는 것을 셋 다 혼자 말했다. 숫자를 붙이면 ④ 128MB에서 넣는 시간 11.82 / 21.55 / 12.99초, 물리적 읽기 298~397 / 87,573~87,963 / 320~456이다. 고칠 것은 둘이었다. UUIDv4로 잰 비용은 조회가 아니라 넣기다(조회는 재지 않았다). UUIDv7은 만든 시각과 순서는 드러내지만 건수는 드러내지 않고, 대가는 16B 키라 보조 인덱스 항목마다 8B가 더 붙는 것이다(`idx_user` 리프 2,110 대 1,713).
- 셈: 혼자 고른 것은 상황 1 전부, 상황 2의 인덱스(커버링)와 커서, 상황 3의 보조 인덱스다. 상황 3의 기본 키 값(UUIDv7)은 다시 쓰기에서 골랐고, 상황 2의 커서 경계(id 덧붙이기, OR 꼴)와 커버링 칼럼이 같은 값 안의 순서를 바꾸는 점은 설명으로 넘어갔다. 숫자는 셋 다 넣지 않았다. 맞힐 것 같은지: 셋 다 맞힐 것 같아였고, 상황 1은 맞음, 상황 2·3은 반쯤이었다.

### 04 변형: 인덱스와 락 범위, 일관된 읽기와 잠금 읽기

- 에이전트: 시작 전 기록의 변형 문제에서 `FOR SHARE`를 스냅숏 읽기로 봤고, 04 문제 상황 1-1에서 인덱스가 없으면 `PRIMARY` 전체가 잠기는 것을 봤으니, 이번 실험의 인덱스와 04의 락을 잇는 순서표를 냈다. orders 100만 행, REPEATABLE READ, 두 세션 A와 B. 고객 4242는 주문 5건(amount 합 445,400), 고객 17은 3건(합 381,900). 경우는 (가) 보조 인덱스 없음 (나) `CREATE INDEX idx_user ON orders (user_id);`였다. 순서표는 1 A `START TRANSACTION;` 2 A `UPDATE orders SET amount = amount + 100 WHERE user_id = 4242;` 3 B `START TRANSACTION;` 4 B `SELECT SUM(amount) FROM orders WHERE user_id = 4242;` 5 B `SELECT SUM(amount) FROM orders WHERE user_id = 17 FOR UPDATE;` 6 A `COMMIT;` 7 B `SELECT SUM(amount) FROM orders WHERE user_id = 4242;` 8 B `SELECT SUM(amount) FROM orders WHERE user_id = 4242 FOR SHARE;` 9 B `COMMIT;`이다. 경우마다 5번이 바로 끝나는지 기다리는지(기다리면 언제 끝나는지), 4·7·8번이 돌려주는 값, 까닭을 락과 읽기 종류로 물었다(8칸).
- 사람의 답(원문): "1. 맞힐 것 같아. / (가) 바로 끝남 / (나) 바로 끝남 / 배타락 모드여도 그 user_id_ = 4242 행에만 갭락이 걸리기 때문에 user_id = 17인 행과는 무관해서 락 충돌이 발생하지 않고 B의 5번 statement는 바로 끝남. / 2. 맞힐 것 같아. / (가) 445900, 4번은 B 트랜잭션의 첫번째 평범한 읽기를 수행하는 문장이기 때문에 해당 행의 최신 버전을 읽어야함. 그런데 2번 문장에서 해당 행에 갭락을 이미 걸고 있어 이를 읽기 위해서 레코드락을 요청하면 충돌이 발생해 6번이 끝날 때까지 기다리다가 4번이 처리됨. user_id = 4242인 행들(5행)의 amount가 각각 100씩 증가한 후에 해당 행들을 조회할 수 있음. / (나) 445900, (가)와 같음" 결과를 보이기 전에 7·8번 값을 더 적어 달라고 한 뒤(원문): "7번 (가) 445900 (나) 445900 / 8번 (가) 445900 (나) 445900"
- 에이전트 피드백: 컨테이너 확인(판정용 아님. 이 확인은 이 값으로 판정했고, 한 번 돌림. 5번을 보낸 뒤 기다림을 확인하려고 약 2초 뒤에 6번을 보냄) 결과는 아래와 같았고, 8칸 중 3칸을 맞혔다.

| 문장 | (가) 보조 인덱스 없음 | (나) `idx_user` |
|---|---|---|
| 2번 A의 `UPDATE` | 635.85ms, A가 잠근 행 1,006,303(`trx_rows_locked`) | 1.39ms, A가 잠근 행 11 |
| 4번 평범한 `SELECT` | 바로 끝남(125.83ms), 445,400 | 바로 끝남(0.57ms), 445,400 |
| 5번 `FOR UPDATE`(고객 17) | 기다림(B가 `PRIMARY` id 1의 X를 요청해 A의 X에 막힘), 6번 `COMMIT` 뒤 381,900(2,715.63ms) | 바로 끝남(0.8ms), 381,900 |
| 7번 평범한 `SELECT` | 445,400(123.53ms) | 445,400(0.58ms) |
| 8번 `FOR SHARE` | 445,900(413.76ms) | 445,900(0.3ms) |

- 에이전트 피드백(이어서): 5번 (가)가 갈린 자리다. 락은 조건에 맞는 행이 아니라 읽으면서 훑은 인덱스 항목에 걸린다. 인덱스가 없으면 A의 `UPDATE`는 user_id = 4242를 찾으려고 `PRIMARY`를 처음부터 끝까지 훑으며 훑은 행마다 X 락을 걸고, REPEATABLE READ는 조건에 맞지 않은 행의 락도 해제하지 않는다(04 문제 상황 1-1). B의 5번 `FOR UPDATE`도 인덱스가 없어 `PRIMARY`를 처음부터 훑다가 첫 행(id 1)에서 A의 X 락에 막혔고, 6번 `COMMIT`으로 A의 락이 해제된 뒤에야 끝났다. (나)는 A가 `idx_user`의 4242 항목과 그 행들만 잠가(11개) 17을 찾는 B와 겹치지 않았다. 인덱스가 읽는 범위가 곧 락 범위다. 4번은 A가 X 락을 보유한 행을 읽는데도 기다리지 않았고, 7번과 8번은 B가 같은 트랜잭션에서 이어 읽었는데 값이 달랐다는 사실만 보이고 까닭을 물었다.
- 왜?(에이전트, 하나): 평범한 `SELECT`(4번, 7번)와 `FOR SHARE`(8번)는 어떻게 다르게 읽길래, 4번은 X 락이 걸린 행을 기다리지 않고 읽었고 7번과 8번은 445,400과 445,900으로 달라졌나.
- 사람의 답(원문): "평범한 SELECT는 그 트랜잭션의 평범한 SELECT에서 생성한 스냅샷에서 데이터를 읽어오고 FOR SHARE는 공유락 모드로서 최신 테이블 데이터를 읽어오기 때문이야. 이 때 최신 테이블 데이터를 읽어오려고 할 때 해당 행에 락이 걸려 있으면 해당 락과 충돌해서 그 작업은 대기하게 되는거야. / 그래서 평범한 SELECT를 했던 4번에서 스냅샷을 만들고 7번에서 그 스냅샷을 읽기 때문에 대기없이 행을 조회할 수는 있었지만 최신 데이터는 가져올 수 없었기 때문에 445400을 조회했고 8번은 락 충돌로 인해 대기하다가 행의 최신 데이터를 참조해서 445900을 읽을 수 있었어."
- 에이전트 피드백: 핵심은 맞다. 평범한 `SELECT`는 락 없이 스냅숏을 읽는 일관된 읽기이고, REPEATABLE READ에서는 트랜잭션의 첫 평범한 `SELECT`(4번) 때 만든 스냅숏을 끝까지 써서 7번도 445,400이다. `FOR SHARE`는 S 락을 거는 잠금 읽기라 최신 커밋 값 445,900을 읽는다. 시작 전 기록에서 `FOR SHARE`를 스냅숏 읽기로 본 것과 이번 처음 답에서 평범한 `SELECT`가 락을 기다린다고 본 것이 둘 다 고쳐졌다. 틀린 곳은 8번이 기다렸다는 것이다. A가 6번 `COMMIT`으로 X 락을 이미 해제해 8번 때는 B를 막을 락이 없었다((나)의 8번 0.3ms). (가)의 8번 414ms도 기다린 시간이 아니라 인덱스 없이 `PRIMARY` 100만 행을 잠금 읽기로 훑은 시간이다(같은 범위를 락 없이 읽은 7번은 124ms). 락이 걸린 행을 잠금 읽기로 읽으려 하면 충돌해 기다린다는 규칙 자체는 맞고, 8번이 6번보다 앞에 있었다면 A의 `COMMIT`까지 기다렸을 것이다(재지 않음). 락은 `COMMIT`이나 `ROLLBACK` 때 해제되니, 순서표에서는 그 문장 때 누가 아직 락을 보유하고 있는지부터 따진다. 덧붙여 스냅숏에는 만든 순간까지 커밋된 것만 들어간다. 4번 때 A의 변경은 커밋 전이라 빠졌고, B는 A가 X 락을 보유한 행을 락 없이 undo log로 되돌린 옛 버전으로 읽었다.
- 셈: 8칸 중 3칸((가)(나)의 8번, (나)의 5번)이었다. 8번 둘은 "모든 읽기가 A의 커밋 뒤 최신 값"이라는 틀로 맞힌 것이었다. 맞힐 것 같은지: 순서표의 두 줄 모두 맞힐 것 같아였고, 5번은 2칸 중 1칸, 값은 6칸 중 2칸이 맞았다. 왜?는 맞힐 것 같은지를 적지 않았다.

## 정리한 결론과 선택 기준

아래는 맥 본 측정(MySQL 8.4.13, Docker Desktop, M2 Pro)과 사람의 답을 대조해 정리한 결론이다. 시간은 워밍업을 뺀 세 번의 최솟값~최댓값이다. 학습 확인 피드백에서만 확인한 값은 "컨테이너 확인(판정용 아님)"으로 적었다. 이 기계와 설정 밖으로 숫자를 일반화하지 않는다.

| 상황 | 이번에 확인한 내용과 선택 기준 |
|---|---|
| 인덱스가 빠른 까닭 | 보조 인덱스는 칼럼 값 순서(같으면 기본 키 순서)로 항목을 놓은 B+Tree다. 루트에서 키를 비교하며 층마다 한 장씩 내려가 첫 항목에 닿고, 리프를 옆으로 읽다 값이 바뀌면 멈춘다. 문제 상황 1 (나) `user_id = 4242`는 `idx_user`를 3장 내려가 5개를 읽어 0.006~0.008ms(논리적 읽기 30)였다. 인덱스가 없으면 클러스터형 인덱스(id 순)에 흩어진 5건을 찾으려고 100만 행을 끝까지 읽어 143~154ms였다. 끝까지 봐야 다 찾았는지 알 수 있기 때문이다. |
| 층 수와 팬아웃 | 16KB 페이지에 중간 항목(키, 자식 페이지 번호 4B, 레코드 머리 5B. 행 데이터 없음)이 수백 개 들어가 층이 낮다. `idx_user`는 리프 1,078장에 100만 항목(장당 약 928), `PRIMARY`는 리프 6,303장(장당 158.7행)이고, 리프 6,303장 위에 중간 8장, 그 위에 루트로 3층이다(중간 장수는 컨테이너 확인). 층마다 약 900배로 늘어 약 1.2억 행까지 3층이다. 페이지가 4KB라면 팬아웃과 리프 행 수가 함께 줄어 1억 행이 4층이 된다(셈, 재지 않음). 층 수는 리프부터 위로 세고, 한 층 적으면 모자란다는 것까지 확인한다. |
| B+Tree를 쓰는 까닭 | 행을 리프에만 두고 리프끼리 앞뒤 페이지 번호로 이어, 범위와 정렬은 한 번 내려간 뒤 리프만 옆으로 읽는다(1-1 (나) 리프 약 54장, 2 (나) `idx_created`의 끝에서 20개 0.020~0.031ms). 중간에 키만 있어 팬아웃이 커 층이 낮다. 해시 인덱스는 등치만 한 번에 찾고 범위·정렬·앞부분 일치를 못 한다. 등치도 B+Tree로 3장이라 해시가 아낄 몫은 1µs가 안 되고, 해시를 따로 두면 쓸 때마다 고칠 구조가 는다. InnoDB의 적응형 해시 인덱스는 8.4에서 기본으로 꺼져 있다(컨테이너 확인). |
| 클러스터형 인덱스와 보조 인덱스, 두 번 읽기 | InnoDB의 클러스터형 인덱스(`PRIMARY`)가 곧 표이고, 리프에 행 전체가 기본 키 순으로 있다. 보조 인덱스의 리프 항목은 (칼럼 값, 기본 키)뿐이고 행의 자리(페이지 번호)를 가리키지 않는다(`idx_user` 항목 약 17B = user_id 4B + id 8B + 머리 5B). 다른 칼럼이 필요하면 항목마다 기본 키로 `PRIMARY`를 루트부터 다시 내려간다. 1-1 (나)는 5만 항목에 논리적 읽기 200,073(항목당 약 4 = `PRIMARY` 3장 + 나머지 약 1, 나머지가 무엇인지는 추측)으로, 100만 행을 다 읽은 (가)의 7,473보다 27배 많았다(시간은 35.2~36.0ms 대 144~151ms, 물리적 읽기는 둘 다 0). 기본 키를 두는 덕에 페이지 분할로 행이 옮겨도 보조 인덱스를 고치지 않는다. |
| 복합 인덱스의 칼럼 순서 | 리프는 앞 칼럼부터, 같으면 다음 칼럼 순으로 놓인다. 같은 값으로 찾는 칼럼(등치)을 앞에, 범위 칼럼을 뒤에 둔다. 문제 상황 1의 `(user_id, created_at)`는 4242의 08-10 이후 항목이 한데 모여 1개를 읽고 멈췄고(0.003~0.005ms), `(created_at, user_id)`는 08-10 이후 251,352항목에 4242가 흩어져 옵티마이저가 `ALL`을 골랐다(142~149ms). WHERE에 조건을 적은 순서는 계획과 상관없다(컨테이너 확인: 순서만 바꾼 두 쿼리의 계획이 같음). 정렬도 필요하면 등치 칼럼 다음에 `ORDER BY` 칼럼을 잇는다(목표 3 상황 1의 `(user_id, status, created_at)`는 20항목 0.613~0.723ms, `(user_id)`만이면 5만 항목과 정렬 79.1~92.3ms, 컨테이너 확인). |
| 커버링 인덱스 | 쿼리가 쓰는 칼럼(WHERE, `SELECT` 목록, `ORDER BY`)이 인덱스에 다 있으면 클러스터형 인덱스를 다시 읽지 않는다(`Using index`). 인덱스의 종류가 아니라 인덱스와 쿼리의 관계다. 1-1에서 amount를 붙인 (마)는 같은 12,656항목에 논리적 읽기 54, 2.37~2.39ms였고 붙이지 않은 (다)는 50,661, 9.90~10.2ms였다. 보조 항목 끝에 기본 키가 있어 `SELECT id, created_at`과 `COUNT(*)`는 (다)로도 덮인다(컨테이너 확인 51). 대가는 크기와 쓰기다(리프 1,632장 대 1,386장). 20행만 돌려주는 쿼리라면 아끼는 것은 다시 읽기 20번 정도다. 칼럼을 붙일 때도 정렬과 커서에 쓰는 칼럼을 먼저 둔다(목표 3 상황 2: `(status, created_at, user_id, amount)`는 id를 넣은 커서에 정렬을 따로 해 4.78~7.63ms, `(status, created_at, id, user_id, amount)`는 정렬 없이 0.188~0.245ms, 컨테이너 확인). |
| 인덱스가 있어도 쓰이지 않는 경우 | 리프는 칼럼의 원래 값 순서로 놓여 있어, 칼럼 값을 행마다 바꾸면 시작 자리를 찾지 못한다. `DATE(created_at) = ...`(153~159ms 대 하루 구간 1.69~1.70ms), VARCHAR에 `phone = 숫자`(칼럼 값을 숫자로 바꿔 비교, Note 1739, 161~165ms 대 문자열 0.003~0.004ms), DATETIME에 `LIKE '2026-11-01%'`(인덱스 전체 읽기 248~255ms 대 하루 구간 0.807~0.857ms, 컨테이너 확인)가 그렇다. 상수를 바꾸는 `user_id = '4242'`(INT 칼럼)는 그대로 인덱스를 썼다(0.005~0.006ms). 앞이 정해지지 않은 `LIKE '%4282'`는 시작 자리가 없어 다 읽고(190~199ms), `LIKE '0100923%'`는 한데 모인 96개만 읽는다(0.080~0.081ms). TEXT는 앞부분 길이 없이 인덱스를 만들 수 없고(오류 1170), `LIKE '%포장%'`는 `memo(20)`이 있어도 `ALL`이었다. 고칠 때는 바꾸는 일을 상수로 옮긴다. 옵티마이저가 비용으로 인덱스를 고르지 않는 경우는 아래 `EXPLAIN` 행에 적었다. |
| `EXPLAIN` 읽기 | `type`은 읽는 방법이다(`ALL` 표 전체, `index` 인덱스 전체, `range` 인덱스의 한 구간, `ref` 같은 값의 항목들, `const` 기본 키나 유일 인덱스로 한 행). rows는 옵티마이저의 추정이고 `LIMIT`을 반영하지 않는다(1-1 (나) 104,988 대 실제 50,000. 이 값은 user_id = 1 범위의 양 끝을 인덱스에서 찾아 어림한 것(index dive)으로 컨테이너에서 확인). 실제 수는 `EXPLAIN ANALYZE`의 actual rows와 `Handler_read_*`로 본다. `Using index`는 인덱스를 쓴다는 뜻이 아니라 커버링이고, `Using index condition`은 인덱스 안에서 조건을 먼저 거른 것, `Using filesort`는 따로 정렬한 것, `Backward index scan`은 거꾸로 읽은 것이다. 옵티마이저는 추정 rows로 계획마다 비용을 셈해 가장 싼 것을 고른다. 문제 상황 1 (라)는 45.9만 항목의 두 번 읽기를 셈해 cost 160,605가 전체 읽기 100,695보다 커서 `ALL`(142~149ms)을 골랐지만, 인덱스로 강제하면 15.0~15.9ms였다(컨테이너 확인). |
| 정렬 생략 | `ORDER BY`가 인덱스에 놓인 순서와 같을 때, 또는 앞 칼럼을 등치 조건으로 하나로 고정하고 그다음 칼럼부터 같을 때, 리프 순서대로 읽고 `LIMIT`에서 멈춘다(`DESC`는 거꾸로 읽기). 2 (나) `(created_at)` 20행 0.020~0.031ms 대 (가) 100만 행과 정렬 192~199ms, (라) `(user_id, created_at)` 20행 0.504~0.510ms 대 (다) `(user_id)` 5만 항목과 정렬 34.1~34.9ms. WHERE는 앞 칼럼을 고정할 뿐이다. 범위(`BETWEEN`)는 앞 칼럼을 고정하지 못해 고객 하나 안에서만 created_at 순이라, 목표 1 쿼리 2는 같은 인덱스로 967항목을 읽고 정렬했다(1.89~2.75ms, 컨테이너 확인). MySQL은 인덱스 정의로만 판단해, 이 데이터에서 id 순이 곧 시간 순이어도 `(user_id)`의 id 순을 created_at 순으로 쓰지 않는다. |
| OFFSET과 커서 | OFFSET은 개수라 인덱스로 N번째에 바로 가지 못하고(페이지에 그 아래 항목 수가 없음) 앞에서부터 읽고 버린다. 2-1 `OFFSET 100000`은 옵티마이저가 `ALL`과 정렬(233~234ms)을 골랐고, `FORCE INDEX`로도 read_prev 100,019, 논리적 읽기 401,307, 58.4~61.5ms였다. 커서는 앞 페이지 마지막 행의 값으로 루트부터 내려가 바로 닿아 페이지 번호와 상관없다(5,001번째 0.479~0.492ms, 170번째 0.468~0.478ms). 같은 created_at이 여러 행이면 (created_at, id)를 기억해 `WHERE created_at < ? OR (created_at = ? AND id < ?) ORDER BY created_at DESC, id DESC`로 쓴다. created_at만 기억하면 `<`는 같은 초의 남은 행을 빠뜨리고(끝까지 넘기면 770행), `<=`는 앞 페이지 마지막 행이 다시 나온다(컨테이너 확인). 행 생성자 꼴 `(created_at, id) < (?, ?)`는 범위로 쓰이지 않아 10만 항목을 읽었다(62.3~64.4ms). 페이지 번호로 바로 가야 하는 화면이 아니면 커서를 고른다. |
| 보조 인덱스 수와 쓰기 | 보조 인덱스마다 새 행의 자리를 찾아 항목을 넣어야 한다. ③ 버퍼 풀 1GB에서 새 주문 10만 건은 보조 인덱스 0·3·6개에 1.12 / 1.74 / 2.41초(1.55배, 2.14배), 데이터 파일 쓰기 29~60 / 67~105 / 167~181MiB였다. 인덱스 페이지도 필요할 때 버퍼 풀로 읽고 자리가 모자라면 축출하므로 늘 메모리에 있는 것은 아니다. 자주 도는 조회에 필요한 인덱스만 둔다. |
| 기본 키 종류 | 기본 키는 클러스터형 인덱스의 정렬 기준이고 모든 보조 인덱스 항목에 붙는다. AUTO_INCREMENT와 UUIDv7은 새 행이 맨 끝에 붙어 끝에서 나뉘고(꽉 찬 페이지는 그대로 둠), UUIDv4는 곳곳의 리프 가운데로 끼어들어 반씩 나뉜 페이지가 평균 3분의 2쯤 찬다. ④ 100만 건에서 `PRIMARY` 리프는 6,303 / 9,664 / 6,832장, 분할은 8,025 / 11,799 / 8,955번이었다. 분할 수는 새로 생긴 페이지 수와 거의 같아, 크기를 정하는 것은 몇 번이 아니라 어디서 나뉘나다. 버퍼 풀 1GB에서 넣는 시간은 11.78 / 14.98 / 12.91초, 데이터 파일 쓰기는 422~442 / 1,179~1,195 / 533~564MiB였다. UUIDv7은 UUIDv4의 이 비용이 없고, 대가는 16B 키라 보조 인덱스 항목마다 8B가 더 붙는 것(`idx_user` 리프 2,110 대 1,713)과 번호에 만든 시각과 순서가 드러나는 것이다(건수는 드러나지 않음). 번호를 밖에 보이면서 건수를 숨겨야 하면 UUIDv7을, 밖에 보이지 않는 키면 AUTO_INCREMENT를 고른다. |
| 버퍼 풀과 자주 건드리는 페이지 | 버퍼 풀은 디스크의 페이지 중 일부만 담는다. 필요한 페이지가 없으면 디스크에서 읽고(물리적 읽기, 미스), 자리가 모자라면 오래 쓰지 않은 페이지를 내보낸다(축출, LRU, 더티 페이지는 먼저 플러시). 느려지는지는 표 크기가 아니라 자주 건드리는 페이지가 버퍼 풀에 들어가는지로 정해진다. ④ 128MB(8,192페이지)에서 파일은 140 / 224 / 172MiB로 셋 다 컸지만, 끝에만 붙는 AUTO_INCREMENT와 UUIDv7은 11.82초, 12.99초로 1GB 때와 거의 같았고, UUIDv4만 축출된 리프를 디스크에서 읽어 21.55초가 됐다(물리적 읽기 87,573~87,963, AUTO_INCREMENT 298~397). |
| 인덱스와 락 범위 | 락은 조건에 맞는 행이 아니라 읽으면서 훑은 인덱스 항목에 걸린다(04와 이어짐). 인덱스가 없으면 REPEATABLE READ의 `UPDATE ... WHERE user_id = 4242`가 `PRIMARY` 전체를 훑으며 1,006,303개를 잠가(635.85ms) 다른 고객의 `FOR UPDATE`도 첫 행에서 기다렸고, `idx_user`가 있으면 11개만 잠가(1.39ms) 다른 고객의 `FOR UPDATE`가 바로 끝났다(컨테이너 확인, 한 번). 쓰기와 잠금 읽기의 조건 칼럼에 인덱스를 두면 잠기는 범위도 준다. 평범한 `SELECT`는 락 없이 스냅숏을 읽고(REPEATABLE READ는 트랜잭션의 첫 평범한 `SELECT` 때 만든 스냅숏을 끝까지 씀), `FOR SHARE`·`FOR UPDATE`는 최신 커밋 값을 읽으며 락을 건다. 같은 트랜잭션에서 평범한 `SELECT`는 445,400, `FOR SHARE`는 445,900을 돌려줬다. |

## 학습 확인 요약

질문 11개 중 직접 잰 숫자를 넣어 스스로 답한 것은 질문 1·3의 둘이었다(03은 9개 중 1개, 04는 8개 중 3개). 둘 다 처음 답이 아니라 "왜?"에서였고, 물음에 준 리프 수(1,078장, 6,303장)로 셈한 것이었다. 처음 답에 장면이나 잰 숫자를 넣은 질문은 없었고, 질문 11에서는 "숫자는 기억나지 않아"라고 했다. 질문 2·7·9는 처음 답이 "모르겠어"였다. "왜?"에 두 번까지 이어 답한 것은 11개 모두였고(03은 4개, 04는 6개), 두 번 모두 힌트 없이 맞힌 것은 질문 2·3이었다. 끝난 뒤 낸 처음 보는 문제에서는 목표 1의 쿼리 3개 15칸 중 8칸을 맞혔고(04는 순서표 2개 16칸 중 12칸, 둘 다 컨테이너 확인 기준), 목표 3의 상황 3개 중 상황 1의 칼럼 순서와 커버링, 상황 2의 인덱스와 커서 방식, 상황 3의 보조 인덱스를 혼자 골랐다. 04 변형 순서표는 8칸 중 3칸이었고, 이어 물은 "왜?"에서 일관된 읽기와 잠금 읽기를 바르게 나눴다.

맞힐 것 같은지를 실제 결과와 견주면 아래와 같다. 11개 질문에서는 물음마다(줄인 물음과 "왜?" 안의 항목 포함) 한 줄을 셌다. 맞음은 그 물음에 피드백 전에 맞게 답한 것이고, 그 전에 받은 장면·측정값·힌트는 따지지 않았다. 적지 않은 5번(그중 셋은 처음 답이 "모르겠어"였음)과, 물음 안의 한 항목에 "모르겠어"로만 답한 4개는 뺐다. 처음 보는 문제는 칸으로 셌다.
