## 용어

- 세마포어가 세는 값은 파이썬 문서를 따라 **카운터**라고 쓴다. 파이썬 문서와 CPython 소스는 내부 카운터(internal counter)라고 부르고, `Semaphore(4)`의 4는 카운터의 초깃값이다. [threading 문서](https://docs.python.org/3.14/library/threading.html#semaphore-objects), [CPython 3.14.2 구현](https://github.com/python/cpython/blob/v3.14.2/Lib/threading.py#L459)
- 다른 이름: POSIX는 세마포어 값(value)이라 부르고 0 밑으로 내려가지 않는 정수로 정의한다. Java와 Rust tokio는 허가(permit)라고 부르며, Java 문서는 실제 허가 객체 없이 남은 개수만 센다고 적는다. 두 연산은 다익스트라가 붙인 이름 P·V로도 부른다. [sem_overview(7)](https://man7.org/linux/man-pages/man7/sem_overview.7.html), [Java Semaphore](https://github.com/openjdk/jdk/blob/master/src/java.base/share/classes/java/util/concurrent/Semaphore.java), [tokio Semaphore](https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html)
- 락의 두 상태는 파이썬 영어 문서의 locked/unlocked, 한국어 번역 문서의 **잠금/잠금 해제**로 쓴다. `RLock`이 기억하는 것은 소유하는 스레드(owning thread)와 재귀 수준(recursion level)이다. [Lock](https://docs.python.org/3.14/library/threading.html#lock-objects), [RLock](https://docs.python.org/3.14/library/threading.html#rlock-objects), [한국어 번역](https://docs.python.org/ko/3.14/library/threading.html)
- 조건 변수(condition variable)의 용어는 파이썬 한국어 문서를 따른다. 조건 변수와 짝을 이룬 락은 **연관된 락**(문서는 "연관된 록", "하부 록"(underlying lock)), 스레드가 진행을 멈추고 기다리는 것은 **블록**, `notify()`가 하는 일은 **통지**, 기다리는 스레드는 **대기 중인 스레드**로 쓴다. 한국어 문서는 lock을 "록"으로 적지만 이 README는 "락"으로 쓴다. [Condition](https://docs.python.org/3.14/library/threading.html#condition-objects), [한국어 번역](https://docs.python.org/ko/3.14/library/threading.html#condition-objects)
- 임계 영역 문제의 용어는 Silberschatz·Galvin·Gagne의 『Operating System Concepts』 임계 영역 문제(The Critical-Section Problem) 절을 따른다. 공유 데이터를 쓰는 스레드의 코드는 **진입 구역**(entry section), **임계 영역**(critical section, 번역에 따라 임계 구역), **퇴출 구역**(exit section), **나머지 구역**(remainder section)으로 나눈다. `with lock:`이라면 `acquire()`가 진입 구역, 블록 안이 임계 영역, `release()`가 퇴출 구역이다. 임계 영역 문제는 다음 세 조건을 모두 만족하는 진입 구역과 퇴출 구역을 설계하는 문제다. **상호 배제**(mutual exclusion): 한 스레드가 임계 영역에서 실행 중이면 다른 어떤 스레드도 임계 영역에서 실행될 수 없다. **진행**(progress): 임계 영역에서 실행 중인 스레드가 없고 들어가려는 스레드가 있으면, 다음에 누가 들어갈지는 나머지 구역에 있지 않은 스레드들만 정할 수 있고 이 결정은 무한히 미뤄질 수 없다. **한정 대기**(bounded waiting): 한 스레드가 진입을 요청한 뒤 그 요청이 허락될 때까지 다른 스레드들이 임계 영역에 들어가는 횟수에는 상한이 있다.

- 문제: GIL이 켜진 일반 CPython에서 순수 Python 계산 작업 16개를 처리한다. 작업 하나는 순차로 0.05초 걸린다. 프로세스 풀 8개를 만들고 닫는 데 0.3초, 결과를 돌려받는 데 작업마다 0.01초가 더 든다고 가정할 때, 순차와 프로세스 8개 중 어느 쪽이 빨리 끝나는가. 01 실험의 "다시 확인할 내용" 중 추가 비용과 절약한 시간의 비교를 새 숫자에 적용하는 문제다.
- 사람의 답(요약): 순차는 0.05초 작업 16개라 0.8초다. 프로세스 8개는 풀 생성 0.3초에, 작업과 결과 전달 0.06초를 두 번 더해 0.42초다. 그래서 프로세스 8개가 더 빠르다고 답했다.
- 에이전트 피드백: 결론과 0.42초는 결과 전달이 작업자마다 따로 겹쳐 일어난다는 가정에서 맞다. 0.3초는 풀 생성과 종료를 합친 값이다. 결과는 부모 프로세스 하나가 받으므로 전달이 겹치지 않는다고 보면 최대 0.3 + 0.1 + 0.16 = 0.56초이고, 결론은 같다. 추가 비용(0.32~0.46초)이 병렬화로 절약한 시간(0.8 − 0.1 = 0.7초)보다 작다고 말할 수 있다.
- 현재 확인한 부분: 해설 없이 계산으로 실행 방식을 골랐다. 추가 비용과 절약한 시간을 나눠 비교하는 표현은 쓰지 않았다. 01의 나머지 재확인 항목(계산 중 스레드 교대와 Task 교대, 순수 Python 계산과 GIL을 해제하는 네이티브 계산의 구분)은 다음 변형 문제로 남긴다.

### 문제 상황 1: 상한 4개인데 동시 호출이 늘어난 서버

에이전트가 제시한 가정 상황이며 실제 측정 결과가 아니다.

스레드로 요청을 처리하는 서버가 외부 API를 부른다. 그 API는 동시에 4개까지만 받는다. 서버를 띄우고 며칠 지나자 외부 API가 HTTP 429(요청이 너무 많음)로 거절하기 시작했다. 그때 로그에서는 동시에 나가는 호출이 4개가 아니라 9~10개였다. 예외나 경고는 없었고, 그 며칠 동안 타임아웃이 6번 있었다. 상한은 아래 코드로 걸었다.

```python
import threading

api_slots = threading.Semaphore(4)

def call_api(req):
    api_slots.acquire()
    try:
        return send(req)          # 느린 외부 호출
    except TimeoutError:
        api_slots.release()       # 기다리는 다른 요청에 자리를 먼저 넘긴다
        return send_later(req)    # 나중에 다시 보낼 큐에 넣는다
    finally:
        api_slots.release()
```

물은 것: 동시 호출이 4개를 넘게 된 원인, 예외가 나지 않은 이유, 모르거나 헷갈리는 부분.

- 사람의 원인 예상(요약): `TimeoutError`가 나면 `except`와 `finally`에서 `release()`가 두 번 불려 "세마포어 두 개가 해제"되는 버그라고 짚었다. 원래는 하나만 해제되어 다른 스레드 하나가 이어서 호출해야 하는데, 두 개가 해제되어 다른 두 스레드가 추가로 호출할 수 있게 됐다고 설명했다. 타임아웃 6번이 호출 상한을 10까지 늘려 9~10개가 호출됐다고 계산했다.
- 에이전트 피드백: 원인과 계산은 맞다. 세마포어는 하나이고 늘어나는 것은 카운터이므로 "세마포어 두 개가 해제됐다"보다 "카운터를 두 번 올렸다"가 정확하다. 타임아웃 한 번에 `acquire()` 한 번과 `release()` 두 번이 일어나 카운터가 영구히 1씩 늘어난다.
- 예외가 나지 않은 이유, 사람의 첫 답(요약): `TimeoutError`만 났고 `except`에서 잡혀 `send_later()`로 실행 흐름을 넘길 수 있었기 때문이라고 답했다.
- 에이전트 피드백: `TimeoutError`가 `except`에서 처리되어 밖으로 나오지 않았다는 설명은 맞다. 질문의 뜻이 모호했으므로, 물은 대상이 `acquire()`보다 한 번 더 부른 두 번째 `release()` 자체라고 다시 짚었다. `release()`가 불릴 때 세마포어가 무엇을 확인하고 무엇을 확인하지 않는지를 확인할 지점으로 제시했다.
- 두 번째 `release()`가 오류를 내지 않은 이유, 사람의 답(요약): 내부 구현은 모르지만 문제 상황에 비추어, `release()`가 지금 쓸 수 있는 개수를 하나 늘린다고 추측했다. 4로 적힌 상한 값을 바꾸지는 않겠지만, 실제로 동작하는 스레드 수를 세지는 않도록 구현됐을 것이라고 추측했다. 이때 "자리"가 표준 용어인지 물었다(위 용어 절).
- 에이전트 피드백: CPython 3.14.2의 `Semaphore.release()`는 `self._value += n` 뒤 `notify(n)`로 기다리는 스레드를 깨운다. 어느 스레드가 `acquire()` 했는지 기록하지 않으므로 스레드 수를 세지 않는다는 추측은 맞다. 다만 일반 `Semaphore`는 `__init__`에서 `self._value = value`만 두어 4를 상한으로 따로 기억하지 않는다. 초깃값을 `_initial_value`로 기억하고 `release()`에서 넘는지 검사해 `ValueError("Semaphore released too many times")`를 내는 것은 `BoundedSemaphore`다. [Semaphore](https://github.com/python/cpython/blob/v3.14.2/Lib/threading.py#L459), [BoundedSemaphore](https://github.com/python/cpython/blob/v3.14.2/Lib/threading.py#L546)
- 다음 질문(에이전트): `Semaphore(4)`를 `BoundedSemaphore(4)`로 바꾸면 첫 타임아웃의 두 번째 `release()`에서 바로 `ValueError`가 나는가.
- 사람의 예상과 이유(요약): 바로 나지 않을 수도 있다고 답했다. 그때 카운터가 3보다 작으면 두 번 `release()`해도 4를 넘지 않아 상한을 넘지 않은 것으로 판단하기 때문이라고 설명했다.
- 에이전트 피드백: 맞다. `BoundedSemaphore.release()`는 호출마다 `self._value + n > self._initial_value`만 검사한다. 타임아웃 난 스레드가 아직 `acquire()` 한 상태에서 카운터가 v라면 두 번째 `release()`에서 바로 `ValueError`가 나는 것은 v = 3, 즉 그 스레드 혼자 `acquire()` 한 상태일 때뿐이다. 다른 스레드가 하나라도 `acquire()` 한 상태면 검사를 통과한다. 이 판단은 소스로 확인했고 실행으로는 아직 확인하지 않았다.
- 이어지는 질문(에이전트): 검사를 통과한 경우 하나 더 올라간 카운터는 그 뒤 어떻게 되는가. `ValueError`가 결국 난다면 언제, 어느 스레드에서 나는가.
- 사람의 예상(요약): `release()`로 카운터가 4를 넘게 되는 순간에 `ValueError`가 난다고 답했다. 예로 카운터가 4인데 들어가 있던 스레드가 호출을 마치고 `release()`하는 경우, 카운터가 3인데 들어가 있던 스레드 둘 이상이 호출을 마치고 모두 `release()`하는 경우를 들었다.
- 에이전트 피드백: 맞다. 두 경우 모두 이중 `release()` 뒤 "카운터 + 지금 `acquire()` 한 스레드 수"가 4가 아니라 5가 되어, 들어가 있던 스레드들이 모두 돌려주는 마지막 `release()`에서 검사에 걸린다. 덧붙인 것은 셋이다. (1) `ValueError`가 나는 스레드는 이중 `release()`를 한 스레드가 아니라 `acquire()`와 `release()`를 한 번씩 한 다른 스레드라서, 오류 위치와 원인 위치가 다르다. (2) 그 `release()`는 카운터를 올리기 전에 거부되어 카운터가 4에 머문다. 늘어난 하나는 그때 사라지지만, 그 전까지는 타임아웃 한 번만으로도 동시 호출이 5개까지 나갈 수 있다. (3) `finally`에서 난 예외는 `try`의 return 값을 덮어쓰므로, 그 스레드의 API 호출은 성공했는데 부른 쪽에는 실패로 보인다. 따라서 `BoundedSemaphore`는 늦게 알려 주는 탐지기이고, 고치는 방법은 `except`의 `release()`를 지우고 `with api_slots:`로 `acquire()` 한 번에 `release()` 한 번이 되게 하는 것이다. 세 가지는 소스와 언어 규칙으로 판단했고 실행으로는 아직 확인하지 않았다. [try 문](https://docs.python.org/3.14/reference/compound_stmts.html#the-try-statement)
- 다음 질문(에이전트): 상한을 1로 줄여 `api_slots`를 `threading.Lock()`으로 바꾸면 타임아웃 때 두 번째 `release()`에서 무슨 일이 일어나는가. `threading.RLock()`이면 무엇이 다른가.
- 사람의 첫 답: "그냥 거부된다?"라고만 표현할 수 있고 지식이 부족해 더 구체적으로 말할 수 없다고 했다. RLock이 무엇인지 물었다.
- 에이전트 보충 설명: `Lock`은 잠김·풀림 두 상태만 있고 누가 잠갔는지 기억하지 않아 다른 스레드도 풀 수 있으며, 풀린 락을 `release()`하면 `RuntimeError("release unlocked lock")`가 난다. `RLock`(재진입 락)은 소유자 스레드와 잠근 횟수를 기억해 같은 스레드가 여러 번 `acquire()`할 수 있고, 소유자가 아닌 스레드가 `release()`하면 `RuntimeError("cannot release un-acquired lock")`가 난다. 락을 쥔 함수가 같은 락을 쓰는 함수를 부를 때 쓰며, 일반 `Lock`이면 그 자리에서 스스로 멈춘다. [Lock](https://docs.python.org/3.14/library/threading.html#lock-objects), [RLock](https://docs.python.org/3.14/library/threading.html#rlock-objects), [CPython 3.14.2 구현](https://github.com/python/cpython/blob/v3.14.2/Modules/_threadmodule.c#L859), [소유자 검사](https://github.com/python/cpython/blob/v3.14.2/Python/lock.c#L410)
- 줄인 질문(에이전트): 타임아웃 난 스레드 T가 첫 `release()`로 `Lock`을 푼 뒤 두 번째 `release()` 전에 (가) 아무도 잡지 않은 경우, (나) 기다리던 스레드 U가 잡고 API를 부르는 중인 경우, T의 두 번째 `release()`는 각각 어떻게 되는가. `RLock`이면 어떻게 되는가.
- 사람의 예상과 이유(요약): (가)는 `Lock`이 이미 잠금 해제 상태이므로 `RuntimeError`가 난다. (나)는 `Lock`이 잠금 상태인지만 검사하므로 잠금 해제로 바꾸고 오류 없이 진행한다. `RLock`이면 (가)는 같고, (나)는 잠근 스레드가 풀기까지 요구하므로 오류가 난다고 답했다. 잠김/풀림이 표준 용어인지 물었다(위 용어 절).
- 에이전트 피드백: 셋 다 맞다. `RLock`의 (가)는 메시지만 `cannot release un-acquired lock`으로 다르다. (나)에서 T가 푼 것은 U가 잡은 락이므로 U가 API를 부르는 중에 락이 잠금 해제 상태가 되고, 기다리던 다른 스레드가 들어와 두 스레드가 함께 API를 부를 수 있다. 상호 배제가 오류 없이 깨진다. `RLock`은 소유자를 기억해 같은 실수를 T 자신의 `release()`에서 바로 잡아낸다. `BoundedSemaphore`가 늦게, 다른 스레드에서 알려 주는 것과 다르다. 실행으로는 아직 확인하지 않았다.

### 문제 상황 2: 첫 업로드 뒤 작업자 하나가 사라진 썸네일 서버

from collections import deque

jobs = deque()
cond = threading.Condition()

def put(job):                    # 업로드 요청 스레드가 부른다
    with cond:
        while len(jobs) >= 5:
            cond.wait()          # 가득 차 있으면 깨울 때까지 기다린다
        jobs.append(job)
        cond.notify()            # 기다리는 스레드 하나를 깨운다

def take():                      # 작업자 스레드가 부른다
    with cond:
        if not jobs:
            cond.wait()          # 비어 있으면 깨울 때까지 기다린다
        job = jobs.popleft()
        cond.notify()            # 기다리는 스레드 하나를 깨운다
        return job

- 묶음 2 마지막 질문(에이전트, 2026-10-26): 같은 버퍼를 세마포어 둘(`empty = Semaphore(5)`, `full = Semaphore(0)`)과 `jobs`를 지키는 `Lock` 하나로 만든다. `put()`은 `empty.acquire()` 뒤 락 안에서 넣고 `full.release()`, `take()`는 `full.acquire()` 뒤 락 안에서 꺼내고 `empty.release()`를 한다. 이 버전에서도 `IndexError`가 날 수 있는가, 조건 변수의 `notify()`와 세마포어의 `release()`는 무엇이 다른가.

- 에이전트 피드백: `release()`가 카운터를 올려 진행할 수 있는 스레드 수를 조정한다는 설명은 맞다. `take()`가 먼저 불려도 `full.acquire()`에서 카운터가 0이면 `put()`의 `full.release()`까지 블록되므로 빈 `jobs`의 `popleft()`에 닿지 않고, `IndexError`는 나지 않는다. `full`의 카운터는 곧 꺼낼 수 있는 작업 수다. `put()`은 작업을 넣은 뒤에야 카운터를 올리고, `acquire()`는 카운터 확인과 차감을 한 번에 하므로 통과한 `take()`마다 작업 하나가 따로 예약되어 다른 작업자가 가로챌 수 없다. 조건 변수의 `notify()`는 깨우기만 하고 아무것도 예약하지 않아 깨어난 뒤 조건을 다시 확인해야 하고, 기다리는 스레드가 없으면 사라진다. `release()`는 카운터에 남는다. 질문 목록의 "모니터와 조건 변수, 세마포어의 차이"로 정리했다. 세마포어는 카운터 자체가 조건이고, 조건 변수는 조건을 프로그램의 데이터에 두고 기다릴 곳만 준다. 운영체제의 모니터는 공유 데이터, 그 데이터를 다루는 함수, 락, 조건 변수를 한데 묶은 것이고 문제 상황 2의 `jobs`·`put()`·`take()`·`cond`가 그 모양이다. 이 질문은 문답으로만 다루고 측정하지 않는다.

### 문제 상황 3: 기다리는 스레드가 늘수록 느려진 서버 시작

에이전트가 제시한 가정 상황이며 실제 측정 결과가 아니다.

서버가 시작할 때 로더 스레드 하나가 큰 설정 파일로 색인을 만들고, 요청 처리 스레드 8개는 그게 끝날 때까지 기다렸다가 요청을 받기 시작한다. 색인 만들기는 순수 Python 계산이라 혼자 돌리면 1초쯤 걸린다. 그런데 서버를 띄우면 요청을 받기 시작할 때까지 9초쯤 걸렸다. 요청 처리 스레드를 4개로 줄였더니 5초쯤으로 줄었다.

```python
import threading

ready = False
index = None

def load():                      # 로더 스레드
    global index, ready
    index = build_index()        # 순수 Python 계산, 혼자 돌면 약 1초
    ready = True

def serve():                     # 요청 처리 스레드
    while not ready:             # 준비될 때까지 기다린다
        pass
    handle_requests(index)

threading.Thread(target=load).start()
for _ in range(8):
    threading.Thread(target=serve).start()
```

물은 것: 1초짜리 로딩이 9초쯤 걸린 원인과 스레드를 4개로 줄이니 5초쯤으로 준 이유, 모르거나 헷갈리는 부분.

- 에이전트 확인(2026-10-26): 서술한 증상이 코드의 실제 동작과 맞는지 임시 스크립트로 확인했다(Linux 컨테이너, CPython 3.14.2). 측정 결과로 쓰지 않는다. 사람의 답 다음에 묶음 3 측정 예상을 묻게 되어, 예상이 이 숫자에 기대지 않도록 숫자는 본 측정이 끝난 뒤에 밝힌다.
- 사람의 답(2026-10-26, 원문): "잘 모르겠어. 내 생각에는 CPU 작업을 진행하다가 GIL이 일정시간이 지나면 알아서 해제되면서 serve 쪽 스레드가 GIL을 획득하고 while 문 실행되다가 다시 일정 시간 지나서 GIL이 해제되고 그걸 load 스레드가 소유해서 다시 indexing 진행하면서 인덱싱 작업이 계속 지연되는 시나리오가 아니면 왜 스레드 개수에 따라 로딩 시간이 변화하는지 모르겠어."
- 에이전트 피드백: 서술한 시나리오가 원인이다. `while not ready: pass`는 하는 일이 없어도 Python 바이트코드를 계속 실행하므로 GIL이 필요하다. 그래서 로더 1개와 요청 처리 스레드 8개, 모두 9개가 GIL을 돌아가며 잡는다. 다른 스레드가 GIL을 기다리면 잡고 있던 스레드는 전환 간격(switch interval, `sys.getswitchinterval()`, 기본 0.005초)이 지나면 GIL을 내놓는다. 로더는 9번 중 1번꼴로만 GIL을 잡으니 1초 일이 9초쯤 걸리고, 4개면 5개가 나눠 써서 5초쯤 걸린다. 이렇게 조건을 계속 확인하며 기다리는 것을 바쁜 대기(busy waiting)라고 한다. 보통은 CPU를 헛되이 쓰는 것이 문제이고, GIL이 있는 CPython에서는 일하는 스레드의 GIL 시간까지 빼앗는다.
- 고치는 방법(에이전트): (가) 반복 안에 `time.sleep(0.01)`을 넣는다. 자는 동안은 GIL을 내놓는다. (나) `threading.Event`를 쓴다. `Event`는 참/거짓 깃발 하나를 가진 도구로, 로더가 `ready.set()`으로 깃발을 올리면 `ready.wait()`에서 블록돼 있던 스레드가 모두 깨어난다.

### 문제 상황 4: 서로에게 송금하면 멈추는 이체

에이전트가 제시한 가정 상황이며 실제 측정 결과가 아니다.

계좌마다 락이 하나씩 있는 이체 기능이다. 이체할 때는 보내는 계좌를 잠그고, DB에서 이체 한도를 확인한 뒤(약 1ms), 받는 계좌를 잠그고 잔액을 옮긴다. 한 스레드에서 A→B 1000번을 마친 뒤 B→A 1000번을 돌리면 늘 끝난다. 그런데 두 사람이 서로에게 동시에 송금하는 경우를 흉내 내 두 스레드로 함께 돌렸더니 프로그램이 끝나지 않았다. 예외도 출력도 없고, 멈춘 동안 CPU 사용률은 0%에 가깝다.

```python
import threading

class Account:
    def __init__(self, name, balance):
        self.name = name
        self.balance = balance
        self.lock = threading.Lock()

def transfer(src, dst, amount):
    with src.lock:                  # 보내는 계좌를 잠근다
        check_limit(src, amount)    # DB에서 이체 한도 확인(약 1ms)
        with dst.lock:              # 받는 계좌를 잠근다
            src.balance -= amount
            dst.balance += amount

a, b = Account("A", 1_000_000), Account("B", 1_000_000)

def a_to_b():
    for _ in range(1000):
        transfer(a, b, 1)

def b_to_a():
    for _ in range(1000):
        transfer(b, a, 1)

t1 = threading.Thread(target=a_to_b)
t2 = threading.Thread(target=b_to_a)
t1.start(); t2.start()
t1.join(); t2.join()                # 여기서 끝나지 않는다
```

물은 것: 프로그램이 멈춘 원인과 멈춘 동안 CPU를 거의 쓰지 않는 이유, 모르거나 헷갈리는 부분.

- 에이전트 확인(2026-10-26): 서술한 증상이 코드의 실제 동작과 맞는지 임시 스크립트로 확인했다(Linux 컨테이너, CPython 3.14.2, `check_limit`은 `time.sleep(0.001)`로 흉내 냄). 측정 결과로 쓰지 않는다. 숫자는 본 측정이 끝난 뒤에 밝힌다.
- 사람의 답(2026-10-26, 원문): "이건 데드락 상황이야. t1에서 src 계좌인 A 계좌에 대한 lock을 획득하고 t2에서는 src 계좌인 B 계좌에 대한 lock을 획득했어. 그리고 각 스레드에서 dst 계좌인 B, A의 계좌에 대한 lock을 획득하기 위해 대기하는 중이야."
- 에이전트 피드백: 맞다. 이 상태를 교착 상태(deadlock)라고 한다. t1은 A의 락을 쥔 채 B의 락을, t2는 B의 락을 쥔 채 A의 락을 기다린다. 둘 다 상대가 먼저 풀어 주길 기다리므로 어느 쪽도 나아가지 못한다.
- 남은 질문(에이전트): 멈춘 동안 CPU를 거의 쓰지 않는 이유. 확인할 지점으로 두 스레드가 `with dst.lock:`에서 어떤 방식으로 기다리는지 보게 했다.
- 사람의 답(2026-10-26, 원문): "서로가 가진 lock을 획득한 이후에 with dst.lock 이후 코드를 실행할 수 있는데, 아직 lock이 없기 때문에 서로 대기만 하고 있어서 CPU를 사용하지 않는거야."
- 에이전트 피드백: 맞다. 다만 기다린다고 늘 CPU를 안 쓰는 것은 아니다. 문제 상황 3의 `while not ready: pass`도 기다리는 중이었지만 CPU를 계속 썼다. 차이는 기다리는 방식이다. `with dst.lock:`은 락을 얻지 못하면 운영체제에 재워 달라고 하고 잠든다(블록). 잠든 스레드는 실행 대상에서 빠지고 GIL도 내놓으므로 CPU를 쓰지 않는다. 락이 풀려야 운영체제가 깨워 주는데, 풀어 줄 상대도 잠들어 있으니 둘 다 계속 잠든 채로 남는다.

- 에이전트 피드백: 넷 다 맞다. 이름을 붙이면 (1) 상호 배제(mutual exclusion): 락은 한 번에 한 스레드만 쥘 수 있다. (2) 점유 대기(hold and wait): 락 하나를 쥔 채로 다른 락을 기다린다. (3) 비선점(no preemption): 남이 쥔 락을 빼앗을 수 없고, 쥔 쪽이 스스로 풀어야 한다. (4) 순환 대기(circular wait): 기다림이 고리를 이룬다. 스레드가 둘이면 t1→t2→t1로 엇갈린 모양이지만 셋이면 t1→t2→t3→t1처럼 원이 되므로 '교차'보다 '고리'가 더 정확하다.

  ```python
  def transfer(src, dst, amount):
      first, second = sorted((src, dst), key=lambda acc: acc.name)  # 모든 스레드가 같은 순서로
      with first.lock:
          with second.lock:
              check_limit(src, amount)    # 한도 확인은 두 락을 잡은 뒤에
              src.balance -= amount
              dst.balance += amount
  ```

### 문제 상황 5: 식사하는 철학자

에이전트가 제시한 가정 상황이며 실제 측정 결과가 아니다.

식사하는 철학자 문제를 코드로 옮겼다. 다섯 철학자가 원탁에 둘러앉아 있고, 철학자 사이마다 포크가 하나씩 모두 다섯 개 있다. 철학자는 생각하다가(0~2ms) 왼쪽 포크를 집고, 1ms 뒤 오른쪽 포크를 집어 먹은 다음(1ms) 두 포크를 내려놓는다. 철학자마다 100번 먹으면 끝난다. 여러 번 돌려 보니 끝날 때도 있고, 끝나지 않고 멈출 때도 있었다. 멈춘 동안 CPU 사용률은 0%에 가깝다.

```python
import random
import threading
import time

N = 5
forks = [threading.Lock() for _ in range(N)]   # 철학자 사이마다 포크 하나

def philosopher(i):
    left, right = forks[i], forks[(i + 1) % N]
    for _ in range(100):                        # 100번 먹으면 끝
        time.sleep(random.uniform(0, 0.002))    # 생각한다(0~2ms)
        with left:                              # 왼쪽 포크를 집는다
            time.sleep(0.001)                   # 포크를 집는 데 1ms
            with right:                         # 오른쪽 포크를 집는다
                time.sleep(0.001)               # 먹는다(1ms)

threads = [threading.Thread(target=philosopher, args=(i,)) for i in range(N)]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

물은 것: 멈춘 상태를 교착 상태의 네 조건으로 설명하기, 매번이 아니라 가끔만 멈추는 이유.

- 에이전트 확인(2026-10-26): 서술한 증상이 코드의 실제 동작과 맞는지 임시 스크립트로 확인했다(Linux 컨테이너, CPython 3.14.2). 측정 결과로 쓰지 않는다. 숫자는 본 측정이 끝난 뒤에 밝힌다.
- 사람의 답(2026-10-26, 원문):

  > * 상호배제: 각 철학자 스레드는 같은 포크를 동시에 소유할 수 없음
  > * 점유 대기: 각 철학자 스레드는 다른 스레드가 이미 소유 중인 포크를 얻기 위해서는 그 포크를 내려놓을 때까지 대기해야함
  > * 비선점: 각 철학자 스레드는 다른 스레드가 이미 소유 중인 포크를 가져올 수 없음
  > * 순환대기: 모든 철학자 스레드가 오른손에 포크를 들고 있으면 모두 왼 손의 포크를 얻기 위해 대기해야함.
  >
  > 0~0.002초의 무작위 식사시간이 우연히 철학자가 양쪽 포크를 집게 할 수 있었기 때문에.

- 에이전트 피드백: 상호 배제와 비선점은 맞다. 점유 대기는 '기다린다'보다 '쥔 채로 기다린다'가 핵심이다. 각 철학자가 왼쪽 포크를 쥔 채로 오른쪽 포크를 기다린다. 순환 대기는 구조는 맞지만 손이 반대다. 이 코드는 왼쪽을 먼저 집으므로 모두 왼쪽 포크를 쥐고 오른쪽 포크를 기다린다. 0번은 1번을, 1번은 2번을, …, 4번은 0번을 기다려 다섯 명짜리 고리가 된다. 가끔만 멈추는 이유도 방향이 맞다(0~2ms는 먹는 시간이 아니라 생각하는 시간이다). 멈추려면 다섯 명 모두가 거의 같은 때, 누군가 오른쪽 포크를 집기 전에 왼쪽 포크를 집어야 한다. 생각 시간이 흩어지면 대개 누군가는 이웃이 오기 전에 오른쪽 포크까지 집어서 고리가 완성되지 않는다.
- 남은 질문(에이전트): (1) 문제 상황 4의 락 순서 고정을 여기에 쓰려면 `philosopher`를 어떻게 바꾸는가. (2) 웨이터를 두어 한 번에 4명까지만 포크를 집으러 가게 하는 방법(`threading.Semaphore(4)`를 `with left:` 바깥에서 잡는다, 묶음 1의 세마포어)은 네 조건 중 무엇을 깨고, 왜 4명이면 멈추지 않는가.
- 사람의 답(2026-10-26, 원문):

  > 1. 포크 인덱싱 부분을 아래와 같이 수정해.
  >
  > ```python
  > indics = [i, (i + 1) % N]
  > left, right = max(indics), min(indics)
  > ```
  >
  > 2. 점유대기 조건이 깨져. 그 이유는 모두 한 쪽 손에 포크를 들고 있어도 그 중에 한 명은 반드시 다른 한 손에도 포크를 들 수 있기 때문이야.

- 에이전트 피드백: (1) 맞다. 모든 철학자가 '번호가 큰 포크 먼저'라는 같은 순서를 따르므로 고리가 생기지 않는다. 순서는 작은 번호 먼저든 큰 번호 먼저든 하나로 정해져 있기만 하면 된다. 이렇게 하면 0~3번은 오른쪽 포크(i+1)를, 4번만 왼쪽 포크(4)를 먼저 집어 한 명이 나머지와 반대로 집는다. 코드에서는 인덱스이므로 `forks[...]`로 감싸야 하고, 이름도 `left`/`right`보다 `first`/`second`가 뜻에 맞다. (2) 이유는 맞지만 깨지는 조건이 다르다. 웨이터가 있어도 철학자는 왼쪽 포크를 쥔 채로 오른쪽을 기다릴 수 있으므로 점유 대기는 남는다. 깨지는 것은 순환 대기다. 4명이 각자 왼쪽 포크를 쥐어도 포크는 5개라 하나가 남는다. 웨이터가 들여보내지 않은 철학자의 왼쪽 포크가 남고, 그 포크를 오른쪽 포크로 쓰는 이웃은 두 포크를 다 집을 수 있다. 그래서 기다림이 다섯 명을 한 바퀴 돌아 고리가 되지 못한다.

### 질문 10: 임계 영역 문제를 푸는 세 조건

(3) 한정 대기(bounded waiting): 한 스레드가 진입을 요청한 뒤 그 요청이 허락될 때까지 다른 스레드들이 임계 영역에 들어가는 횟수에는 상한이 있어야 한다. 2번의 '나머지 구역에 있지 않은 스레드들만'은 들어갈 생각이 없는 스레드가 남의 진입을 막으면 안 된다는 뜻이다. 예로, 두 스레드가 반드시 번갈아 들어가게 짜면 차례인 스레드가 들어갈 생각이 없을 때 다른 스레드는 비어 있는 임계 영역에 못 들어가므로 진행을 어긴다.

(2) 여기서 임계 영역은 두 잔액을 바꾸는 줄, 곧 두 락을 모두 잡은 뒤의 코드다. 멈춘 순간 t1과 t2는 각각 어느 줄에 있는가, 잔액을 바꾸는 줄에 들어간 스레드가 있는가, A의 락과 B의 락은 각각 몇 개의 스레드가 쥐고 있는가. 진입 구역과 임계 영역을 나눠 보게 했다. (3) 이 경우 상대 스레드는 이체를 계속 마친다. 두 스레드가 동시에 잔액을 바꾸는가, 임계 영역에 들어가는 스레드가 계속 있는가, 밀리는 스레드가 기다리는 동안 상대가 먼저 들어가는 횟수에 상한이 있는가를 세 조건에 하나씩 대 보게 했다.
- 사람의 답(2026-10-26, 원문): "1. 상호배제 조건이 깨져. 이미 다른 스레드가 임계영역에 진입해있는데 다른 스레드가 들어올 수 있게되면서 조건이 깨져. / 2. 진행 조건이 깨졌어. 데드락으로 임계영역에 진입하지 못하고 있어. / 3. 한정 대기 조건이 깨졌어. 한 스레드가 지속적으로 순서가 밀리는 기아현상이 발생했어. / 내가 임계영역에 대한 정의를 락을 얻는 순간부터 해제하는 순간으로 잘 못 이해하고 있었어"
- 에이전트 피드백: 셋 다 맞다. 1번은 상호 배제, 2번은 진행, 3번은 한정 대기다. 임계 영역을 '락을 얻은 순간부터 푸는 순간까지'로 본 것은 락이 하나일 때는 맞는 이해다. 문제 상황 4는 락이 둘이라 이체라는 임계 영역은 두 락을 모두 얻은 뒤부터이고, 첫 락만 쥔 동안은 아직 진입 구역이다. 락을 하나씩 따로 봐도 각 락을 쥔 스레드는 하나뿐이라 상호 배제는 지켜졌다. 덧붙여, 파이썬 `Lock`은 기다리던 스레드 중 누가 먼저 들어갈지 정해 두지 않으므로([threading 문서](https://docs.python.org/3.14/library/threading.html#lock-objects): "which one of the waiting threads proceeds is not defined") 엄밀히는 한정 대기를 보장하지 않는다. Java `ReentrantLock`도 기본은 순서를 보장하지 않고 공정 모드를 따로 두는데, 순서를 지키면 처리량이 떨어지기 때문이다. 이 둘은 에이전트가 알고 있는 문서 내용이며 이 실험에서 확인하지 않았다.

### 묶음 1: 같은 이중 `release()`, 다른 결과

- 질문(에이전트): 고치지 않은 코드의 최대 동시 호출이 `Semaphore` 7, `Lock` 4, `RLock` 1이고, 오류는 `Semaphore` 없음, `Lock`은 36~40번째의 다른 호출, `RLock`은 타임아웃 난 호출 자신에서 났다. 같은 이중 `release()`인데 왜 셋이 달랐는가.
- 사람의 답(원문): "semaphore는 내부 카운터만 관리하기 때문에 내부 카운터가 release 두 번 호출로 초기값을 넘어가더라도 예외를 일으키거나 하지 않고 동시 호출 가능한 스레드의 개수만 하나 더 올라가기 때문에 오류가 발생하지 않았다. / Lock은 잠김 상태로 바꾼 스레드가 아닌 다른 스레드에서 해당 락을 해제할 수 있기 때문에 두 번의 release 사이에 다시 acquire가 호출되어 release 호출 시에 해제 상태가 아니라면 예외가 발생하지 않는다. 그래서 호출이 지속적으로 발생하는 해당 작업에서는 잠김/해제의 데이터 정합이 엇나가면서 동시에 실행할 수 있는 스레드가 쌓이다가 두 번의 release 사이에 acquire를 호출할 또 다른 작업이 없어지는 36~40번째 작업에서 해제 상태인 락을 release로 해제하려다가 RuntimeError가 발생한다. / RLock은 잠김 상태로 바꾼 스레드만 다시 해당 락을 해제상태로 변경할 수 있기 때문에 release가 두 번 호출되는 타임아웃이 발생한 스레드에서 RuntimeError가 발생한다."
- 에이전트 피드백: 셋 다 맞고 측정값과도 맞는다(`Semaphore` 4+3=7, `Lock` 1+3=4, `RLock` 1). 다듬은 점: `Lock`의 끝 무렵 오류는 타임아웃 난 호출의 두 번째 `release()`가 아니라 그때 `release()`를 부른 보통 호출이 받았다(오류 300번 모두 타임아웃이 아닌 호출). 원인(5·15·25번째 타임아웃)과 오류가 난 곳(36~40번째)이 떨어져 있고, `RLock`은 원인이 생긴 호출에서 바로 오류가 난다.
- 왜? 1(에이전트): `Semaphore`도 남는 `release()`가 3번이었는데 끝까지 오류 없이 받아 냈다. 왜 `Lock`만 끝에서 오류를 냈는가(둘이 상태를 어떻게 기억하는지로).
- 사람의 답(원문): "semaphore는 내부 카운터가 0 밑으로 내려가지 않으면 value error를 일으키지 않는데, release를 내부 카운터를 1 증가시키기 때문에 에러가 발생하지 않았다. Lock은 앞서 말했듯이 잠김/해제 두 상태만 존재하는데, 36~40번째 작업에서는 해제 -> 해제를 시도하는 release 호출로 인해 오류가 발생한다."
- 에이전트 피드백: 핵심은 맞다. 카운터는 남는 `release()`를 쌓아 두고(끝난 뒤 7), `Lock`은 두 상태뿐이라 쌓아 둘 곳이 없어 풀린 락을 또 풀 때 오류가 난다. 바로잡은 점: `Semaphore`는 카운터가 0이면 `acquire()`가 기다릴 뿐 0 밑으로 내려가지 않고, `release()`는 상한 검사 없이 올리기만 하므로 카운터가 커지는 것으로는 오류가 나지 않는다. `ValueError`는 `BoundedSemaphore`가 카운터를 초깃값보다 크게 만드는 `release()`에서 낸다.
- 왜? 2(에이전트): 왜 `Semaphore`는 초깃값을 넘는 `release()`를 오류로 보지 않는가.
- 사람의 답(원문): "그건 모르겠어"
- 에이전트 힌트: 묶음 2 마지막 질문의 세마포어 버퍼에서 `full = Semaphore(0)`은 꺼낼 수 있는 작업 수를 세고, `put()`은 작업을 넣을 때마다 `full.release()`를 부른다. 아무도 꺼내기 전에 작업이 3개 들어오면 `full`의 카운터는 몇이고, 초깃값 0을 넘는 것이 잘못인가.
- 사람의 답(원문): "현재 동시에 실행 가능한 스레드의 개수를 제한하기 위해서 사용하는게 semaphore이지 상한을 정하는게 아니기 때문일까?"
- 에이전트 설명(예제와 설명 단계): 맞지 않다. 동시 실행 수 제한도 상한을 정하는 일이고 세마포어의 쓰임 중 하나일 뿐이다. 작업이 3개 들어오면 `full`의 카운터는 3으로 초깃값 0을 넘고, 이는 '꺼낼 수 있는 작업 수'를 세는 의도한 동작이다. 세마포어의 카운터는 지금 쓸 수 있는 것의 개수이고 쓰임이 둘이다. 자원 수 제한(`Semaphore(4)`, 초깃값을 넘으면 버그, 묶음 1)과 개수 세기·신호(`Semaphore(0)`, 생길 때마다 `release()`, 초깃값을 넘는 것이 정상, `full`). `Semaphore`는 두 쓰임을 다 받아야 하므로 초깃값을 넘는 것을 오류로 볼 수 없고, 파이썬은 첫 번째 쓰임을 위해 `BoundedSemaphore`를 따로 둔다. 이 "왜?"는 도움받은 부분이다.

### 묶음 2: `if`·`while`과 `notify()`·`notify_all()`

- 질문(에이전트): `if`인 1~4번은 작업자가 줄고 `while`인 5~8번은 30번 모두 그대로였다. `if`·작업자 4개에서 `notify()`(3번)는 3·2·1개로 하나씩 줄고 `notify_all()`(4번)은 첫 업로드에서 바로 1개가 됐다. 왜 그런가.
- 사람의 질문(원문): "원래 코드가 뭐였는지 알려줘". 에이전트가 문제 상황 2의 `put()`·`take()`와 측정 순서를 다시 보여 줬다.
- 사람의 답(원문): "if로 jobs를 검사한 1~4번은 t1에서 job을 처리하고 notify를 호출하면 t2가 wait을 지나 job.popleft를 호출하다가 인덱스 에러가 발생하고 t2 작업자는 종료된다. 이렇게, put이 호출되면 작업자가 하나씩 줄어들기 때문에 1~4번은 작업자가 1개씩 줄어드는 현상이 나타난다. / while을 사용한 5~8번은 t1에서 job을 처리하고 notify를 호출해 t2가 시작되도 while 문에서 벗어나지 않기 때문에 empty jobs에서 popleft를 호출하지 않아. 작업자가 종료되지 않고 유지된다. / notify는 다음 작업자만 실행하게 만들어서 해당 작업자가 index error를 일으키고 종료되어도 하나의 작업자만 종료되지만 notify_all은 모든 작업자를 실행하게 만들기 때문에 job을 처리한 작업자 이외의 작업자는 모두 empty jobs를 참조해서 index error를 일으키고 종료된다."
- 에이전트 피드백: 셋 다 맞고 측정과 맞는다(1·2·4번 30번 모두 1·1·1, 3번 3·2·1, `IndexError` 회마다 1·1·3·3번, 5~8번 0번). 다듬은 점: t1이 t2를 깨우는 것은 썸네일을 처리한 뒤가 아니라 `take()` 안에서 작업을 꺼낸 직후의 `notify()`다.
- 왜? 1(에이전트): 작업은 하나뿐이고 t1이 이미 꺼냈는데, `take()`의 `notify()`는 원래 누구에게 무엇을 알리려는 줄인가(`put()`의 `wait()`와 함께).
- 사람의 답(원문): "그건 모르겠어. 왜 있는거야? jobs가 변경된걸 알리는건가? 누구한테 알리는거지?"
- 에이전트 힌트: `jobs`가 바뀐 것을 알리는 것은 맞다. `take()`는 작업을 꺼내 `jobs`를 줄였다. '`jobs`가 줄어들기'를 기다리는 스레드는 누구인가(`put()`의 `while len(jobs) >= 5: cond.wait()`).
- 사람의 답(원문): "main 스레드인가?"
- 에이전트 피드백: 맞다. 이번 측정에서는 실행 틀의 주 스레드가 업로드 요청 스레드 자리에서 `put()`을 불렀다. `take()`의 `notify()`는 버퍼가 가득 차 `put()`의 `wait()`에서 기다리는 업로드 요청 스레드에게 '자리가 하나 났다'고 알리는 줄이다.
- 왜? 2(에이전트): 업로드를 하나씩 넣을 때는 버퍼가 가득 찰 일이 없어 `put()`에서 기다리는 스레드가 없었다. 그 알림은 왜 사라지지 않고 작업자 t2를 깨웠는가(`put()`과 `take()`가 각각 무엇으로 기다리는지 비교).
- 사람의 질문과 답(원문): "그런데, put에서 기다리는 스레드라는게 뭐야? cond.wait()을 호출하고 있는 스레드인거야? / 그리고 메인 스레드가 아니라 t2를 깨운 이유는 다음 순번이 t2라는 건데, 그러면 왜 notify를 작성한거야?"
- 에이전트 설명(예제와 설명 단계): `put()`에서 기다리는 스레드는 `jobs`가 이미 5개라 `put()` 안의 `cond.wait()`에서 멈춰 있는 스레드다. '다음 순번이 t2'는 맞다. `notify()`는 그 조건 변수에서 기다리는 스레드 하나를 깨우고, CPython은 먼저 기다리기 시작한 스레드부터 깨운다(문서가 약속한 순서는 아니다). `notify()`를 쓴 이유는 작업 20개를 한꺼번에 넣을 때 보인다. 주 스레드는 5개를 채우고 `put()`의 `cond.wait()`에서 멈추고, 작업자가 하나를 꺼내면 `take()`의 깨우기가 주 스레드를 깨운다. 이 줄이 없으면 실행이 멈추며, 20개가 240회 모두 끝까지 처리됐으므로 이 줄이 주 스레드를 깨웠다. 알림이 t2에게 간 것은 `put()`과 `take()`가 같은 `cond`의 대기열 하나를 함께 쓰고 `notify()`는 누가 어느 함수에서 기다리는지 가리지 않고 맨 앞을 깨우기 때문이다. `while`인 5·7번에서도 업로드마다 작업자 하나가 빈 `jobs`에서 깨어났고(회마다 3번) 다시 기다렸을 뿐이다. 이 "왜?"는 도움받은 부분이다. 사람이 스스로 짚은 것은 `notify()`가 '다음 순번'을 깨운다는 점이다.
- 마지막 질문(에이전트): `take()`의 알림은 업로드 요청 스레드에게만, `put()`의 알림은 작업자에게만 가게 하려면 코드를 어떻게 바꾸는가.
- 사람의 답(원문): "cond1, cond2를 따로 만들어서 업로드 요청과 작업자 대기열 두 개로 분리할 수 있을까?"
- 에이전트 피드백: 맞다(핵심은 혼자 답함). 파이썬 `queue.Queue`가 같은 구조로, 업로드 요청 스레드가 기다리는 `not_full`과 작업자가 기다리는 `not_empty` 두 조건 변수를 둔다. 에이전트가 보탠 두 가지: (1) 두 조건 변수가 락 하나를 함께 써야 한다. 둘 다 같은 `jobs`를 보고 바꾸고, `notify()`는 그 조건 변수의 락을 쥔 스레드만 부를 수 있다. `threading.Condition()`을 따로 두 개 만들면 `put()` 안에서 `not_empty.notify()`를 부를 때 `RuntimeError: cannot notify on un-acquired lock`이 난다(컨테이너 임시 확인, CPython 3.13·3.14.2). (2) `while`은 그대로 둔다. 대기열을 나눠도 깨어난 작업자가 락을 다시 잡기 전에 작업을 막 끝내고 돌아온 다른 작업자가 먼저 꺼내 갈 수 있다. 고친 모양은 아래와 같다(에이전트 작성).

  ```python
  lock = threading.Lock()
  not_full = threading.Condition(lock)   # 업로드 요청 스레드가 기다리는 곳
  not_empty = threading.Condition(lock)  # 작업자가 기다리는 곳

  def put(job):
      with not_full:
          while len(jobs) >= 5:
              not_full.wait()
          jobs.append(job)
          not_empty.notify()

  def take():
      with not_empty:
          while not jobs:
              not_empty.wait()
          job = jobs.popleft()
          not_full.notify()
          return job
  ```

### 묶음 3: 바쁜 대기, `sleep`, `Event`

- 질문(에이전트): 요청 처리 스레드 4개/8개에서 `pass`는 로딩 4.84초/8.71초, 마지막 깨어남 0.11ms/0.16ms, 기다리는 스레드 CPU 3.87초/7.79초였다. `time.sleep(0.01)`은 로딩 0.996초/0.993초, 마지막 깨어남 8.73ms/8.74ms, CPU 0.003초/0.010초였다. `Event.wait()`는 로딩 1.000초/1.003초, 마지막 깨어남 0.12ms/0.31ms, CPU 0.000초/0.000초였다. 세 방법이 왜 이렇게 다른지 측정값을 근거로 설명하기.
- 사람의 질문(원문): "이게 문항이 정확히 뭐였는지 알려줘". 에이전트가 문제 상황 3의 상황과 코드, 기다리는 방법 셋, 조건 7가지, 잰 값 셋의 뜻을 해설 없이 다시 보여 줬다.
- 사람의 답(원문):

  > pass
  >
  > * while 문이 동작하는 동안 CPU를 점유하고 있기 때문에 그 시간 동안 요청 처리 스레드가 GIL을 소유하고 있게 된다. 그래서 로더 스레드는 그 동안 인덱싱 작업을 수행하지 못해서 딜레이된다. 여기서 스레드의 개수에 비례해서 인덱싱 완료 시간이 늘어나는 이유는 GIL을 소유하던 처리 스레드에서 GIL 해제되어도 로더 스레드가 GIL을 소유하게될 확률을 1/(1 + 요청 스레드 개수) 이기 때문에 요청 스레드가 많을 수록 로더 스레드의 작업은 지연되게 된다.
  >
  > time.sleep(0.01)
  >
  > * 요청 스레드에서 time.sleep(0.01)을 호출해서 GIL이 해제되면 또 다른 요청 스레드가 GIL을 소유하게 되더라도 해당 스레드도 sleep을 호출해서 GIL을 다시 해제하기 때문에 결국 0.01초 동안 GIL을 소유해 작업을 처리할 수 있는 스레드는 로더 스레드가 된다. 그래서 요청 스레드들은 while 한 턴 지나는 아주 잠깐 동안 GIL을 소유하지 곧바로 sleep으로 GIL을 해제하기 때문에 로더 스레드는 지연이 거의 없이 인덱싱 작업을 완료하게 되어 약 1초정도에 끝나게된다.
  >
  > threading.Event
  >
  > * 요청 처리 스레드는 wait을 호출해서 다른 스레드에 lock을 넘기고 그 lock을 로더 스레드가 소유해서 작업을 지연없이 처리하기 때문에 인덱싱 작업을 약 1초 정도에 끝내게 된다.

- 에이전트 피드백: 로딩 시간 설명은 셋 다 맞다(`pass`·`sleep`은 혼자 설명). 다듬은 점: (1) `pass`는 'CPU를 점유해서 GIL을 갖는다'가 아니라 `while` 문이 파이썬 코드를 계속 실행하므로 GIL이 필요하고, GIL을 쥐고 도는 동안 CPU를 쓴다. 1/(1+N)은 매번의 확률보다 N+1개 스레드가 GIL 시간을 고르게 나눠 쓸 때 로더가 받는 몫으로 보는 것이 정확하다. 로딩 시간은 로더의 1초와 기다리는 스레드 CPU의 합과 거의 같다(1+3.87≈4.84, 1+7.79≈8.71). 한 번에 한 스레드만 파이썬 코드를 실행했다는 뜻이다. (2) `sleep`은 잠깐 깨서 확인하고 다시 자므로 CPU도 0.003초/0.010초뿐이었다. (3) `Event`는 lock이 GIL을 뜻했다면 방향은 맞다. 정확히는 요청 처리 스레드가 `wait()`에서 블록되어 `set()` 전까지 깨어나지 않으므로 GIL을 아예 요청하지 않는다(CPU 0.000초). `Event` 안의 락은 로더의 계산과 상관없다. 빠진 점: 마지막 깨어남과 CPU 값은 설명에 쓰지 않았다.
- 왜? 1(에이전트): `sleep`과 `Event`는 로딩이 둘 다 1초인데 마지막 깨어남은 `sleep`이 8.7ms, `Event`가 0.12ms/0.31ms였다. 왜 이렇게 차이가 나는가.
- 사람의 질문(원문): "마지막 깨어남이 뭐야?". 에이전트가 뜻을 다시 설명했다(로더가 계산을 끝낸 시각부터 요청 처리 스레드마다 기다리는 코드를 빠져나온 시각까지의 차이 중 가장 큰 값, 예: 로더 1.000초, 스레드 넷 1.001~1.004초면 4ms).
- 사람의 답(원문): "로더 작업이 언제 끝나도 일단 sleep이 호출된 시점으로부터 0.01초 동안 기다린 후에 깨어나지만 Event는 로더 작업이 끝난 직후에 깨어나기 때문이야."
- 에이전트 피드백: 맞다(혼자 설명). 더 정확히는 `sleep`에서 늦어지는 시간은 로딩이 끝난 순간 각 스레드에게 남아 있던 잠 시간이다. 스레드마다 잠든 시점이 달라 그 값은 0~10ms 사이로 흩어지고, 4개나 8개 중 가장 늦은 스레드는 10ms에 가깝다. 그래서 마지막 깨어남의 중앙값이 10ms보다 조금 짧은 8.7ms였다.
- 왜? 2(에이전트): `sleep`의 스레드는 정해진 시간이 지나면 운영체제가 깨운다. `Event`의 스레드는 무엇이 깨우길래 로더가 끝나자마자 깨어나는가(묶음 2의 조건 변수와 견주어).
- 사람의 답(원문): "로더 스레드가 깨우기 때문에 끝나자마자 바로 알 수 있는거 아니야? 로더 스레드에서 ready.set을 호출하잖아."
- 에이전트 피드백: 맞다(혼자 설명). `sleep`은 시간이 지나야 깨고, `Event`는 조건을 바꾼 로더가 직접 깨운다. CPython 3.14.2의 `Event`는 깃발 하나와 조건 변수 하나(`Condition(Lock())`)로 만들어져 있다. `wait()`는 깃발이 내려가 있으면 내부 조건 변수의 `wait()`로 블록되고, `set()`은 깃발을 올린 뒤 `notify_all()`로 기다리던 스레드를 모두 깨운다([threading.py L591-L671](https://github.com/python/cpython/blob/v3.14.2/Lib/threading.py#L591-L671)). 요청 처리 스레드가 모두 출발해야 하므로 `notify()`가 아니라 `notify_all()`이다. 한꺼번에 깨워도 깨어난 스레드가 내부 락과 GIL을 차례로 잡아야 해서 8개(0.31ms)가 4개(0.12ms)보다 오래 걸린 것으로 본다(차례로 잡는 과정은 재지 않았다).

### 변형 문제 1: 버퍼 크기 1과 조건 변수 하나

- 문제(에이전트): 문제 상황 2를 `while`로 고친 코드에서 버퍼 크기를 1로 줄이고, 작업자 t1·t2가 둘 다 `take()`에서 기다리는 중에 업로드 요청 스레드가 `put(1)`, `put(2)`를 연달아 부른다. 조건 변수는 `cond` 하나이고 `notify()`를 쓴다. 두 작업을 다 처리하고 끝까지 가는가. 대기열에 누가 어떤 순서로 서고 `notify()`가 누구를 깨우는지 따라가며 설명한다.
- 사람의 답(원문): "두 작업 모두 처리될거라 생각해. put(1)이 호출되고 put(2)가 바로 호출되면 put(1) 호출 스레드는 jobs에 job을 추가하고 cond.notify를 호출해서 take 1 스레드를 깨워. 그리고 그 사이에 put(2)는 put의 while에서 wait으로 블록되어있어. 그러고 take 1 스레드에서 jobs.popleft 호출 이후에 cond.notify를 호출하면 put(2) 스레드가 job을 추가하고 take 2를 cond.notify로 깨워. 그러면 take 2 스레드에서 jobs.popleft를 호출해서 job을 소비하고 cond.notify로 다른 스레드를 깨워. 그런데 여기서 다른 스레드가 뭔지 모르겠네. 이러면 두 작업은 모두 처리되지만 마지막은 empty jobs를 호출하고 index error로 끝날거 같아."
- 에이전트 확인할 지점: (1) t1이 `popleft()` 뒤 `notify()`를 부를 때 대기열에는 t2와 업로드 요청 스레드가 있다. 둘 중 누가 먼저 기다리기 시작했는가. (2) `take()`도 `while`이므로 빈 `jobs`에서 깨어난 작업자는 `IndexError`를 내는가, 무엇을 하는가.
- 사람의 답과 질문(원문): "1. 업로드 요청 스레드가 먼저 서 있어. / 2. 아, while이라면 take는 에러가 나지 않고 wait을 호출해 블록 상태로 전환될거야. / 그런데, 대기열에 대기중인 스레드가 없을 때 notify를 호출하면 어떻게 되는거야? t2에서 notify가 호출되어도 대기열에 대기중인 스레드가 없을거 같은데"
- 에이전트 설명과 피드백: 기다리는 스레드가 없으면 `notify()`는 아무 일도 하지 않는다(파이썬 문서: no-op). 알림은 쌓이지 않아 나중에 `wait()`를 부른 스레드는 받지 못한다. 세마포어의 `release()`는 카운터에 남지만 `notify()`는 그 순간 기다리던 스레드에게만 전해진다. 그래서 조건 변수는 바뀐 것을 `jobs` 같은 공유 상태에 남기고 깬 쪽이 `while`로 다시 확인한다. 2번은 맞다(혼자 답함). 1번은 틀렸다. t2는 처음부터 기다렸고, `put(1)`의 `notify()`가 맨 앞의 t1을 깨운 뒤 대기열은 `[t2]`이며, 업로드 요청 스레드는 `put(2)`에서 그 뒤에 서서 `[t2, 업로드]`가 된다(에이전트가 알려 줌).
- 사람의 답(원문): "아, 문제에서 t1,t2가 기다리는 중이라고 했구나. 그러면 t1의 notify는 t2를 깨울거야. 그리고 t2는 빈 jobs를 확인하고 while 문에서 wait을 호출하고 put(2) 업로드 요청 스레드가 블록 상태에서 재개한 뒤에 job을 하나 추가하면 대기중인 t2가 새로 추가된 job을 처리할거야. 그래서 결과적으로 두 작업이 다 처리될거야."
- 에이전트 설명(예제와 설명 단계): t1의 `notify()`가 t2를 깨우고 t2가 다시 `wait()`한다는 데까지는 맞다. 빠진 것은 업로드 요청 스레드를 깨우는 스레드가 없다는 점이다. `wait()`에서 블록된 스레드는 `notify()`를 받기 전에는 돌아오지 못한다. 대기열은 처음 `[t1, t2]` → `put(1)`이 t1을 깨워 `[t2]` → `put(2)`가 가득 차 기다려 `[t2, 업로드]` → t1이 꺼내고 t2를 깨워 `[업로드]` → t2가 빈 `jobs`를 보고 다시 기다려 `[업로드, t2]` → t1이 작업 1을 처리하고 돌아와 기다려 `[업로드, t2, t1]`이 되고, 아무도 `notify()`를 부르지 않아 멈춘다. 컨테이너 임시 확인(CPython 3.13·3.14.2, 본 측정 아님): 실험 코드의 `put()`·`take_while()`에 버퍼 크기 1로 20번 돌려 20번 모두 작업 1만 처리하고 세 스레드가 대기열에 남은 채 멈췄다. 업로드 요청 스레드에게 가야 할 알림을 같은 대기열 맨 앞의 t2가 받고 다시 잠들어 알림이 사라진 것이다. 묶음 2에서는 잘못된 깨움이 `IndexError`나 헛깨움으로 끝났지만, 생산자가 기다리는 상황에서는 멈춤이 된다. `while`만으로는 부족하고 조건 변수 두 개(`not_full`, `not_empty`)가 필요하다. `notify_all()`도 멈춤은 막지만 모두를 깨운다. 이 변형 문제는 도움받은 부분이다(대기열 순서와 '깨워 주지 않으면 돌아오지 않음'). 사람이 스스로 짚은 것은 `while`이면 빈 `jobs`에서 깬 작업자가 오류 없이 다시 기다린다는 점이다.

### 변형 문제 2: 자기 계좌로 이체

- 문제(에이전트): 묶음 4에서 고친 두 이체 함수로 자기 계좌에 이체한다(`transfer(a, a, 1)`, 락은 `threading.Lock()`, 스레드 하나). 4번 락 순서 고정과 5번 내려놓고 다시는 각각 어떻게 되는가. 락을 `threading.RLock()`으로 바꾸면 어떻게 달라지는가.
- 사람의 답(원문): "4번은 잠김 상태에서 잠김 상태로 전환하려고 시도하다가 runtime error가 발생할거 같아. / 5번은 무한루프에 빠질 것이라 생각해. / RLock으로 바꿔도 마찬가지야. 결국 같은 스레드가 해당 RLock을 제어하는 거라서."
- 에이전트 확인할 지점: 5번은 맞다(혼자 답함). `blocking=False`는 이미 잠긴 락이면 바로 `False`를 돌려주므로 쥔 락을 풀고 쉬었다 다시 하기를 끝없이 되풀이한다. 나머지는 두 곳을 확인하게 했다. (1) 잠긴 `Lock`에 `acquire()`를 부르면 오류가 나는가 기다리는가, 묶음 1의 `RuntimeError`는 `acquire()`와 `release()` 중 어디서 났는가, 기다린다면 그 락은 누가 풀어 줄 수 있는가. (2) `RLock`은 주인 스레드를 기억한다. 주인 스레드가 이미 쥔 `RLock`을 한 번 더 `acquire()`하면 어떻게 되는가(R은 reentrant, 재진입).
- 사람의 답(원문): "1. acquire는 잠김 상태면 대기하는구나. 그러면 계속 대기할거 같아. 이걸 풀어줄 다른 스레드가 없어. / 2. 이건 재진입하겠구나 release를 두 번 하면 에러도 안날테니까 작업이 진행되겠네"
- 에이전트 피드백: 둘 다 맞다(확인할 지점을 받은 뒤 답함). 잠긴 `Lock`에 `acquire()`를 부르면 기다리고, 풀어 줄 스레드가 자기 자신뿐이라 영원히 기다린다. `RLock`은 주인 스레드가 다시 잡을 수 있고 잡은 횟수만큼 풀면 된다. 컨테이너 임시 확인(CPython 3.13·3.14.2, 실험 코드의 `transfer_ordered`·`transfer_retry`, 2초 제한, 답을 받은 뒤 밝힘): `Lock`이면 둘 다 끝나지 않았고, `RLock`이면 둘 다 끝났다(다시 시도 0번, 잔액 그대로). 스레드 하나만으로도 자기가 쥔 락을 기다리며 멈출 수 있고, A→B와 B→A로 확인한 고친 코드도 같은 계좌라는 경계에서 다시 멈출 수 있다. 고칠 때는 `src is dst`면 처음에 바로 돌아가게 하는 것이 가장 분명하고, `RLock`으로 바꾸는 것도 방법이다. 처음 답에서 헷갈린 점은 잠긴 `Lock`의 `acquire()`가 `RuntimeError`를 낸다고 본 것(오류는 풀린 락의 `release()`에서 난다)과 `RLock`도 같은 스레드라 마찬가지라고 본 것이다.

### 상황별 도구 선택

- 질문(에이전트): 상황마다 고를 도구와 근거(측정값이나 문답에서 확인한 것)를 한두 줄로 적는다. (1) 외부 API를 동시에 최대 4개까지만 부른다. (2) 여러 스레드가 공유 자료를 바꾸는 구간에 한 번에 하나만 들어가게 한다. (3) 한 스레드가 넣은 작업을 여러 작업자가 꺼내 처리한다. (4) 준비가 끝날 때까지 여러 스레드를 기다리게 했다가 한꺼번에 출발시킨다. (5) 락 두 개 이상을 함께 잡아야 한다.
- 사람의 답(원문):

  > 1. BoundedSemaphore, 최대 동시 작업 개수의 상한이 정해져있다.
  > 2. Lock, with lock: 구문을 쓰면 임계영역에 하나의 스레드만 진입하게 만들 수 있다.
  > 3. Condition, 요청자의 요청이 추가되면 대기하던 작업자들이 맡아서 처리할 수 있다.
  > 4. Event, Event.set으로 여러 스레드가 공유하는 상태를 전환할 수 있다.
  > 5. RLock, 재진입이 가능해서 한 스레드에서도 둘 이상의 Lock을 잡을 수 있다.

- 에이전트 피드백: 1~4번은 고른 도구가 맞다(혼자 답함). 근거를 측정값으로 보탰다. (1) `BoundedSemaphore`도 묶음 1에서 동시 호출이 7까지 느는 것을 막지 못했다. 남는 `release()`가 카운터를 상한 위로 올리려는 순간(34~40번째)에야 `ValueError`로 알린다. `Semaphore`는 끝까지 조용했다(끝난 뒤 카운터 7). 상한을 지키는 것은 `with`로 잡고 푸는 짝을 맞추는 쪽이고(고친 코드 넷 모두 상한 이하, 오류 0번), `BoundedSemaphore`는 실수를 드러내는 안전장치다. (2) `Lock`은 주인이 없어 남이 쥔 락까지 풀려 동시 호출이 4까지 늘었으므로 `with lock:`으로 짝을 맞추는 것이 중요하다. 같은 스레드가 같은 락을 다시 잡는 구조면 `RLock`(변형 문제 2). (3) `Condition`도 맞지만 실제로는 `queue.Queue`를 먼저 고른다. 락 하나와 조건 변수 두 개(`not_full`, `not_empty`)에 `while`까지 갖춰져 있다. 직접 짜면 묶음 2(`if` → `IndexError`)와 변형 문제 1(조건 변수 하나 → 멈춤)의 함정을 밟기 쉽다. (4) `Event`는 로딩 1초를 지켰고(바쁜 대기 4.84초/8.71초), 0.12ms/0.31ms 만에 모두 깨웠고, 기다리는 동안 CPU를 쓰지 않았다(`sleep` 확인은 8.7ms 늦음).
- 에이전트 확인할 지점(5번): 계좌마다 `RLock`을 두고 문제 상황 4처럼 t1은 A→B, t2는 B→A로 동시에 이체하면 멈추는가. `RLock`의 재진입은 같은 스레드가 '같은 락'을 다시 잡는 경우이고, 서로 다른 두 락은 `Lock`으로도 한 스레드가 함께 쥘 수 있다.
- 사람의 답(원문): "그러게 5번은 Lock이 더 적절하겠다"
- 에이전트 힌트: 락 종류는 `Lock`이면 충분하다. 그러나 `Lock`이어도 문제 상황 4 코드 그대로면 멈췄다(이체 1번 10번 중 10번). 5번의 답은 어떤 락을 쓰느냐보다 어떻게 잡느냐다. 묶음 4에서 10번 모두 멈추지 않은 두 방법을 근거와 함께 적게 했다.
- 사람의 답(원문): "락 순서를 고정해서 순환대기를 피했어"
- 에이전트 피드백: 맞다(힌트 뒤 답함, 두 방법 중 하나). 락 순서 고정은 이체 4번 10번 모두 끝남(2.79초), 철학자 2번 10번 모두 끝남(0.70초)이 근거다. 두 번째 방법은 내려놓고 다시다. 둘째 락을 바로 못 잡으면 쥔 락을 풀고 무작위로 쉬었다가 다시 한다(이체 5번 10번 모두 끝남, 다시 시도 1,147번에도 시간은 4번과 거의 같은 2.78초). 쉬는 시간을 무작위로 두는 것은 두 스레드가 같은 박자로 부딪히고 물러나기를 되풀이하지 않게 하려는 것이다. 고르는 기준(에이전트, 일반 지식이며 이번에 비교하지 않음): 필요한 락을 미리 알 수 있으면 순서 고정을 먼저 쓰고, 첫 락을 잡은 뒤에야 다음 락이 정해지는 경우처럼 순서를 정하기 어려우면 내려놓고 다시를 쓴다. 어느 쪽이든 두 락이 같은 경우(자기 계좌 이체)는 따로 처리한다. 처음 답(`RLock`)에서 헷갈린 점은 재진입이 다른 스레드 사이의 순환 대기를 막는다고 본 것이다.

## 정리한 결론과 선택 기준

아래는 측정값과 사람의 답을 대조해 정리한 결론이다. 시간은 워밍업을 뺀 중앙값이다. 측정은 맥의 일반 CPython 3.14.2(GIL 켜짐) 한 가지이므로 GIL을 끈 빌드나 다른 언어로 일반화하지 않는다.

| 상황 | 이번에 확인한 내용과 선택 기준 |
|---|---|
| 동시에 N개까지만 부르기 | `acquire()`와 `release()`를 `with`로 짝지으면 네 도구 모두 상한을 지켰다(100회 모두 4·4·1·1, 오류 0번). 짝이 어긋나면 `Semaphore`는 동시 호출이 7까지 조용히 늘었고(끝난 뒤 카운터 7), `BoundedSemaphore`도 7까지 늘었다가 34~40번째의 `release()`에서야 `ValueError`로 알렸다. 상한을 지키는 것은 짝을 맞춘 코드이고 `BoundedSemaphore`는 짝이 어긋난 것을 늦게라도 드러내는 안전장치다. 상한에는 `BoundedSemaphore`를 `with`로 쓴다. |
| 공유 자료를 바꾸는 구간에 한 번에 하나 | `Lock`은 주인을 기억하지 않아 남이 쥔 락도 풀 수 있고, 그래서 이중 `release()`가 오류 없이 동시 호출을 4까지 늘렸다. 오류는 원인(5·15·25번째 타임아웃)과 떨어진 36~40번째의 다른 호출이 받았다. `RLock`은 주인을 기억해 그 호출 자신에서 바로 `RuntimeError`를 냈다(동시 호출 1). `Lock`을 `with lock:`으로 쓰고, 같은 스레드가 같은 락을 다시 잡아야 하는 구조에서만 `RLock`을 쓴다. |
| 생산자·소비자 버퍼 | 깨어난 뒤 조건을 다시 보지 않는 `if`는 업로드마다 작업자를 잃었고(회마다 `IndexError` 1~3번), 남은 작업자 수만큼 20개 처리 시간이 2배·4배(1.99~2.01배, 3.92~3.93배)가 됐다. `while`은 30번 모두 작업자를 지켰다. `notify()`는 누가 어느 함수에서 기다리는지 가리지 않아 생산자에게 갈 알림을 작업자가 받기도 했고(빈 `jobs`에서 깨어남 회마다 1~9번), 버퍼 크기 1에서는 이것이 멈춤으로 이어졌다(변형 문제 1, 컨테이너 임시 확인). 직접 짜면 `while`과, 락 하나를 함께 쓰는 조건 변수 둘(`not_full`, `not_empty`)을 쓴다. 실제로는 이를 갖춘 `queue.Queue`를 먼저 고른다. |
| 준비가 끝날 때까지 기다렸다 한꺼번에 출발 | 바쁜 대기(`pass`)는 GIL을 나눠 써서 1초 로딩을 4.84초·8.71초로 늘렸다(기다리는 스레드 CPU 3.87초·7.79초). `sleep(0.01)` 확인은 로딩 1초를 지켰지만 마지막 깨어남이 8.7ms 늦었다. `Event.wait()`는 로딩 1초, 마지막 깨어남 0.12ms·0.31ms, 기다리는 스레드 CPU 0초였다. 여러 스레드를 한 신호로 출발시킬 때는 `Event`를 쓴다. 돌면서 기다리는 것은 기다림이 재웠다 깨우는 비용보다 짧고 락을 쥔 쪽이 다른 코어에서 실제로 돌고 있을 때만 이득이다(문답으로 정리, 측정하지 않음). |
| 락 두 개 이상 | 서로 반대 순서로 잡은 이체는 10번 모두 첫 이체에서 멈췄다. 락 안의 느린 I/O를 빼도(이체 3번) 20만 번 동안 10번 중 9번 멈췄으므로 '쥐는 시간이 짧으면 괜찮다'는 기대는 맞지 않았다. 락 순서 고정(이체 4번 2.79초, 철학자 2번 0.70초), 내려놓고 다시(이체 5번 2.78초, 다시 시도 1,147번), 웨이터 `Semaphore(4)`(철학자 3번 0.75초)는 10번 모두 끝났다. 필요한 락을 미리 알면 락 순서 고정을 먼저 쓰고, 순서를 정하기 어려우면 내려놓고 다시를 쓴다(이 고르는 기준은 일반 지식이며 이번에 비교하지 않았다). 어느 쪽이든 두 락이 같은 경우(자기 계좌 이체)는 따로 처리한다. |
| 가끔만 멈추는 교착 상태 | 철학자 1번은 10번 중 6번 멈췄고, 멈춘 6번은 모두 먹은 횟수 0, 처음을 넘긴 4번은 끝까지 갔다. 측정 직전의 작은 입력 검증에서는 철학자 1번이 한 번도 멈추지 않았고 이체 3번도 2회 모두 끝났다. 몇 번 돌려 멈추지 않았다는 것으로 교착 상태가 없다고 판단하지 않고, 락 순서 같은 구조로 막는다. |

질문 10의 세 조건으로 다시 보면, 묶음 1의 `Lock`에서 동시 호출이 4까지 늘어난 것은 상호 배제가 깨진 것이고, 이체 1번에서 두 스레드가 모두 멈춘 것은 진행이 깨진 것이다. 둘 다 측정에서 나타났다. 내려놓고 다시에서 한 스레드만 계속 밀리는 기아는 한정 대기를 깨는 경우이지만, 이번 측정에서는 10번 모두 끝났고 스레드별로 밀린 횟수는 기록하지 않았다. 파이썬 `Lock`이 기다리는 스레드 중 누가 먼저 들어갈지 정하지 않아 한정 대기를 보장하지 않는다는 것은 문서로 확인한 내용이며 재지 않았다.

CPython 3.14.2에서 `Condition.notify()`가 먼저 기다린 스레드부터 깨우고 기다리는 스레드가 없으면 아무 일도 하지 않는다는 것, `Event`가 깃발과 조건 변수로 만들어져 `set()`이 `notify_all()`을 부른다는 것, `BoundedSemaphore.release()`가 초깃값을 넘는지 검사한다는 것은 소스와 공식 문서로 확인했다([threading.py](https://github.com/python/cpython/blob/v3.14.2/Lib/threading.py), [threading 문서](https://docs.python.org/3.14/library/threading.html)). 버퍼 크기 1의 멈춤, 따로 만든 조건 변수 둘의 `RuntimeError`, 자기 계좌 이체는 컨테이너(Linux x86_64, CPython 3.13·3.14.2)에서 임시로 확인했을 뿐 본 측정이 아니며 원자료를 남기지 않았다.

### 구현에서 사용한 자료구조

측정 틀과 고친 코드는 모두 에이전트가 썼다(묶음 1에서 사람이 요청했고 다음 묶음도 같은 방식으로 했다). 고친 방법 중 번호가 큰 포크 먼저는 사람이 문제 상황 5에서 제안한 것이다.

- 묶음 1의 가짜 API(`FakeApi`)는 실험 대상과 다른 측정용 락 하나로 들어간 순서, 지금 들어와 있는 호출 수와 그 최댓값을 센다. 상한 도구는 `RecordingSlots`로 감싸 요청별 `acquire()`·`release()` 결과를 목록에 덧붙이고, 지금 어느 요청인지는 `threading.local()`에 둔다. 목록은 따로 잠그지 않아 기록이 실행 순서에 주는 영향을 줄였다.
- 묶음 2의 버퍼는 문제 상황 2처럼 `collections.deque`(`append`, `popleft`)와 조건 변수 하나다. 조건 변수는 `RecordingCondition`으로 감싸 아직 깨우지 않은 대기 수와 빈 `jobs`에서 깨어난 횟수를 그 조건 변수의 락 안에서 센다. 깨우는 순서는 감싼 `threading.Condition`이 정한다. 작업자를 끝낸 예외는 `threading.excepthook` 자리에 둔 기록 객체가 받는다.
- 묶음 3의 준비 신호는 깃발과 `threading.Event`를 함께 가진 `Ready` 하나로 두어, `pass`·`sleep`은 깃발을, `event`는 `Event`를 본다. 시각은 모든 스레드가 같은 시계(`perf_counter()`)로 재고, 기다리는 스레드의 CPU 시간은 스레드마다 `thread_time()`으로 잰다.
- 묶음 4의 계좌는 이름·잔액·락을 가진 `Account`이고, 락 순서 고정은 계좌 이름으로 정렬해 잡는다. 포크는 `threading.Lock` 다섯 개의 목록이고 웨이터는 `threading.Semaphore(4)`다. 철학자마다 먹은 횟수는 자기 칸만 바꾸는 목록에 둬 따로 잠그지 않았다. 멈춘 스레드가 다음 실행에 남지 않도록 실행마다 자식 프로세스를 새로 띄우고, 10초 안에 끝나지 않으면 `faulthandler`로 모든 스레드의 스택을 남긴다.
- 원자료는 JSON Lines로 저장하고 환경 파일에 코드의 `source_sha256`을 남겼다. 반복마다 조건 순서를 뒤집어 시간에 따른 기계 상태 변화가 한 조건에 몰리지 않게 했다.
