# 07 스키마 설계와 정규화

요구 사항을 테이블로 옮기고, 한 테이블에 몰아넣었을 때 생기는 삽입·갱신·삭제 이상을 MySQL에서 직접 일으킨 뒤 나눈 테이블을 JOIN으로 되살려 무손실 분해를 확인한다. 같은 예약 100만 건을 정규화 판(JOIN)과 비정규화 판(회원 등급 복사)으로 두고 읽기·쓰기 시간을 재며, 외래 키가 있을 때와 없을 때의 INSERT 시간과 부모 행에 걸리는 락을 본다. MySQL에서만 한다. 공통 규칙은 [작업 지침](../../AGENTS.md)을 따른다.

2026-11-19에 목표와 범위를 정하고 묶음 ①②를 손으로 했고, 2026-11-20에 ②를 맥에서 실행해 확인한 뒤 ③④의 예상을 받고 본 측정을 했다. 2026-11-23에 학습 확인을 했고, 그 문답은 [완료 후 학습 확인](#완료-후-학습-확인)에, 정리한 결론은 [정리한 결론과 선택 기준](#정리한-결론과-선택-기준)에 있다.

복습할 때는 [앞면·뒷면으로 정리한 카드](../../anki/07-schema-normalization.md)를 쓴다.

## 목표

실험을 마치면 다음을 할 수 있어야 한다.

1. **옮기기:** 요구 사항 몇 줄을 보고 엔터티, 관계 차수, 연결 테이블, 키를 정해 테이블로 옮기고, 키를 고른 이유를 말한다.
2. **설명:** 한 테이블에 몰아넣었을 때 생기는 삽입·갱신·삭제 이상을 함수적 종속으로 설명하고, 나눈 뒤 JOIN으로 원래 행이 그대로 나오는지(무손실 분해)를 보인다. 외래 키가 쓰기에 거는 비용(검사, 부모 행의 공유 락, 자동 인덱스)을 실험 4·5와 이어 설명한다.
3. **고르기:** 정규화(JOIN)와 비정규화(칼럼 복사)를 읽기 시간과 바뀔 때 고칠 행 수로 고르고, 외래 키를 걸지 말지를 무결성과 쓰기 비용으로 고른다.

확인 방법은 03~06과 같다. 측정 전에 적은 예상을 실측과 대조하고, 완료 후에는 아래 질문에 해설 없이 답해 직접 잰 숫자를 넣어 답한 수와 "왜?"에 두 번까지 답한 수를 센다. 질문마다 답하기 전에 맞힐 것 같은지를 한 줄로 먼저 말한다.

### 확인할 질문

1. 1:1·1:N·N:M 관계는 어떻게 테이블로 옮기고, N:M은 왜 연결 테이블로 푸는가.
2. 자연 키와 인조 키 중 기본 키로 무엇을 쓰는가.
3. 삽입·갱신·삭제 이상은 무엇이고 왜 생기는가.
4. 함수적 종속과 1·2·3정규형은 각각 무엇을 없애는가.
5. 외래 키 칼럼에 인덱스를 두는 이유는 무엇인가.
6. 외래 키 제약을 실무에서 거는가.
7. 정규화는 꼭 해야 하는가, 비정규화는 언제 하는가.

계획에 있던 RDB와 문서형 데이터베이스(MongoDB) 비교는 ⑤를 빼면서 이 실험에서 묻지 않았다.

## 다룰 범위

| 묶음 | 볼 것 |
|---|---|
| ① | 카셰어링 요구 사항 다섯 줄(회원·차량·예약·결제·공동 운전자)을 테이블로 옮기고 관계 차수와 키를 고른 이유 |
| ② | 회원·차량 정보를 예약 행에 몰아넣은 `reservation_flat`에서 이상 셋을 SQL로 일으키고, 나눈 테이블을 JOIN해 원래 행과 `EXCEPT`로 비교 |
| ③ | 회원 10만·예약 100만에서 정규화 판(`reservations_n` + `members`)과 비정규화 판(`reservations_d`에 `member_plan` 복사)의 읽기 둘(Q1, Q2)과 등급 변경 둘(U1, U2). 비정규화 판 인덱스를 `(member_id, started_at, member_plan)`으로 바꿔 다시 잼 |
| ④ | 외래 키만 걸었을 때 생기는 인덱스(P1), 같은 인덱스를 둔 외래 키 있음/없음의 예약 10만 건 INSERT(P2), 커밋 전 INSERT가 부모 행에 거는 락과 부모 UPDATE의 대기(P3) |

①은 손으로, ②~④는 맥에서 했다. ①의 테이블과 ②의 되살리기 쿼리는 사람이 썼고, 측정 코드는 에이전트가 썼다(2026-11-19 사람이 고른 범위). 계획에 선택으로 있던 ⑤ MongoDB 비교는 환경을 새로 띄워야 해 뺐다.

## 시작 전 기록

아래는 측정 전의 예상과 그 뒤의 문답이다. 사람의 답은 원문 그대로 옮겼다(메시지의 줄 바꿈은 " / "로 적음). 옵티마이저가 내놓은 숫자는 추정, 에이전트가 확인하지 못한 설명은 추측으로 적는다.

### 지난 실험의 변형 문제 (2026-11-19)

- 문제(에이전트, 06의 "결과 행 먼저 따지기"와 "JOIN과 LIMIT"): users (1, kim) (2, lee) (3, park), orders (10, 1, 'paid') (11, 1, 'paid') (12, 2, 'cancel'). 회원 2명을 결제한 주문과 함께 보여 주려고 `SELECT u.name, o.id FROM users u LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid' ORDER BY u.id, o.id LIMIT 2;`를 썼다. (1) 결과 행 (2) 회원 2명이 나오나, 아니면 고치기.
- 사람의 답(원문): "맞힐 것 같아. / 1. (kim, 10) (kim, 11) / 2. 회원은 kim 하나만 나와. 결제한 회원이 1명인데 2명이 나오게 할 수는 없어."
- 에이전트 피드백: 1은 맞다. 2는 kim 하나만 나온다는 것은 맞지만 까닭이 다르다. LEFT JOIN이라 lee·park도 NULL로 남아 조인 결과는 4행이고, `LIMIT 2`가 조인 결과 행에 걸려 kim의 두 행에서 끝난다. 고친 판은 `FROM (SELECT id, name FROM users ORDER BY id LIMIT 2) u LEFT JOIN …`이다.
- 셈: 1/2 맞음, 1/2 반쯤. 예상 적중에는 넣지 않았다.

### 묶음 ①: 요구 사항을 테이블로 (2026-11-19)

- 요구 사항(에이전트): 1 회원은 이메일로 가입하고 이름과 등급(일반·골드)을 가진다. 2 차량은 번호판으로 구분되고 차종과 시간당 요금을 가진다. 3 회원은 차량 하나를 시작·끝 시각을 정해 예약한다. 회원도 차량도 여러 번 예약될 수 있다. 4 예약 하나에 결제가 여러 번 있을 수 있다. 5 예약에 다른 회원을 공동 운전자로 여러 명 더할 수 있고, 한 회원이 여러 예약의 공동 운전자가 될 수 있다.
- 사람의 답(원문, 처음 답을 고친 판): "반반 / members(id PK, email PK, name, plan) / cars(id PK, number PK, type, fee) / drivers(id PK, member_ids) / reservations(id PK, driver_id FK, car_id FK, started_at, ended_at) / payments(id PK, reservation_id FK, type, amount) / drivers: cars = 1:N / reservations: payments = 1:N / id는 auto increment를 사용해서 인덱스 리프에 더 빠르게 행을 추가할 수 있게 만들었어. 그리고 unique해야하는 email, number를 추가로 PK로 선언했어."
- 에이전트 피드백: 네 테이블과 예약:결제 1:N, auto increment를 클러스터형 인덱스 끝에 붙는 것으로 설명한 것은 맞다. 기본 키는 테이블에 하나뿐이고 email·number는 `UNIQUE`(대체키)로 건다. 회원:예약, 차량:예약 1:N이 빠졌다.
- `drivers.member_ids = '3,5'`로 "회원 5가 공동 운전자인 예약 찾기"를 어떻게 쓰고 무엇이 어려운지 물었다. 사람(원문): "음, drivers를 없애고 그냥 reservations에 member_id를 직접 추가하고 reservations 행을 같은 car_id와 하나의 그룹으로 reservation을 묶을 수 있는 unique 후보키가 되는 컬럼을 추가하도록 수정해야하려나.. 네 질문에는 답을 못하겠어. SQL을 어떻게 쓰고 무엇이 어려운지는 몰라". 에이전트가 설명했다. `LIKE '%5%'`는 15·25도 걸리고 `FIND_IN_SET`은 인덱스를 못 쓰며, 문자열 안의 값에는 외래 키를 걸 수 없고, 한 칸에 값이 여럿이면 원자값이 아니라 제1정규형을 어긴다. 예약 행을 운전자마다 복제하는 안은 시각·차량이 반복돼 갱신 이상이 생긴다. N:M은 `reservation_drivers(reservation_id FK, member_id FK, PRIMARY KEY (reservation_id, member_id))`로 푼다.
- 복합 기본 키가 막아 주는 것. 사람(원문): "맞힐 것 같아. 같은 예약에 같은 멤버가 중복으로 등록되는걸 막을 수 있어." 맞다.
- 셈: 처음 답 반쯤, 힌트 질문 모르겠어, 이어서 맞음.

### 묶음 ②: 한 테이블에 몰아넣은 예약 (2026-11-19)

- 표(에이전트): `reservation_flat(reservation_id PK, member_email, member_name, member_plan, car_number, car_type, car_fee, started_at)`에 (1, kim@a.com, kim, 일반, 12가3456, 모닝, 5000, 11-20 09:00) (2, kim@a.com, kim, 일반, 12가3456, 모닝, 5000, 11-21 09:00) (3, lee@a.com, lee, 골드, 34나5678, 아반떼, 8000, 11-20 13:00). 장면 (A) kim을 골드로 올렸는데 `WHERE reservation_id = 1`만 고쳐 kim이 일반·골드 둘 (B) 예약이 없는 새 차 56다7890을 넣을 곳이 없음 (C) 예약 3을 지웠더니 34나5678 정보까지 사라짐. 각각 왜 생기는가.
- 사람의 답(원문): "(A) 반반 / 데이터 정합성이 소실됐다고 해야할까. kim에 대한 행은 1, 2행 두 개인데 reservation = 1인 행의 plan만 골드로 바뀌어서 1행이 조회되는 화면에서는 골드로 보이고 2행이 조회되는 화면에서는 일반 플랜으로 보이는거야. / (B) 못 맞힐 것 같아. / 데이터 사이에 서로 의존관계가 있는데 이게 순환의존성을 가져서 데이터를 새로 생성할 수 없는거라고 생각해. 각 컬럼이 NULLABLE이 아니라면 모두 어떤 값으로 채워져야 하지만 다른 값이 먼저 채워져야 하는 컬럼끼리 서로 순환의존하고 있으면 발생할 수 있는 현상이라고 생각해. / (C) 못 맞힐 것 같아. / 정규화되어서 서로 분리되어 관리되어야할 데이터가 한 행에서 모두 관리되기 때문에 발생하는 현상이야. 뭐라고 부르는지는 모르겠어."
- 에이전트 피드백: (A)는 갱신 이상이고 까닭은 회원 등급이 예약 행마다 반복되기 때문이다(반쯤). (B)는 삽입 이상이고 순환 의존이 아니라 기본 키가 `reservation_id`라 예약 없이 행을 만들 수 없기 때문이다(틀림). (C)는 삭제 이상이고 까닭은 맞다.
- 함수적 종속. 물음: `member_email`을 알면 정해지는 칼럼, `car_number`를 알면 정해지는 칼럼. 사람(원문): "* member_name, member_plan / * car_type, car_fee" 맞다. 에이전트가 `reservation_id → member_email → member_plan`을 이행적 함수적 종속, 제3정규형을 "키가 아닌 칼럼은 기본 키에만 직접 종속"으로 설명했다.
- 나눈 테이블(①과 같은 모양)에서 원래 3행을 되살리는 쿼리. 사람(원문): "맞힐 것 같아. / SELECT r.id, m.email, m.name, m.plan, c.number, c.type, c.fee, r.started_at FROM (reservations r LEFT JOIN members m ON r.member_id = m.id) LEFT JOIN cars ON r.car_id = c.id;" 맞다(`cars` 뒤 별칭 `c`가 빠진 오타 하나).
- 왜? 1(LEFT를 INNER로 바꾸면 달라지나). 사람(원문): "맞힐 것 같아. / 달라질 건 없어. reservations는 members와 cars에 의존하고 있기 때문에 reservations 행이 존재한다는 건 members나 cars에 그 예약에 필요한 행들이 이미 존재한다는 것이기 때문에 reservations의 행만 존재해서 reservation_id는 null이 아니지만 다른 컬럼이 null인 경우는 없기 때문이야." 반쯤이다. 외래 키와 NOT NULL이 지켜질 때만 같다.
- 왜? 2(예약이 있는 회원 kim을 DELETE하면). 사람(원문): "반반이야. / delete on cascade 옵션이었나, 그게 켜져있으면 reservation도 같이 삭제될거라 생각해" 반쯤이다. 외래 키가 없으면 고아 행이 남고, 외래 키 기본값이면 DELETE가 오류 1451로 막히며, `ON DELETE CASCADE`면 예약도 지워진다. 지켜 주는 것은 외래 키 제약(참조 무결성)이다.

### 묶음 ③ 예상 (2026-11-20)

- 조건(에이전트): 회원 10만(등급 일반·골드), 예약 100만(회원 1은 1만 건, 회원 2~99001은 10건씩), 두 판 모두 `idx_member (member_id, started_at)`. Q1 회원 1의 최근 예약 20건과 등급, Q2 골드 회원의 예약 수, U1 회원 1의 등급 변경, U2 예약 10건인 회원 2의 등급 변경. 어느 판이 빠르고 몇 ms쯤인지, U1·U2는 고칠 행 수.
- 사람의 예상(원문): "* Q1. 맞힐 것 같아. * 비정규화판이 빨라. 소요시간은 정확히는 모르겠지만 아마 시간이 큰 차이는 안 날거라 생각해. 그 이유는 정규화판은 조인이 필요하기 때문이야. * Q2 맞힐 것 같아. * 정규화판이 빨라. 소요시간은 10ms 이상 큰 차이가 날거라 생각해. 그 이유는 비정규화판은 풀스캔을 하지만, 정규화판은 골드 회원 행만 찾은 뒤에 reservations와 조인을 수행하면 더 적은 행을 탐색할 수 있다고 생각했기 때문이야. * U1 맞힐 것 같아. * 정규화판. 소요시간은 정규화판이 작아. 그 이유는 정규화판은 한 행만 찾아서 수정할 수 있는데 비해 비정규화판은 회원 1인 행 10행을 모두 찾아서 plan을 수행해야하기 때문이야. * U2 맞힐 것 같아. * 정규화판. 소요시간은 큰 차이는 안 날거라 생각해. 다만, 정규화판이 더 빠르다고 생각한 이유는 예약 10건인 회원의 행을 비정규화 회원마다 10행씩 수정해야하지만 정규화판은 한 행씩만 수정해서 작업을 처리할 수 있기 때문이야."
- U1의 회원 1을 10건으로 읽은 것은 에이전트가 조건만 다시 짚었고, 측정 전 고친 예상은 없었다.

### 묶음 ④ 예상 (2026-11-20)

## 첫 해석

- Q1(2026-11-20): JOIN이 있는 정규화 판이 왜 빠른가. 사람(원문): "모르겠어. / 커버링 인덱스로 O(1)로 행을 찾을 수 있는건가? / 그런데 (plan, id) 인덱스는 없었잖아?" 에이전트가 설명했다. 커버링은 O(1)이 아니라 찾은 뒤 클러스터형 인덱스로 다시 가지 않는 것이다. 정규화 판에서 `reservations_n`이 쓰는 칼럼(id, member_id, started_at)은 모두 `idx_member` 리프에 있고(기본 키가 리프에 붙음, 실험 5), `members`는 `m.id = 1`인 상수 조회 1행이다. 비정규화 판은 `member_plan`이 인덱스에 없어 20건마다 클러스터형 인덱스로 다시 간다.
- 비정규화 판 Q1을 커버링으로 만들려면. 사람(원문): "반반 / (member_id, plan) 보조 인덱스를 추가하는거라고 생각해." 반쯤이다. `started_at`이 빠져 커버링이 아니고 정렬이 필요하다(맥에서 이 인덱스를 달아 보니 옵티마이저는 쓰지 않았고, `FORCE INDEX`로 쓰게 하면 `Using filesort`). `(member_id, started_at, member_plan)`이어야 한다.
- U1 재측정이 왜 느려졌나. 사람(원문): "모르겠어." 에이전트가 설명했다. 앞 판에서 `member_plan`은 행에만 있어 행만 고쳤지만, 새 인덱스 판에서는 보조 인덱스 키에도 있어 1만 1행마다 인덱스 항목을 지우고 새 자리에 넣는 일이 더해진다. `Using temporary`는 훑는 인덱스의 칼럼을 고쳐 행을 먼저 모은 것으로 보이나 확인하지 않았다.
- P3에서 B가 왜 기다렸나. 사람(원문): "맞힐 것 같아. / RR에서는 삽입 의도락과 레코드 락은 서로 충돌하기 때문에. 삽입 의도락을 가지고 있는 A가 변경사항을 커밋하기 전까지 B는 레코드락을 획득할 수 없기 때문에 충돌이 발생하고 대기 상태가 된거야." 반쯤이다. A가 커밋할 때까지 B가 기다린 것은 맞지만, A가 가진 것은 외래 키 검사가 부모 `members` id 1에 건 레코드 락(S 모드)이고 B의 UPDATE는 같은 레코드 락을 X 모드로 원해 충돌했다. 격리 수준과 상관없다. 이 문답 중 사람이 "공유락 배타락을 모드라며?"라고 짚어 에이전트가 종류(레코드·갭·넥스트 키·삽입 의도 락)와 모드(S·X)를 섞어 쓴 것을 바로잡았다.
- 외래 키 검사가 왜 커밋까지 공유 락을 잡나. 사람(원문): "뭔가 부모행의 변경이 이를 외래키로 가리키는 행에 영향을 줄 수도 있는건가? 이유를 모르겠는데? 굳이 필요한가?" 에이전트가 설명했다. 확인과 커밋 사이에 다른 트랜잭션이 부모를 지우거나 키를 바꾸고 커밋하면 고아 행이 생기므로 커밋까지 잡는다. 다만 이번 B처럼 외래 키와 상관없는 `plan`만 바꿔도 레코드 락이 행 단위라 막힌다. 이것이 외래 키의 쓰기 비용이다.

- 장면: 회원 기본 키를 `email`로, 예약·결제가 외래 키로 가리킨다.
- 답(원문): "서로 다른 유저의 중복된 이메일이 서로 충돌해서 한 쪽은 회원가입을 할 수 없어. / 그냥 users.id가 항상 unique하기 때문에 외래 키로 사용하기에 합리적이라고 생각해." 반쯤이다. 인조 키를 고른 것은 맞지만 든 문제는 `email UNIQUE`로도 생기는 것이라 기본 키라서의 문제가 아니다.
- 왜? 1(kim이 이메일을 바꾸고 예약 50·결제 80이 있을 때). 답(원문): "130건을 고쳐야겠네" 맞다(회원 행까지 131행, 외래 키면 `ON UPDATE CASCADE` 없이는 오류).
- 왜? 2(4바이트 INT 대신 30바이트쯤의 email이 기본 키면 보조 인덱스는). 답(원문): "행마다 크기가 26바이트 증가할거야. 그러면 한 리프에 포함될 수 있는 인덱스 행의 수가 감소해서 더 많은 인덱스 저장공간을 필요로 할거야." 맞다. 에이전트는 자식 테이블의 외래 키 칼럼·인덱스도 커지고, 이메일은 순서 없이 들어와 리프 중간에 끼어든다고 보탰다.

### 질문 3: 삽입·갱신·삭제 이상

- 장면: `order_lines(order_id PK, product_id, product_name, product_price, qty)`에서 (가) 상품 7 가격 인상 (나) 안 팔린 새 상품 등록 (다) 상품 9가 팔린 유일한 주문 취소.
- 답(원문): "(가) 갱신이상, 근데 이게 이상현상인거야? 그냥 가격을 올려야 한다는 요구같은데? / (나) 삽입이상, 존재하지 않는 상품을 주문 내역에 포함시킬 수는 없어. / (다) 삭제이상, 이것도 그냥 주문내역에서 9번을 주문한 행을 제거할 뿐인데 이상현상인 이유가 뭐야?" 이름 셋은 맞고 (가)(다)의 까닭은 되물었다(반쯤). 에이전트가 이상은 요구가 아니라 그 요구를 처리할 때의 부작용이라고 설명했다. (가)는 상품 7이 팔린 모든 주문 행을 고쳐야 하고, (다)는 상품 9가 있다는 사실까지 사라진다. 주문 당시 가격은 일부러 주문 행에 두는 값이라는 것도 보탰다.

### 질문 4: 함수적 종속과 정규형

- 장면: `enrollments(student_id, lecture_id, student_name, grade)`, 기본 키 `(student_id, lecture_id)`.
- 답(원문): "보조키, 함수형 종속, 제 1정규형, 제 3정규형 이렇게 용어들이 떠오르는데 하나같이 정확하게 내가 의미를 설명할 수가 없어. 그래서 답을 모르겠어. 그냥 용어만 떠올라" 모르겠어.
- 줄인 물음(`student_name`은 둘 다 알아야 정해지나). 답(원문): "student_id만 알면 students 테이블에서 student_id로 해당 행을 조회해서 student_name을 알아낼 수 있어." 맞다. 에이전트가 부분 함수적 종속과 제2정규형, 1·2·3NF·BCNF가 없애는 것을 표로 정리했다.
- 왜? 1(`reservation_flat`의 `reservation_id → member_email → member_plan`은 부분인가 이행적인가). 답(원문): "member_plan은 부분 함수적 종속을 어겨서 제 2정규형을 어겼어." 틀림이다. 기본 키가 칼럼 하나라 "키의 일부"가 없고, 키가 아닌 칼럼을 거쳐 정해지므로 이행적 함수적 종속, 제3정규형이다.

### 질문 5: 외래 키 칼럼의 인덱스

- 답(원문): "확신은 못하겠어. / 다만 질문의 문맥을 보면 외래 키를 가진 행들이 해당 외래 키 컬럼의 값이 바뀌면 함께 바뀌어야 하기 때문에 외래 키 칼럼의 인덱스를 둬서 그 수정 작업을 더 빠르게 처리하기 위함일거라 생각해." 반쯤이다. CASCADE가 없어도 부모를 지우거나 키를 바꿀 때 "가리키는 자식이 있나"를 확인해야 한다.
- 왜? 1(예약 100만, 인덱스 없음, 예약 없는 회원을 DELETE). 답(원문): "인덱스가 없으면 100만 행 모두 읽어야 해. 해당 행이 어떤 회원을 가리키는지 실제로 읽어볼 때까지는 알 수 없어. / 인덱스가 있으면 어떤 행이 해당 회원을 가리키는지 정렬된 인덱스를 훑으면서 회원id가 변하는 시점까지만 읽어서 알 수 있어." 맞다.

### 질문 6: 외래 키를 거나

- 장면: 저녁마다 예약이 몰리는 카셰어링 서비스.
- 답(원문): "확신은 없어. / 그런데 외래키를 걸어야 데이터 정합성이 안전하게 지켜질 수 있을거라 생각해." 반쯤이다(근거 숫자와 대가 없음).
- 왜? 1(무엇을 치르나, 숫자로). 사람이 "4가 뭔지 기억 안 나"라고 해서 에이전트가 ④ 결과를 다시 적었다. 답(원문): "뭔가를 기다리는 시간을 대가로 치를거 같은데, 너가 준 P3 표에서 members 행이 가리키는 대상 행 id 1과 cars가 가리키는 대상 행 id 1은 서로 같은 행을 말하는거야? 어느 테이블의 id를 가리키는거야?" 이어서(원문): "3초, 0.0015초가 너가 원하는 답이야? 그런데 전자는 측정한게 아니고 그냥 설정해둔 기준 값이잖아. 전자는 측정된 적이 없는데? / 외래 키가 삽입 작업을 얼마나 지연시켰는지는 모르겠어." 반쯤이다. 3.018초가 대기 한도에 잘린 값이라 B의 대기 시간을 잰 것이 아니라는 지적은 맞다. P2의 약 14%(1.29초 대 1.13초)는 넣지 못했다.

### 질문 7: 비정규화는 언제

- 장면: ③의 두 표와 질문 3의 주문 당시 가격.
- 답(원문): "회원 등급을 예약행에 복사해두면 회원 등급을 수정할 때 예약행까지 모두 수정해야해서 작업 처리 시간이 더 길어질거라 생각해. 그래서 비정규화는 부적절하다고 생각해. / 주문 당시 가격은 사실 복사한다기 보다는 도메인 관점에서는 그 행의 컬럼으로 봐야해. / 그 이유는 주문 당시에 결정된 가격이기 때문에 여러가지 할인 같은 정책이 적용된 후의 새로운 값으로 봐야하고 그 값은 그 당시 상황에서만 유효하기 때문에 그 당시 상황의 데이터를 모두 갖고 있는 해당 주문 내역 행에 포함되는게 데이터 정합성이 더 잘 지켜질 수 있다고 생각해." 반쯤이다. 고른 쪽과 까닭은 맞고 숫자가 없다. 주문 당시 가격은 결정자가 다른 사실(`상품 → 지금 가격`, `주문 줄 → 낸 가격`)이라 비정규화가 아니라는 설명은 혼자 정확히 했다.
- 왜? 1(근거 숫자). 답(원문): "U1, U2의 고친 행 수를 보면 알 수 있어." 맞다(1 / 10,001과 1 / 11).
- 왜? 2(비정규화가 맞는 때). 답(원문): "극단적인 경우지만 정규화된 테이블의 데이터를 한 화면에서 표현하고 싶을 때 매번 조인을 해서 데이터를 조회하기 보다는 조회용으로 비정규화된 테이블을 구성해서 조회 요청에 해당 테이블을 참조하도록 만들 때 필요하다고 알고 있어. 또 다른 경우가 있을까?" 맞다. 에이전트는 집계값 칼럼, 다른 테이블 칼럼으로 거르고 정렬해야 해 인덱스 하나로 못 풀 때, DB가 나뉘어 JOIN을 못 할 때를 보탰다.

### 처음 보는 문제 1 (목표 1): 도서관

- 요구 사항: 1 회원은 휴대폰 번호로 가입하고 이름을 가진다(번호는 바뀔 수 있다). 2 책은 ISBN과 제목, 같은 책을 여러 권, 권마다 바코드. 3 책 한 종에 저자 여럿, 저자도 여러 책. 4 회원이 실물 한 권을 빌리고 반납, 빌린 날·반납한 날, 같은 권을 여러 번 빌릴 수 있다.
- 답(원문): "members(id PK, phone_number UNIQUE, name) / authors(id PK, name) / books(ISBN PK, title) / authors_books(id PK, author_id FK, book_id FK) / lents(id PK, member_id FK, book_id FK, borrowed_at, returned_at)" 회원(인조 키 + `UNIQUE`)과 저자, 연결 테이블, 대출을 `id` 기본 키로 둔 것은 맞다. 실물 권 테이블이 없어 대출이 책 종류를 가리키고, 연결 테이블의 중복 막기가 다시 빠졌다.
- 왜? 1(3권 중 A-2를 kim이 빌렸을 때 어느 권이 대출 중인지 아나). 답(원문): "아, 그건 알 수 없어. books에 id PK와 ISBN은 일반행으로 둬야겠구나" 반쯤이다.
- 왜? 2(그 판에서 제목 오타를 고치면). 답(원문): "3행을 함께 고쳐야 해. / 갱신 이상이야. / ISBN, title을 별도 테이블로 빼고 books에서 이걸 참조하도록 만들어야겠네. 이게 2NF인가?" 맞다(책 종류와 실물 권을 혼자 나눔). 다만 2NF가 아니라 3NF(키가 `id` 하나, `id → isbn → title`)다.
- 셈: 6칸(회원·저자·책·연결·실물 권·대출) 중 맞음 2, 반쯤 3, 빠짐 1.

## 정리한 결론과 선택 기준

| 상황 | 고를 것 | 근거 |
|---|---|---|
| N:M 관계 | 연결 테이블, 짝에 `UNIQUE` 또는 복합 기본 키, 짝마다 다른 값(신청 날짜)은 연결 테이블에 | 한 칸에 여러 값은 제1정규형 위반이고 외래 키·인덱스를 못 씀(묶음 ①). 보통 인덱스는 중복을 막지 않음(질문 1) |
| 기본 키 | 인조 키(auto increment) + 자연 키는 `UNIQUE` | 자연 키는 바뀌면 자식 행까지 고침(질문 2: 131행), 길면 모든 보조 인덱스 리프가 커짐 |
| 한 테이블에 다른 것의 정보가 섞임 | 함수적 종속을 보고 나눔. 키 일부에 종속하면 2NF, 키가 아닌 칼럼을 거치면 3NF로 고침 | ② 이상 셋을 맥에서 재현, 나눈 뒤 JOIN이 원래 행과 `EXCEPT` 0행·0행 |
| 읽기가 느림 | 비정규화 전에 인덱스 모양(커버링) | Q1 정규화 0.892ms 대 비정규화 3.038ms, 커버링 인덱스 뒤 1.167 대 1.198ms |
| 비정규화 | 복사본이 적고 원본이 드물게 바뀌며, JOIN·집계를 인덱스로 못 풀 때만 | U1 1 / 10,001행 2.874 대 41.893ms, 복사 칼럼을 인덱스에 넣으면 74.395ms. U2 1 / 11행은 2.152 대 2.063ms로 차이 없음 |
| 그 시점의 값(주문 당시 가격) | 그 행의 칼럼 | 결정자가 다른 사실이라 비정규화가 아님(질문 7, 사람의 답) |
| 외래 키 | 무결성이 중요하면 걸고, 쓰기 경합이 큰 부모 행이 있으면 대가를 잼 | P2 약 14% 느림(1.292 대 1.132초, COMMIT 동기화 포함), P3 부모 행 S 모드 레코드 락으로 부모 UPDATE가 A의 커밋까지 대기 |
| 외래 키 칼럼 인덱스 | 둠(InnoDB는 없으면 만듦) | 부모 DELETE·키 변경 때 자식 확인이 100만 행 스캔이 됨(질문 5), P1 `KEY member_id` 자동 생성 |
